## B01. Common protected command pipeline

W02–W06 invoke this single executor, not route-specific transactions. No external network effects occur.

1. Parse `body` with `warehouseCommandBodySchema` even for a direct service caller; map parser issues to existing `ValidationException` with `body.` paths. Reject duplicate/budget/unknown privileged fields before locks. Canonicalize normalized groups/IDs; hash JSON `{operation,orders:canonicalGroups}` with SHA-256, excluding commandId but including versions, exact members, attempt IDs and every capture value. No trimming/significant-text rewrite beyond C02. Do not stringify a Prisma Decimal/raw record.
2. Start `database.$transaction` with ReadCommitted, maxWait5000ms, timeout10000ms, existing bounded P05/P06 profile. Set transaction-local lock_timeout5000ms using parameterized `$queryRaw`. No timeout increase or transaction-internal external I/O.
3. `lockAccountRows(tx,[actorId],'read')`, `loadIdentityAccount`, `assertBusinessAuthority(actor,'WAREHOUSE')`. Hold the account SHARE lock through COMMIT so staff suspension/reassignment serializes; current authority is checked before replay/observation as well. No body actor/role grants authority.
4. Lock command key using transaction advisory lock: first16 hex characters SHA-256 of `p07-warehouse-command:`+canonical command UUID, convert with `BigInt.asIntN(64,BigInt('0x'+prefix)).toString()`, then parameterized `pg_advisory_xact_lock(key::bigint)`. Do not use JavaScript number for64-bit key. This is a warehouse-specific copy of the existing pattern, not a call to private P06 commandLock.
5. Read `WarehouseCommand` by commandId with WAREHOUSE_COMMAND_SELECT. If present, require exact actorId/operation/payloadHash; otherwise WAREHOUSE_COMMAND_CONFLICT. Return `mapWarehouseCommandResult(retained,true)` without checking later mutable order state or issuing another write. Current actor eligibility remains required; original command result contains no private customer snapshots.
6. For a fresh intent, acquire existing submitted `sales_drafts` root rows `FOR UPDATE` in sorted UUID order **before** loading mutable pieces/status. All P03–P06 commands use this root boundary; no separate piece-lock hierarchy is added. A missing/non-SUBMITTED root, nonparticipating order or missing reviewed piece relation is ORDER_NOT_FOUND before exposing version/state. The warehouse relation C05 also applies to ADMIN's warehouse context. No P04 child-command lock is needed because P07 invokes no P04 command.
7. Use WAREHOUSE_LOCKED_ROOT_SELECT and bulk load at most200 **selected** physical contexts and latest accepted/receipt/attempt/correction facts through the same tx. Compute per-order physical counts/blocker booleans with indexed aggregate SQL, without loading up to200 complete captured orders. For delivery, compare active count to reviewed count first, then compare selected identity/order membership and current receipt state; these checks establish full active equality while loading≤200 selected rows. RECEIVE reads only its selected sources/receipt contexts plus order aggregates. No40,000-piece captured payload enters the command pipeline. Require current root.version==expectedVersion and expectedVersion<2147483647; otherwise whole-batch ORDER_VERSION_CONFLICT. Validate every group's operation predicates in W02–W06 **before any business write**. Reject any invalid group/member unchanged. Do not silently update expectedVersion or choose substitute IDs.
8. After all preconditions hold, capture one server `occurredAt=new Date()` for the complete atomic batch. Reuse the exact parsed `body.commandId` for the root command; allocate only event/group/attempt/outcome/retry UUIDs as needed. Never replace the frozen intent key. Compute exact final statuses/versions/immutable safe outcome. Insert command once with its final validated outcome, then its CommandOrder rows and operation-specific children. Deferrable graphs permit parent/child sequencing; no mutable placeholder outcome and no update to INSERT-only command rows.
9. Apply exact conditional physical/order writes. Every `updateMany` predicate repeats relevant locked order/status/stage/receipt/cancellation constraints and requires the exact expected count (one physical per selected identity, one header per group). Advance each order once with actual existing `advanceApprovalOrderVersion(tx,{orderId,expectedVersion,occurredAt})` imported from approval-command.writer.ts. It is a genuine existing generic root-update primitive despite its name; overflow was checked before effects. No new standalone version counter or nested P04 execution.
10. Map/parse the stored safe result, then let the transaction COMMIT run all graph/immutable/head constraints. Return success only after transaction resolves. Failure in any required child/status/version/history save rolls back every group/order. Do not return a success before COMMIT or turn a thrown raw database error into fixture data.

Transaction retry: reuse actual `isSalesLockTimeout`, P2034 and P06's inspected typed PostgreSQL40001/40P01 classification pattern. Only the new `WarehouseCommand` commandId P2002 conflict and true serialization/deadlock retry once with the same frozen parsed input/key; on second conflict throw WAREHOUSE_TRANSACTION_CONFLICT. Lock timeout55P03 returns conflict without blind retry. A business selection/unique receipt/outcome conflict is not a serialization retry; map expected unique races to WAREHOUSE_SELECTION_CONFLICT. Unexpected graph/constraint failure is a safe internal error, not indiscriminately 409. Preserve actual diagnostic classification in redacted server logs/request ID; expose no SQL/Prisma values.

Lock order across modules: account SHARE → warehouse advisory command lock → sorted SalesDraft roots → bounded child writes. P04/P05/P06 hold the same root before mutable domain effects and do not acquire warehouse keys, so no inverse cross-module lock is introduced. Staff writes acquire account write locks and cannot change authority midcommand. Two warehouse batches overlapping roots use the same canonical order and settle winner/loser without partial effects.

## W01. Reads, participation and reconciliation

FR-001–004/008–010/024–027; VR-001/003/006/008.

1. Service read wrapper uses RepeatableRead, maxWait5000/timeout10000 and lock_timeout5000. Lock/load/recheck actor as B01 step3. Retry actual serialization/deadlock once; do not rerun read as anonymous on business failure.
2. Build the fixed participating-order CTE from Quality INSPECT/ACCEPT handoff, ReceiptPiece or DeliveryAttempt, tied to same physical/order identity. Pure approval/upstream stage alone is insufficient. A retained cancelled historical member permits safe history, not work. Detail/history first authorize the exact order; unknown/foreign/upstream-only results are the same ORDER_NOT_FOUND. A requested history piece must actually belong to that order or be the same missing result.
3. Build one physical-order count aggregate from all retained physical pieces and the strict W08 formula. Choose queue predicates exactly C05; only active membership contributes readiness. An unresolved hold/correction/open manufacturing visit cannot be ready. No counter table, local segment ledger, date clock or received carton count substitutes for physical pieces.
4. Apply type/search/optional requested orderId to matching queue-piece relation. Use fixed parameterized predicates and escaped literal search (ILIKE wildcards in user input are escaped; no user SQL). Search term may match business/customer header or exact piece/model/retained worker names; expose only permitted matching records. Compute count distinct orders/count pieces from this same relation before page slicing. Header counts remain whole-order counts. Echo department/view/orderId even for empty pages, binding C06 context.
5. Page identities in C07 deterministic order using existing parsePaginationQuery/buildPaginationMeta. Lists never load every order to filter in JavaScript. Grouped limit≤25, flat≤100; default25. Dashboard accepts the same search/type scope and independently counts six queue relations in one read snapshot, not sums overlapping inventory. A true empty page is successful empty data; a failed count/query is a safe read failure.
6. Load page roots, selected physical rows, latest accepted events, receipt groups, latest attempts/outcomes/retries and required quality-packing registry in bounded bulk maps. DISTINCT ON/LATERAL joins use order/piece/version keys; no Promise.all across arbitrary rows. For flat/detail packing, resolve distinct optional group references from the current authorized accepted-source command/order/piece identities. Join `quality_packing_groups packing` to `quality_command_orders g` on command_id/order_id and `quality_commands c` on command_id with `c.operation='INSPECT'`; bind each reference to that source ACCEPT event and its full original packing-piece membership. Select `packing.order_id AS "orderId"` and `${qualityPackingSummarySql} AS packing` using parameterized identities. Parse each unknown projection with the existing `qualityPackingGroupSchema`, verify group/order, `inspectionId=g.event_id`, and the source command/piece bindings before deduplication by group ID. Store the validated `QualityPackingGroup[]` in each applicable context. Preserve complete original acceptedPieceIds, significant carton text, inspectorNote, original inspector and packedAt; never shorten a group to the page subset. Flat registry bounds remain100 groups, detail200; grouped summaries do not load a packing registry they do not return. A genuinely absent optional source group is null/unrecorded; a missing referenced group, invalid projection or mismatched identity is a safe internal read failure. Refuse >200 retained pieces on a detail/201 sentinel rather than truncating evidence. Detail has safe full paper, one work context per paper piece, minimal contact and only latest attempt. Load earlier attempts/history separately.
7. `mapManufacturingPaper` + current `findIssueInstructions(...,'FACTORY')` produces safe accepted specifications/current issue instructions. It includes no money/customer-master/raw proposals. Add submitted name/phone/address only in separate WarehouseOrderData.deliveryContact (address stays null if absent). Return named schemas, private/no-store headers and C01 envelope.
8. Activity pages warehouse CommandOrder event IDs for permitted orders first, then joins immutable command/child facts. Order history adds existing manufacturing/quality/safe issue event identities for the exact permitted order, optional matching piece. Exclude SUBMIT_CONTACT/proposed fields/raw P04 facts. Reuse `qualityIssueActivityEventSchema` as C07 permits; projection is a new warehouse-owned safe SQL query, not an alleged exported private Quality helper. Ensure original grouped upstream event membership is retained. Sort/count across the union before projection, never concatenate separately paged lists.

Reads do not repair root status, backfill legacy receipt or create warehouse history. Any contradictory current graph yields a safe server error. Existing-data normalization is D04 migration work. A witnessed Quality handoff appears incoming/incomplete before first receipt; safe companion locations remain visible for reconciliation.

## W02. RECEIVE exact incoming physical pieces

FR-005–010/020–027; applies B01 and C03 RECEIVE.

1. Require order.status APPROVED and approvedAt present; selected IDs noncancelled, WAREHOUSE/INCOMING, receivedAt/issueId/currentWorkVisitId/cancelledAt/cancellationReason null, no open correction. Each must have a retained actual Quality INSPECT ACCEPT source for the same identity and no ReceiptPiece row. Legacy unwitnessed incoming cannot become actionable by opening its URL or copying a group ID.
2. Preserve source acceptance/packing group separately. Receipt carton/location/notes are only the supplied normalized capture of this arrival; absence creates no values and cannot overwrite earlier groups.
3. Precompute final physical counts after receiving selected exact IDs. If positive active exact equality and no blocker, status READY_FOR_DELIVERY; otherwise APPROVED. Allocate one ReceiptGroup per order and one ReceiptPiece per selected piece with COMMAND origin, real acceptance event and common receivedAt. Create command/group/members within B01.
4. Conditional piece update per selected identity fixes exact before state and receivedAt null, writes only workState COMPLETED and receivedAt; stage remains WAREHOUSE and all accepted specifications/paid/history untouched. Require affected1 each. Header update matches APPROVED and sets computed status, require affected1; root version advances+1 for that order, not once per piece.
5. Immutable command event/result binds every selected ID and receipt group. Repeat through same key returns original; another key encounters the nonnull receipt/unique PK and conflicts. Physical delivery return never invokes RECEIVE again.

Concrete B02/B03 proof: accepted P1/P2 with P3 production; receive P1 with carton2/Shelf B-12/note → counts1/3, one group, P2 incoming/P3 unchanged; repeated/concurrent P1 counts once. Separate P2 arrival preserves first group and P06 packing. Required child failure leaves all groups/versions unchanged.

## W03. DISPATCH reviewed whole orders

FR-009/011–013/020–027; B01 plus C03 DISPATCH.

1. Frontend has explicitly reviewed every selected order's full active IDs/quantity, including initially unselected rows. Server does not infer this scope from a quantity or first-N rows: compare supplied IDs exactly to all current noncancelled IDs under the root lock and require unchanged expectedVersion.
2. Require status READY_FOR_DELIVERY, positive exact counts received==active, every active piece WAREHOUSE/COMPLETED with matching ReceiptPiece timestamp, no issue/open correction/current manufacturing visit. Reject incomplete/zero-active/failed-awaiting-retry/dispatched/delivered or changed scope atomically. All originally cancelled pieces remain outside membership/history unchanged.
3. Load latest indexed attempt. No prior attempt→number1/predecessorRetryId null. Otherwise require latest FAILED outcome and its immutable retry, no existing successor; number=previous.number+1 within integer range, predecessorRetryId=that retry ID. A failed root without retry cannot dispatch.
4. Insert one immutable Attempt and full active AttemptMember rows, binding each to its initial receipt. deliveryNote is retained as note, never an invented representative. Update header READY_FOR_DELIVERY→OUT_FOR_DELIVERY conditionally; root+1. Physical piece stage/workState/initial receivedAt are unchanged: complete dispatch is represented by the one root transition plus exact attempt-membership scope, not invented piece delivery stages.
5. Record original dispatched-only event/attempt snapshot and safe outcome IDs. A later delivery outcome does not rewrite the dispatch event. Simultaneous/different-key dispatch is defeated by root state/version, sequential-attempt/predecessor uniqueness and graph constraints.

B04: select one row from ready two-piece order; review expands to both; cancel writes nothing, confirmed POST contains both; one attempt/membership both/root OUT. O1 ready+O2 changed→zero effects for both. Expanded total201 or body413 is denied without automatic splitting.

## W04. CONFIRM_DELIVERY for current attempt

FR-014–015/019–027; B01 plus C03 CONFIRM_DELIVERY.

1. Require root OUT_FOR_DELIVERY, supplied attemptId equals latest attempt and its parent order, no outcome/retry yet. Supplied full active IDs must equal attempt members and current active set; no subset/old-attempt result or later root mutation accepted.
2. Require all active receipt facts still intact. Store the explicitly supplied optional recipient/deliveredAt/notes; actual deliveredAt is parsed as an offset-aware instant and stored UTC, separate from common server recording time. No assumed recipient/current timestamp is filled for absent capture. Retain typed optional data only.
3. Insert unique DELIVERED Outcome for this attempt: returnedToWarehouse false, reason null. Update header OUT_FOR_DELIVERY→DELIVERED conditionally, root+1, immutable result/event with exact attempt and full membership. Piece initial receipts/manufacturing/money unchanged.
4. A competing failure/success loses by root/version/unique attempt outcome; return conflict without contradictory history. Replayed original command returns original saved result even if current order is terminal; changed original body conflicts.

B05/B08: valid explicit `2026-11-13T12:30:00Z`, recipient and note survive reload; absent optional capture stays absent; invalid/no-offset supplied instant and subset/old attempt denied unchanged; success-versus-failure yields exactly one terminal outcome.

## W05. FAIL_DELIVERY only after full physical return

FR-016–017/019–027; B01 plus C03 FAIL_DELIVERY.

1. Same current latest OUT_FOR_DELIVERY/unresolved-attempt/full-membership checks as W04. Schema requires literal returnedToWarehouse true and actual nonblank reason≤4000; backend cannot infer physical return from a network error/courier note. This is staff's explicit complete-return acknowledgement, not external sensor proof.
2. Create one FAILED Outcome with returnedToWarehouse true, entered reason/notes, recipient/deliveredAt null, server actor/time. No fake generic reason; quick-fill must be explicitly selected in existing UI.
3. Header OUT_FOR_DELIVERY→DELIVERY_FAILED, root+1. Physical receipt/group and completed manufacturing stay retained; no RECEIVE, count increase, rewind or partial-return lifecycle. Original attempt scope is immutable and all returned goods are now in warehouse custody.
4. Direct redispatch from this state remains denied until W06. Late old success/failure and repeated/different-key result attempts conflict or replay exactly as B01.

B06: missing acknowledgement/blank reason leaves state OUT unchanged; acknowledged full return yields one failed attempt, original received count unchanged. Goods partly/not returned cannot truthfully pass confirmation and no partial subsystem is invented.
