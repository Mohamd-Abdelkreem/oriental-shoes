## Summary

P07 replaces browser-local warehouse authority with explicit physical receipt and whole-order delivery commands. P06 already supplies accepted incoming pieces; it does not acknowledge physical receipt. Receive exact pieces once, retain each arrival's optional data, reconcile active/received counts, explicitly review expanded whole-order scopes, then dispatch and record one current attempt's result. Failed delivery means all goods physically returned; explicit retry restores ready before another dispatch. Every selected batch commits entirely or leaves every member unchanged.

The owner confirmed whole-order expansion with review, all-or-nothing batches and submitted customer name/phone/address for authorized warehouse delivery. Keep email, finance, unrelated history and raw snapshots outside warehouse employee output. Preserve existing Arabic/RTL/Cairo screens, dialogs, navigation, grouped/flat interaction and print presentation. No courier service, carton inventory, partial delivery or financial subsystem is introduced.

Required contracts, forward persistence/guards, current authority, bounded reads, command recovery, shared projections and real backend evidence precede dependent UI wiring. Blueprint conformance is a design claim, not implemented backend or phase acceptance.

## Contracts, Authority and Failure Design

The canonical fields and symbol names belong to [contracts/warehouse.md](contracts/warehouse.md), not duplicated schemas here. The planned route family is:

| Method/path under `/api/v1`                                         | Service intent                                                                                   |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `GET /warehouse/dashboard`                                          | Scoped order/piece counters with documented overlap                                              |
| `GET /warehouse/orders`, `GET /warehouse/pieces`                    | Bounded filtered grouped/flat reads                                                              |
| `GET /warehouse/orders/:orderId`                                    | Current permitted order, safe specifications, contacts, receipt/packing and attempt context      |
| `GET /warehouse/activity`, `GET /warehouse/orders/:orderId/history` | Bounded retained safe warehouse history                                                          |
| `POST /warehouse/commands`                                          | One canonical atomic RECEIVE, DISPATCH, CONFIRM_DELIVERY, FAIL_DELIVERY or RETRY_DELIVERY intent |
| `GET /warehouse-commands/:commandId`                                | Current-authority, originating-actor-only result observation                                     |

These endpoints are **proposed**. The real API currently composes no warehouse module. The wire owner fixes middleware order, success/error status, envelopes, schema exports, safe output and validation paths; implementation must align OpenAPI/producer/consumer together.

Warehouse authority reuses `lockAccountRows(tx, ids, 'read')`, `loadIdentityAccount(tx, actorId)` and `assertBusinessAuthority(actor, 'WAREHOUSE')`. These are existing auth exports, checked before replay/private data and at protected execution under the established account lock. Cross-order commands follow the proven command/root/physical lock order and inspect current versions, full scope and attempts before writes. Specific sequencing, constraint names and rollback/retry classification are in the backend/data owners.

Existing factory specifications remain free of contacts/finance. P07's separate contact object includes submitted name/phone/address only for a warehouse-participating order; it grants no customer directory or email/financial history access. Descriptive shelf text never becomes authority to set piece location/status. Captured actual delivery time is distinct from server action time; retry date stays a date-only value. No fixed demo clock or inferred production timezone is accepted.

### Maximum and sparse command cases

The effect budget is 200 selected pieces, not 200 contextual pieces in the database. Command execution uses the minimal locked-root selection and per-order physical count/blocker aggregate in backend B00/B01, plus at most 200 selected physical/source/receipt records. Detail-read selection remains separately bounded. Do not silently cap companion evidence or materialize full captured specifications for every companion during a write.

Two distinct future viability cases are required: one order with 200 affected pieces, and 200 participating APPROVED orders each retaining 200 active pieces with only P1 accepted/incoming. The sparse single RECEIVE selects P1 in each order: exactly 200 receipts/groups and root version increments, each order remains APPROVED with received1/active200, and all 39,800 upstream companions, specifications, packing and paid values remain unchanged. Setup finishes before timing; measure command execution through COMMIT with all guards enabled against the unchanged 10-second transaction budget. The final-required-child fault variant must leave the complete graph of all 200 orders unchanged. This validates bounded technical viability, not a new production SLA or customer volume promise.
