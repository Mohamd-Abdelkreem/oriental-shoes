The `detail` inside a review is presentation evidence, not wire input. `toWarehouseCommand` explicitly maps only canonical fields. Every command group uses exact `orderId/expectedVersion/pieceIds`; delivery operations use the full reviewed active membership and, when required, reviewed attempt ID. Technical maximum is 200 distinct affected pieces across at most 200 roots for the complete atomic action. An expanded order causing overflow blocks with reselection guidance; never split one owner-confirmed action into several requests.

The existing API parser separately applies `appConfig.bodyLimit` (default `1mb`, configurable through existing `BODY_LIMIT`). Individually valid fields can exceed that aggregate byte limit in a large batch. On HTTP 413 `PAYLOAD_TOO_LARGE`, preserve drafts and explain that no new action was admitted by this rejected request; reduce text/selection and explicitly review again. Do not increase the global body cap, split the action, truncate text or mistake this definitive initial rejection for success. If an earlier same-intent request was already unknown, a later rejected replay does not prove the earlier request failed and its recovery remains unknown.

## 3. Query/cache blueprint

Every key begins with `warehouseScopeKey(scope)`; credentials, contact text, submitted notes and command bodies never appear in keys. The normalized queries come from canonical shared schemas; raw partial search text is separate transient input.

| Read                    | Exact suffix after the P07 scope prefix                                                                          |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Dashboard               | `["dashboard", query.search ?? "", query.type ?? null]`                                                          |
| Grouped orders          | `["orders", query.view, query.search ?? "", query.type ?? null, query.page, query.limit]`                        |
| Flat pieces             | `["pieces", query.view, query.search ?? "", query.type ?? null, query.orderId ?? null, query.page, query.limit]` |
| Order detail            | `["order", orderId]`                                                                                             |
| Warehouse activity      | `["activity", query.page, query.limit]`                                                                          |
| Order history           | `["order-history", orderId, query.pieceId ?? null, query.page, query.limit]`                                     |
| Command slot            | `["command-session"]`; disabled subscriber, `gcTime: Infinity`, no fetch/auto-retry                              |
| Observe original result | `["command-receipt", commandId]`; disabled until explicit recovery, `retry: false`, `staleTime: 0`, `gcTime: 0`  |

Reads are enabled only with a current warehouse scope and valid intended input. Null inactive input uses `skipToken`; no auth-error or missing-ID request is issued. Assert scope immediately before and after every request/publication and around `reconcileBusinessDenial`. GETs pass signals. Reuse repository 30-second freshness and retry defaults for ordinary views. Explicit preparation/review always uses `fetchWarehouseOrder(... staleTime: 0)` regardless of cached freshness. Data publication uses schema validation plus `replaceEqualDeep`; a detail with a lower `summary.version` never overwrites a newer published detail for the same ID. Wrong-ID data always rejects.

UI grouped orders use page 1/limit 10, within the canonical order-page maximum 25; flat pieces page 1/limit 25, within maximum 100. Activity/history use page 1/limit 25. Changing search/type/view/mode resets page 1, selection and expanded groups; an open unsent review is closed/discarded, and no write occurs. Page navigation clears displayed selection rather than silently carrying hidden rows. Select-all means the displayed page, explicitly labelled; group selection fetches its bounded detail and uses matching IDs, never the first N pieces. Grouped/flat modes retain identical filter membership; no browser filtering of one server page as a substitute for whole-dataset search.

At most 10 expanded order details coexist on the grouped page; collapse clears only the UI expansion, not authoritative cache. Preparation of a larger explicitly selected scope fetches distinct order details sequentially in sorted order, bounded by 200 affected roots/pieces. This avoids an unbounded `Promise.all` detail fan-out. No query loads all warehouse orders into the browser.

If a returned page is beyond the new final page after a mutation/filter reconciliation, move to `max(1,totalPages)`, invalidate that exact destination before reading it and show its actual loading/error state. Zero total means zero pages and real empty data; no fabricated page contents or fallback order.

Mutation synchronization:

1. Parse/bind the accepted result to original actor/body; keep its immutable historical outcome in the command slot.
2. Cancel then invalidate current-scope `dashboard/orders/pieces/activity` prefixes and changed IDs' `order/order-history` entries; refetch active entries with errors propagated. Do not invalidate the command slot/receipt during this work.
3. For any affected cached detail, require its current `summary.version >= outcome.afterVersion`; explicitly fetch with staleTime 0 when needed. Historical command results do not overwrite current detail or regress a later operator's version.
4. Invalidate existing authorized shared tracking/read owners only if the current actor can read them: P05 department prefixes via `readManufacturingOperationalScope`/`manufacturingKeys`, P06 prefix via `readQualityOperationalScope`/`qualityKeys`, sales own-order/tracking through `readOperationalScope`/`customerKeys`, P04 approval/contact through existing capability readers/keys. ADMIN can reach several domains; warehouse employees never gain those reads. Mark existing permitted official-paper order keys stale only, without fetching or changing print eligibility. Do not create/write unconverted P08 fixture caches.
5. If any required refresh fails, state is `confirmed` with `syncError`: saved action and stale display are distinct. Offer synchronize-only retry, never another write. Only synchronized completion announces success once through the initiating surface; the persistent recovery strip remains available for closed forms and owns no duplicate toast.

The backend shared read model owns count changes across roles. A second operator sees the result through normal reload/refetch; this design adds no polling/realtime service or delivery timing guarantee.

### Upstream changes invalidate already-cached warehouse reads

`invalidateWarehouseReads` is exported from proposed **read owner** `hooks/warehouse.hooks.ts`, not the command hook. It depends only on local warehouse keys/read scope. This prevents reciprocal command-hook imports: existing quality/approval command hooks may import the warehouse read helper, while warehouse command synchronization uses quality/approval read/key owners, never imports their command hooks.

In existing `apps/web/src/features/manufacturing/hooks/quality-commands.hooks.ts` / `synchronizeQualityCommand`, after a bound accepted INSPECT result, derive affected roots with at least one `decision:"ACCEPT"` and call `readWarehouseOperationalScope(client)`. If nonnull, await `invalidateWarehouseReads(client, permittedWarehouseScope, affectedOrderIds)`; reassert the original quality scope around the await. This ensures ADMIN's cached warehouse incoming/dashboard/detail is refreshed/staled after actual P06 handoff. Another employee's warehouse session remains reload/refetch-based; no cross-account cache is accessed.

In existing `apps/web/src/features/approval/hooks/approval-commands.hooks.ts` / `synchronizeApprovalCommand`, a bound result with cancelled-piece outcome (`outcome.pieceStage === "CANCELLED"`) can reduce active requirement and make a retained received remainder ready. Obtain current warehouse scope the same way and await the same read helper for `result.receipt.orderId`, with outer P04 scope checks. No client recomputation of readiness, cancellation or quantities replaces backend output. Definite operation confirmation and failed synchronization retain the existing P04/P06 command semantics; the extra refetch cannot trigger another write.

Both calls refresh only the current actor's permitted P07 scope/resources and exclude command-session/receipt keys. On ordinary inactive cached P07 pages, mark stale so the next navigation refetches within the old 30-second freshness window. Where P07 queries are active, refetch them and propagate failures as saved-but-unsynchronized state. No global cache clear or hard-coded ADMIN assumption is needed; current capability readers decide.

## 4. Selection, review and command algorithms

### W-F01 — Exact physical receipt

1. Initiating row, group or toolbar passes explicit `WarehousePieceTarget[]`; reject empty/duplicate target identities immediately. A group uses its declared matching IDs, not every order piece. Capture initiating route/filter/account identity before async preparation.
2. Read every distinct order freshly; validate each requested piece belongs to that order, expected version agrees, the piece is uncancelled/unheld, `work.allowedActions.canReceive` is true and the accepted-handoff/initial-receipt fields match canonical eligibility. Any invalid member rejects the whole preparation; no filtered substitute selection.
3. Freeze exact resolved rows/groups. Show their piece identities and per-order receipt fields. P06 packing is read-only separate evidence; no carton/packing copy becomes an invented new receipt.
4. Form confirmation validates values, current read availability, current account, current review object, preparation guard and command-idle state, before allocating a UUID or occupying the slot. Submit one canonical RECEIVE body. Every selected order's values apply to that one receipt group; do not multiply carton text per piece or sum opaque text.
5. On definite conflict keep safe input and require explicit fresh review; on uncertain outcome use W-F04. No local piece/segment mutation or optimistic receipt.

### W-F02 — Reviewed whole-order delivery scope

1. Initiating selected rows identify distinct order IDs. Distinct P1/P2 rows from O1 resolve to one order; repeated identical target/submitted order remains invalid. Fetch all distinct details freshly with sorted bounded sequencing.
2. Resolve **every noncancelled active piece** of each affected order, including pieces outside the original filter/page/selection. Reject zero-active, excessive total membership, missing/foreign pieces, version mismatch and operation-ineligible order. Use `summary.allowedActions` and current attempt details; do not infer permission merely from received count.
3. Freeze operation, order version, sorted complete active IDs, relevant attempt ID and safe context. Display each order once with business number, all active piece identities/full count, added-outside-selection explanation and captured fields. This review is required for dispatch, complete delivery, failure and retry, even when initiated from one piece row.
4. Dispatch requires every active piece received and canDispatch. Confirm/failure require the current dispatched attempt and exact whole membership. Failure requires a checked acknowledgement meaning all goods are physically returned plus nonblank reason. Retry requires the current failed returned attempt and restores ready only. Never offer direct dispatch in the failed view or confirm delivery from ready.
5. Immediately before final submission, rerun guards and compare current cached version/membership/attempt with frozen review; stale/refetching/error data blocks admission. The server still enforces exact scopes atomically. A read or local recheck cannot replace its write predicate.
6. A stale server response changes neither captured scope nor payload. Display refresh/review, retain per-order input keyed by stable order ID and keep confirmation disabled. Explicit review refetches the **original affected order identities**, recomputes complete scope and displays changes. It does not silently add another order or replace selected receipt pieces. User confirms the newly displayed scope as a new intent only after a definite rejection; an unknown intent cannot take this branch.

### W-F03 — Read fences and form lifetime

`readAvailability` derives from the initiating order/queue plus all demanded details: `error` if any required read failed/invalid, `refreshing` if any is fetching, otherwise `ready`. Retained data during failure is visible context, not permission. Open forms keep drafts editable but disable confirmation until required reads recover. Gate both actual form `onSubmit` **before RHF starts submitting**, and parent callback, immediately before UUID/POST. Mouse, Enter, programmatic form submission and late stale callbacks follow the same gate.

Read Retry invokes only the correct GET/refetch for the original context, with a ref-based immediate duplicate guard. It allocates no command ID and cannot clear pending/unknown/confirmed command state. Keep read-retry feedback separate from write feedback so a healthy GET cannot erase an uncertain POST message. Focus the existing BaseDialog root before the retry control disappears. A rejected review callback is a read error and says no saving was attempted.

An unsent Cancel/backdrop/Escape closes/discards the local draft and writes nothing; reopening starts empty optional values from fresh review. While a command is pending/unknown/confirmed, close may hide the form but never clear its slot or claim cancellation. On route/order/account changes, close the unsent local form and invalidate preparation identity. A late preparation cannot open a dialog for another context. The QueryClient-owned command persists across same-account route/form unmount and is presented through recovery.

### W-F04 — Durable intent in the existing session lifetime

Create one UUID only at accepted user confirmation. Freeze the canonical parsed body plus originating scope before the first POST. A QueryClient slot, not component refs or mutation cache alone, owns it. Use the P06 verified slot/read-before-publish protocol with P07 schemas and errors; do not introduce browser persistence. The `pending` slot is installed synchronously so two mounted controllers cannot both admit independent commands.

| Slot state                                       | Permitted next behavior                                                                                              |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| `idle`                                           | Admit one fully prepared/reviewed new body                                                                           |
| `pending {originScope,body}`                     | Block new commands, show action/scope pending; close does not roll back                                              |
| `unknown {originScope,body,failure}`             | Explicit observe original command, or resend exact frozen body/UUID under same authority; no edited retry/new intent |
| `confirmed {originScope,body,result,syncError?}` | Saved truth; retry synchronization only                                                                              |
| `synchronized {originScope,body,result}`         | Display confirmation; explicit acknowledge clears this exact slot, then a new intent is possible                     |

Unknown classification includes network/no status, 5xx, malformed success, command binding failure and canonical `WAREHOUSE_TRANSACTION_CONFLICT`. Initial known validation/denial/conflict clears only its matching pending slot and returns to editable review. A failed exact replay stays unknown until observed/resolved; a failed GET/404 result never proves noncommit. Result binding verifies whole original order/piece scope, operation, actor, versions and receipt/attempt identities before publishing confirmed state. No implicit write retry by TanStack or React effect.

`WarehouseCommandRecovery` is mounted on dashboard, queues, activity and detail, including loading/error states. It shows original order/piece scope and action, pending/unknown/saved-refresh-failed distinction, observe/same-intent retry/synchronize/acknowledge controls with immediate ref guards and safe request-reference text. Observe uses the original scope and command ID; it cannot consume another actor's outcome. It has no editable body. After a full browser reload volatile intent is absent: existing activity exposes observe-only links for that actor's retained command IDs; no activity action replays a guessed body. The limitation is explicit and no localStorage/sessionStorage command journal is added.

On real access loss, current-scope checks fence publication/cache/toasts; cancel old reads, reset mounted observers before removing old P07 cache, and discard private local drafts. Old requests cannot restore obsolete command/contact data. Do not send an old-account command using a new account's transport. Recovery becomes available only if existing current authority legitimately permits the original actor's observation; browser state never grants that permission. Ordinary same-actor warehouse route navigation preserves the slot, and ADMIN visiting another existing department is not by itself an identity loss.
