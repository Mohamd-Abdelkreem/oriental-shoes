# P08 frontend integration blueprint

This document owns the proposed frontend design for [P08](spec.md), FR-001–027 and D-007–009. The [contract ledger](contracts/administration.md) alone owns wire fields, schemas, bounds and endpoint behavior; this file references those definitions rather than creating another schema. All new files and exports below are **proposed**. Reading source and writing this plan execute no implementation or acceptance test.

## Intake and preserved owners

Intake uses revision `382a7f5`, the existing Arabic/RTL/Cairo product, current central Axios transport, one QueryClient, real session/operational-scope lifecycle, and the owning engineering guides. Read `apps/web/AGENTS.md` and the installed Next 16.2.12 guides before implementation. The reviewed installed pages are `01-app/01-getting-started/05-server-and-client-components.md`, `01-app/03-api-reference/01-directives/use-client.md`, and `01-app/03-api-reference/04-functions/use-search-params.md` / `use-router.md` under `apps/web/node_modules/next/dist/docs/`.

Pages remain thin server compositions; interactive screens/hooks remain client entry points. New protected data fetches stay in the browser feature API through `apiClient`. Do not add protected server fetches, Server Actions, Next API routes, another session store or another QueryClient. New `useSearchParams` consumers must be beneath `Suspense` in their page composition, with the existing `SessionLoader` fallback. The installed guide explicitly requires that boundary for production prerender/build; development success alone is insufficient. Use `Link` for ordinary navigation and allowlisted route builders plus the native History API described in F02.1 for same-page filter/page changes.

Every GET accepts `signal?:AbortSignal`, passes it unchanged into the central client and returns only validated domain data. The prefix remains owned by the client's existing base URL.

Adapter algorithm: parse request with its shared schema; issue central-client request; treat successful payload as `unknown`; use `parseApiResponse(raw, owningDataSchema).data`; bind detail/history/command IDs, result kind, echoed normalized context/query, tab/page/limit and any scoped row IDs to the actual request. Compare canonical parsed fields with a fixed field order, not arbitrary raw object property ordering. A contract/context mismatch throws `ApiContractError`; it never becomes an empty result or an offline error. No component calls Axios directly.

### F01.3 Scope, keys and publication

Administration scope reads the existing `readBusinessSessionScope` private foundation and requires `user.role === "ADMIN"`. Actor ID, accessVersion and auth epoch must all match before a read starts, after it settles and immediately before cache publication. Old scope cleanup follows existing P07 reset/cancel/remove behavior: cancel prefix; recheck scope; reset each exact Query to notify mounted disabled observers; remove only that same still-obsolete query when its data is absent. Do not clear unrelated queries or use URL roles as authority.

Canonical key prefix is `administrationScopeKey(scope) = ["p08",actorId,accessVersion,epoch]`. Define one private filter tuple in fixed order: `[search??"",status??null,type??null,department??null,exception??null,salespersonId??null,period,from??null,to??null]`, using the parsed/defaulted query. `period` is ALL for all-orders and MONTH for reports when absent. Keys never contain credentials or contact correction drafts.

| `administrationKeys` member       | Suffix after scope prefix                                                   |
| --------------------------------- | --------------------------------------------------------------------------- |
| `dashboard(scope)`                | `["dashboard"]`                                                             |
| `filterOptions(scope,query)`      | `["filter-options",query.salespersonName??null]`                            |
| `orders(scope,query)`             | `["orders",...filterTuple,query.page,query.limit]`                          |
| `order(scope,id)`                 | `["order",id]`                                                              |
| `orderHistory(scope,id,query)`    | `["order-history",id,query.page,query.limit]`                               |
| `approvals(scope,query)`          | `["approvals",query.tab,query.search??"",query.page,query.limit]`           |
| `corrections(scope,query)`        | `["corrections",query.tab,query.search??"",query.page,query.limit]`         |
| `deliveryExceptions(scope,query)` | `["delivery-exceptions",query.tab,query.search??"",query.page,query.limit]` |
| `activity(scope,query)`           | `["activity",query.orderId??null,query.search??"",query.page,query.limit]`  |

| `reportPrint(scope,query)`        | `["report-print",...filterTuple]`                                           |
| private command session           | `["command-session"]`                                                       |
| private command receipt           | `["command-receipt",commandId]`                                             |

Read hooks are `useAdministrationDashboard()`, `useAdministrationFilterOptions(input)`, `useAdministrationOrders(input|null)`, `useAdministrationOrder(orderId:string|null)`, `useAdministrationOrderHistory(orderId:string|null,input)`, `useAdministrationApprovals(input|null)`, `useAdministrationCorrections(input|null)`, `useAdministrationDeliveryExceptions(input|null)`, `useAdministrationActivity(input|null)`, `useAdministrationReport(input|null)`, and `useAdministrationReportPrint(input|null)`. Input types are `z.input<typeof correspondingQuerySchema>`. Null/invalid input disables the query using `skipToken`, exposes no data and does not request a broadened default query. No conditional hook call is permitted.

The hook read helper asserts scope, calls the feature API, reasserts scope, and on failure calls `reconcileBusinessDenial(client,error,scope)` then reasserts before rethrowing. Structural sharing runtime-parses prior and incoming data, binds it to the current key context, and uses `replaceEqualDeep`; a submitted/draft detail cannot regress from a later version already published. For a detail transition from draft to submitted, the submitted kind wins over any late old draft response. Current incoming detail/tracking versions and piece sets must agree. Never publish a partial admin DTO as a factory DTO.

Reuse global 30-second read freshness and bounded network/server read retries. Commands have no automatic retry. Report-print and command receipt reads instead use `staleTime:0`, `gcTime:0`; receipt is disabled/manual-only. Every hook masks data immediately when the current scope is absent; a last successful private value is not rendered after denial or identity change.

`fetchAdministrationOrder` performs an authoritative `fetchQuery({...administrationOrderOptions(...),staleTime:0})`, then rereads the validated published cache value and checks ID/kind/version rather than returning a stale raw promise result. It is the only detail admission path for F03/F04 dialog preparation.
