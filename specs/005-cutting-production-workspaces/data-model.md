# P05 Data Model and Persistent Invariants

This is a proposed implementation design for [P05](spec.md), inspected against revision `9a7e13f`. No model, migration or application behavior below has been implemented by PLAN. The wire owner is [contracts/manufacturing.md](contracts/manufacturing.md); algorithms and source changes belong to [backend-design.md](backend-design.md).

## 1. Existing authoritative records

Retain `SalesDraft` as the stable submitted-order root and version lock, `SalesDraftPiece` as the captured physical-piece identity, and `SalesOrderPiece` as its current lifecycle. Each submitted piece has quantity one. `SalesOrderPiece.receivedAt` continues to mean **physical warehouse receipt**, never manufacturing receipt.

Preserve all existing SQL, including the immutable submitted/frozen terms, catalog bindings, money/count graph, current issue graph, P04 decision witnesses and retained command records. P05 neither recalculates money nor rewrites captured specifications, prices, numbering, customer contacts or earlier audit facts. Root versions advance once per affected order for one successful P05 batch, even if that order contributes several pieces.

## 2. Proposed schema additions

Modify `packages/database/prisma/schema.prisma` and the deliberate exports in `packages/database/src/index.ts`. Add exactly one forward migration at `packages/database/prisma/migrations/20261111000100_p05_manufacturing_workspaces/migration.sql`. The names in this section are proposed Prisma names with mapped snake-case SQL names.

### ManufacturingCommand / `manufacturing_commands`

| Field                                           | Storage and meaning                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `commandId`                                     | UUID primary key, client-generated identity of the entire exact selection                                    |
| `operation`                                     | New `ManufacturingOperation` enum: `RECEIVE_AND_START`, `CONTINUE`, `COMPLETE_TRANSFER`                      |
| `department`                                    | Existing Department, constrained to CUTTING/PRODUCTION; selected workspace context, not an actor override    |
| `actorId`                                       | User UUID FK, RESTRICT deletion                                                                              |
| `actorFullName`, `actorRole`, `actorDepartment` | Current authenticated snapshots, same limits/enums as existing command ledgers                               |
| `payloadHash`                                   | CHAR(64), lowercase SHA-256 of canonical department/operation/sorted order-version-piece sets                |
| `outcome`                                       | JSONB validated against the shared safe command outcome; contains identities, versions and piece states only |
| `occurredAt`                                    | TIMESTAMPTZ(6), one server instant for this transaction's accepted work                                      |

The command is inserted only in its successful transaction. There is no separately committed pending/failed row, deletion endpoint, expiration policy or background job. Reconciliation reads the retained success; missing is not proof that a disconnected request failed. The command actor snapshot supplies work-event and visit actor display without copying account credentials, private contacts or financial snapshots.

### ManufacturingCommandOrder / `manufacturing_command_orders`

| Field                           | Storage and meaning                                                                                 |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| `commandId`, `orderId`          | Composite primary key; FKs to ManufacturingCommand and SalesOrder                                   |
| `eventId`                       | UUID unique identity for the order's activity item; separate from a cross-order command ID          |
| `beforeVersion`, `afterVersion` | INTEGER, before >=1 and after = before+1 without integer overflow                                   |
| `pieceIds`                      | UUID[] exact distinct selected IDs for that order; 1–200, every ID bound to that order's event rows |

One batch can affect several orders. Its receipt remains one result, while each order has a distinct history identity and version. Enforce unique `(orderId, afterVersion)` inside this ledger and exact equality between retained selected IDs, event rows and the safe stored outcome. Cross-ledger serialization uses the shared root lock/version protocol, not a second version counter.

### ManufacturingWorkVisit / `manufacturing_work_visits`

| Field                                               | Storage and meaning                                                                                                                                                                         |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                                | UUID PK; also unique `(id, orderId, pieceId)` for composite bindings                                                                                                                        |
| `orderId`, `pieceId`                                | Composite FK to SalesOrderPiece `(id, orderId)`, RESTRICT deletion                                                                                                                          |
| `department`                                        | CUTTING or PRODUCTION                                                                                                                                                                       |
| `sequence`                                          | Positive INTEGER, unique `(pieceId, sequence)`, increasing across all manufacturing visits of that piece                                                                                    |
| `originKind`                                        | New enum: INITIAL_APPROVAL, APPROVAL_RETURN, DEPARTMENT_TRANSFER, QUALITY_CORRECTION, LEGACY_BASELINE                                                                                       |
| `sourceDepartment`                                  | Existing Department or null for genuinely unknown legacy source                                                                                                                             |
| `sourceApprovalCommandId`                           | Nullable P04 command UUID witness, FK deferred until commit                                                                                                                                 |
| `sourceTransferEventId`                             | Nullable ManufacturingPieceEvent UUID witness, FK deferred until commit                                                                                                                     |
| `sourceIssueId`                                     | Nullable ManufacturingIssue UUID, composite-bound to this order/piece                                                                                                                       |
| `sourceReferenceId`                                 | Nullable stable UUID of a future P06 retained rejection decision/command for one order/version; shared by its returned pieces, trusted in-process provenance, never accepted from a browser |
| `sourceCorrectionCycle`                             | Nullable positive INTEGER for QUALITY_CORRECTION only; distinct from this visit's per-piece sequence and a P04 issue cycle                                                                  |
| `sourceOrderVersion`                                | Nullable positive INTEGER for QUALITY_CORRECTION only: caller's expected root version+1; internal source witness, not a new public piece version                                            |
| `instructions`                                      | Nullable VARCHAR(4000); exact approved return instructions or retained correction instructions, never unapproved proposal values                                                            |
| `enteredAt`                                         | Nullable TIMESTAMPTZ(6); actual source transition instant when known, null for an unknown legacy baseline                                                                                   |
| `receivedAt`, `receivedCommandId`                   | Nullable manufacturing receipt instant and retained P05 command witness                                                                                                                     |
| `startedAt`, `startedCommandId`                     | Nullable original start instant and command witness; never replaced by continuation                                                                                                         |
| `endedAt`, `endReason`                              | Nullable instant and TRANSFERRED / ISSUE_REPORTED / CANCELLED; both null while open                                                                                                         |
| `endManufacturingCommandId`, `endApprovalCommandId` | Mutually exclusive nullable terminal witness: P05 transfer or P04 hold/cancellation                                                                                                         |
| `destination`                                       | PRODUCTION / QUALITY only for TRANSFERRED, otherwise null                                                                                                                                   |
| `legacyUnknownStart`                                | BOOLEAN default false; true only for a migrated in-progress state with no recorded original starter/time                                                                                    |

`receivedBy`, `startedBy` and `endedBy` are wire projections of immutable command actor snapshots, not new editable worker fields. `receivedAt` here is unrelated to the warehouse field on SalesOrderPiece. No quantity, price, current exclusive assignee or attendance field is added.

Open means `endedAt IS NULL`. Add a partial unique index on `pieceId WHERE ended_at IS NULL`: one physical piece has at most one open manufacturing visit, including across departments. Completing cutting closes its visit and opens a production visit in the same transaction. Completing production closes the visit and leaves no current manufacturing visit at quality. Reporting an issue terminates that visit as ISSUE_REPORTED; a later approved return creates a fresh visit, including when the target is the same department.

### ManufacturingPieceEvent / `manufacturing_piece_events`

| Field                            | Storage and meaning                                                                                  |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `id`                             | UUID PK, also unique `(id, orderId, pieceId)` for source bindings                                    |
| `commandId`, `orderId`           | Composite FK to ManufacturingCommandOrder                                                            |
| `pieceId`, `visitId`             | Composite-bound to the same order/piece/visit                                                        |
| `operation`                      | ManufacturingOperation equal to the parent command, retained for a database partial completion index |
| `beforeStage`, `beforeWorkState` | Existing lifecycle enum values before this command                                                   |
| `afterStage`, `afterWorkState`   | Existing lifecycle enum values after this command                                                    |

Actor and instant come from ManufacturingCommand. Enforce unique `(commandId, pieceId)` and one COMPLETE_TRANSFER event per visit using a partial index on event `operation`. The repeated operation column earns its place by enforcing this physical one-completion fact at the database boundary. RECEIVE_AND_START and CONTINUE events stay within the same department; COMPLETE_TRANSFER records the normal outgoing state. P04 report/decision events remain in their existing ledger; do not insert duplicate synthetic manufacturing actions for them.

### SalesOrderPiece extension

Add nullable `currentWorkVisitId UUID`, with deferred composite FK `(current_work_visit_id, order_id, id)` → ManufacturingWorkVisit `(id, order_id, piece_id)`. Its only meaning is the current open cutting/production visit. It does not replace `stage`, `workState`, `issueId` or warehouse receipt.

- Current CUTTING/PRODUCTION + INCOMING/IN_PROGRESS, no issue/cancellation/warehouse receipt: pointer must reference its open matching-department visit.
- BLOCKED, CANCELLED, AWAITING_APPROVAL, QUALITY or WAREHOUSE: pointer is null.
- An ended visit cannot remain pointed to; an open visit cannot be orphaned or belong to a different piece.

## 3. Database enforcement ledger

Use SQL for partial indexes and deferred constraints Prisma cannot express. Circular witness/pointer FKs use RESTRICT deletion, NO ACTION update and DEFERRABLE INITIALLY DEFERRED, following P04's established technique. Do not edit or weaken P03/P04 triggers.

Implement `check_p05_manufacturing_order_graph(affected_order UUID)` for the **current pointer/open-visit graph and immutable membership/witness relations only**. It must not scan old command afterVersions/states against current mutable pieces. Deferred piece/visit/event/command-order and relevant P04 inserts invoke this graph check. End/receive/start witness checks compare retained command instant, actor/department and operation, not merely existence of a UUID.

Use these separate deferred transition checks so historical receipts survive later valid work:

1. A constraint trigger on each **new** ManufacturingCommandOrder validates NEW's exact selected events and retained result. Its afterVersion must equal the current root head when inserted by the one-command service transaction; its affected current states match the just-created events. This trigger never runs again merely because a later root/piece changes. Every later receipt read validates immutable receipt/event equality, without a current-state equality assertion.
2. A deferred root-version UPDATE trigger applies to newly changed submitted roots: NEW.version must be OLD.version+1 and exactly one head witness exists at NEW.version across `sales_commands(draft_id,after_version)`, `approval_commands(order_id,after_version)`, `manufacturing_command_orders(order_id,after_version)` or the narrow trusted QUALITY_CORRECTION source described below. Count/validate only that version, not all previous versions. Direct new-order submission starts at version1; submitting an existing draft preserves P03's old-version+1 receipt. Both keep the actual P03 witness/graph, without assuming every first submission is version1. No second registry or independent version is added.
3. A deferred piece-transition trigger captures OLD/NEW core lifecycle fields (stage, workState, issueId, warehouse receivedAt, cancellation facts). A P05 change must match that piece's event under the current root-head order witness, including exact OLD→NEW stage/state and unchanged protected fields. A P04 change must match the selected piece's actual before/after facts at that head version and its accepted operation. Pointer-only updates run the final graph check and bind the newly opened/ended visit's actual source/terminal witness; they do not require a fabricated second lifecycle transition. This permits the existing source-owned physical update followed by visit-pointer maintenance within the same transaction. Direct core updates without a matching transition witness fail.
4. CONTINUE has unchanged physical core, so its new event/command-order checks prove its actual actor and root step. Terminal/start witness fields on a visit can change only from the allowed prior state with that matching command; a closed visit cannot reopen. Command-order/event/receipt rows are immutable, and later visits or P04 decisions never invalidate their historic before/after facts.

Test start→continue→transfer→P04 return→new visit→transfer followed by observation of **every earlier receipt** and history read; all remain valid. Test a direct arbitrary core update and a duplicate head witness reject. The future P06 root/correction witness is an explicit later integration extension described below, not silently asserted to exist now.

Future P06 provenance is deliberately not a pretend FK to an absent table. Its typed helper first verifies the caller-held root version equals `expectedVersion`, rejects overflow and stores `sourceOrderVersion=expectedVersion+1` before the caller's root CAS. For the root-head witness query, each distinct `(orderId,sourceReferenceId,sourceOrderVersion)` counts **once**, even if one order decision returns multiple pieces. A single source reference means that order's actual retained quality rejection decision/command; it is not a separately invented per-piece source ID. Per-piece `sourceCorrectionCycle` is retained independently.

The piece-transition trigger has one narrow additional branch: OLD QUALITY/IN_PROGRESS, no issue/cancellation/warehouse receipt/current manufacturing visit, → NEW CUTTING or PRODUCTION/INCOMING with its exact open QUALITY_CORRECTION visit, sourceDepartment QUALITY, nonnull shared decision reference, positive correction cycle and sourceOrderVersion equal to the current root head. It changes no captured terms or money. This permits the trusted future caller's coherent source transition without fabricating a P04/P05 command. No browser endpoint exposes that source branch. P06 must verify/bind its real correction record in the same transaction before live quality acceptance; P05's isolated labelled source fixture proves the helper/consumption only, including multiple pieces under one order-version witness. The actual quality-record provenance gate stays P06.

## 4. Query indexes and bounded work

Add indexes justified by the actual operations in backend M01/M07:

- `sales_order_pieces_department_state_id_idx(stage, work_state, id)` for current department queue membership.
- `manufacturing_work_visits_dept_piece_sequence_idx(department, piece_id, sequence DESC)` for latest department visit, returned/completed and historical relation.
- `manufacturing_work_visits_order_piece_sequence_idx(order_id, piece_id, sequence DESC)` for bounded detail history.
- `manufacturing_commands_actor_dept_time_idx(actor_id, department, occurred_at DESC, command_id DESC)` for current-actor result discovery.
- `manufacturing_command_orders_order_event_idx(order_id, event_id)` and `manufacturing_piece_events_visit_command_idx(visit_id, command_id)` for order/piece history joins.
- The command-order unique version and event indexes and existing P04 issue/source/order indexes are reused. Do not add speculative full-text/trigram/analytics indexes or a cache.

Grouped reads page at most 25 matching orders and return matching ID sets, not 25 full orders with every private record. Flat reads page at most 100 pieces. Detail loads at most the existing 200 submitted pieces and one requested-department latest visit/context per piece. History/activity are separately paged; never nest unlimited visits/events into detail. Use batched SQL joins/window ranking, not one query per order/piece/visit.

## 5. Migration and existing-data policy

1. Treat every existing migration as possibly applied. Record current file hashes and inspect the selected environment's migration history read-only before a later authorized deployment. PLAN runs no database mutation. No reset, push, old SQL rewrite or generated-client hand edit is allowed.
2. The forward migration adds tables/enums/pointer, preserves all current rows and terms, then initializes only current nonblocked CUTTING/PRODUCTION visits. It does not manufacture visits for earlier downstream departments, completed work, old actors, durations or closed correction cycles.
3. For each such piece, choose the latest **matching retained** P04 initial approval or positive issue-return/reapproval witness for this exact piece/target, if one exists. Use its actual instant/source/issue/instructions. A generic order `updatedAt` or current catalog is not provenance. Where no witness exists, use LEGACY_BASELINE with null source/reference/enteredAt and null receipt/start witnesses.
4. Existing IN_PROGRESS with no actual P05 start evidence receives `legacyUnknownStart=true`, null original starter/start/receipt and unchanged piece work state. It may be continued/completed by a currently authorized worker; new actions are real and earlier unknown work remains visibly unknown. Existing INCOMING has no manufactured receipt/start. Do not convert unknown history into historical department-participation permission.
5. Existing BLOCKED/CANCELLED/downstream pieces retain null pointer. Their existing P04 issue/decision history stays authoritative; a future actual return opens a new visit. Reject contradictory current graphs rather than clearing issue/cancellation/receipt data to make migration pass.
6. Install/validate new final-graph constraints only after backfill. Validate old terms, counts, money, versions and command hashes byte-for-byte unchanged; add no root-version increment for the schema backfill. Backfill rows do not claim employee work or a new issued command.
7. Deployment is a coordinated API/web migration change: stop/drain operational writes, apply the reviewed forward migration, deploy producer and consumer, verify. Old P04 code cannot create new released visits after the constraint becomes active; do not claim rolling compatibility. Real target deployment remains separately authorized.
8. On failed migration the transaction rolls back. After a successful migration, prefer a reviewed forward repair; do not drop newly retained history to run older application code. Recovery preparation belongs to the actual target owner/backup gate, not a destructive local reset.
