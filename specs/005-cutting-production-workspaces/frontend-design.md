## F05. Exact selection and preserved task identity

1. A row captures its actual `orderId`, current root version, piece ID and canonical work eligibility. Selection is a local map keyed by stable row key containing immutable target records, never a quantity counter or a dynamic filter expression. Select-all means the currently displayed server rows only. The transport's 200-piece total limit is enforced before confirmation with actionable feedback, not silent truncation.
2. Group actions first fetch that exact group's safe detail, require `paper.order.version === summary.version`, resolve precisely the summary's `matchingPieceIds`, and check a complete matching context/eligibility for every ID. No group button may silently choose every piece of the order. A group changed by a refetch becomes review-required, not automatically rebased.
3. Opening an action confirmation clones/freeze-captures origin scope/department, operation and distinct selected order/piece/version records plus a safe display summary. Show order reference, each selected piece reference, total count, source and fixed next destination. A subset is selected with existing piece checkboxes; a numeric completion input cannot choose first N pieces. In persisted completion mode, the count is read-only derived from selected IDs.
4. `captureManufacturingSelection` validates nonempty/distinct IDs, one version per order and the canonical cap, groups by order, orders groups and IDs canonically, and returns `ManufacturingCommandBody['orders']`. It does not silently deduplicate, filter ineligible rows, generate IDs or infer a next department from order type. Root versions protect stale visits; visit IDs are not submitted as authority.
5. On explicit confirm, recheck current scope and the captured context, create one `crypto.randomUUID()` command ID and parse the canonical body. The whole selection goes in one request. Pending/unknown/confirmed-needs-refresh blocks conflicting triggers from rows, groups, toolbar and task detail through the single slot, not only one disabled button.
6. Recoverable precommit rejection preserves safe selected IDs/text, marks current confirmation review-required and refreshes. An explicit review fetches current exact IDs/versions, shows pieces no longer eligible and requires the worker to change/confirm the selection. It never substitutes other pieces, clears authored text or retries under a new command ID without review.
7. Task URLs retain `/cutting/tasks/[orderId]` and `/production/tasks/[orderId]`. `pieceId` is canonical new query selection; legacy `itemId` resolves only the same exact UUID. Legacy `segmentId` can resolve only a real published visit ID in the requested order's contexts; when both a piece and visit are specified they must agree. Unknown/foreign/mismatched IDs produce the safe missing/conflict state. No explicit selection shows the order's safe work overview and offers the existing exact-piece chooser; it does not silently select the first piece/group. A derived multi-piece group uses selected piece IDs, not a new mutable segment identity.

## F06. Command state, synchronization and result recovery

Local intent is a strict discriminated union:

- `{kind:'work', department:ManufacturingDepartment, body:ManufacturingCommandBody}`; body operation is exactly RECEIVE_AND_START, CONTINUE or COMPLETE_TRANSFER.
- `{kind:'report', department:ManufacturingDepartment, orderId:string, pieceId:string, body:ReportIssueBody}`; existing P04 protocol.

Export `ManufacturingCommandResult = Readonly<{kind:"work";data:ManufacturingCommandData}> | Readonly<{kind:"report";data:ApprovalCommandData}>`; it is browser session state, not a third HTTP envelope. `ManufacturingCommandState` is a strict union: `{phase:"idle"}`; `{phase:"pending",originScope,intent}`; `{phase:"unknown",originScope,intent,failure:ApiError}`; `{phase:"confirmed",originScope,intent,result:ManufacturingCommandResult,syncError?:ApiError|null}`; `{phase:"synchronized",originScope,intent,result:ManufacturingCommandResult}`. All fields are readonly, `originScope` is `ManufacturingOperationalScope`, `intent` is `ManufacturingCommandIntent`, and intent department must equal origin scope department. Every nonidle state has one immutable original scope and intent. One root-scoped QueryClient slot covers both kinds and both departments for an ADMIN; do not add a mutable module map, component-only duplicate slot or reused approval capability that denies factory staff. The existing P04 `useApprovalCommand` does not dispatch REPORT_ISSUE and is therefore a reference for lifecycle, not a callable factory hook.

### Submit and settle algorithm

1. Validate scope, exact intent and an idle slot synchronously; publish a deep-cloned/frozen pending entry before awaiting transport. Re-read its identity before every subsequent publication. A stale handler/acknowledgement cannot replace or clear a newer command.
2. Dispatch one request through F03. Known precommit validation/denial/conflict releases only that same pending entry and preserves its form/selection context. Unknown network/timeout/5xx, contract-invalid success or canonical transaction-uncertainty failure retains original intent as unknown. An already-unknown replay remains unknown on another ambiguous/rejected response until authoritative observation or result binding resolves it; no new command is fabricated.
3. Check result binding, then publish confirmed before synchronization. A committed action plus failed refetch is saved-with-refresh-error, never failed-and-resend. `ManufacturingSynchronizationError` carries known result and safe sync error. An old scope result cannot publish UI/cache state or success notices; the server commit itself is not rolled back by browser cancellation.
4. Synchronization cancels relevant current-scope reads before invalidating. Mark affected order/task/history keys stale for both departments currently permitted to that actor, plus current dashboard/orders/pieces/activity. Refetch active mounted P05 queries with `throwOnError:true`; check every published affected order detail has version at least its command afterVersion. Do not fetch an unauthorized next-department scope just to update a counter. Quality UI is not wired by P05; authoritative handoff persists for P06.
5. Apply the exact same-actor upstream invalidation ledger below only where its current capability helper returns a scope matching actor/accessVersion/epoch. Do not fetch factory finance or clear the entire cache. ADMIN broad existing caches become stale without inventing a new admin screen. Reuse affected current safe resources; never set a partial receipt as a full detail DTO.
6. Only after successful synchronization publish synchronized. The initiating mounted/current-scope callback may clear just the captured selection, close its dialog, emit one notice and acknowledge. A later selection/draft must not be cleared. If the form closed during pending, the recovery region remains the owner of observation/synchronization; no duplicate toast or automatic reopen.
7. `acknowledge` resets and exact-removes only the matching synchronized Query entry after checking query identity, command ID, scope and state. Query reset notifies disabled subscribers; no direct query-state mutation or broad removal is permitted.

## F09. Failure and message ownership

[The spec failure matrix](spec.md#frontend-and-state-requirements) fixes intended meaning and recovery. Technical artifacts stay English; actual runtime strings on these screens must be Arabic. `getApiError` remains the one safe transport normalizer; a feature message mapper owns localized action/field/recovery meaning and does not surface its current English fallback directly. Stable server codes select known causes; unknown errors name the failed load/action without guessing. Include sanitized request ID where available, never parser payload/stack/database details.

One visible notice owner handles each outcome: modal validation/general error, read-boundary error/retry or command-recovery state. Hooks synchronize state without duplicate toasts. Specifically distinguish definitive whole-batch rejection with unchanged work from uncertain result, and committed-but-refresh-failed from both. Validation names reason versus notes, explains required versus over-limit and preserves authored input. A private/missing resource error gives safe navigation, not another order's identity or hidden batch membership.
