# P05 Backend Operation Design

This is a proposed design for [spec.md](spec.md), based on source revision `9a7e13f`. Nothing in this document is an implemented interface or executed test unless explicitly identified as existing. [The contract](contracts/manufacturing.md) owns exact HTTP/wire fields; [data-model.md](data-model.md) owns storage, constraints, migration and existing-data policy. PLAN does not generate tasks or authorize application edits.

## 1. Source-grounded decisions

- Existing `ApprovalCommandExecutor` and `SalesCommandExecutor` bind one actor/key/payload to one order/customer result. Reuse their established identity/lock/error/receipt principles, but do not invoke either once per order for a P05 batch: that would violate accepted whole-selection atomicity. A cohesive `ManufacturingCommandExecutor` owns one bounded multi-order transaction. No generic command framework or universal ledger is introduced.
- Existing `lockAccountRows`, `loadIdentityAccount` and `assertBusinessAuthority` remain the authority owner. Existing sales/approval commands lock the submitted `sales_drafts` root and increment `version`. P05 locks the same roots and advances the same versions, preserving paid/approval/cancellation concurrency.
- `lockApprovalOrder` reads an order version before factory piece-department validation. Do not reuse it for P05 multi-order mutations. New locking first establishes a permitted resource relationship and selected-piece membership, then exposes a version/state conflict. An unrelated order never leaks its version or current worker.
- Existing `findFactoryPaper` and GET `/manufacturing-orders/:orderId` retain P04's current-piece/unresolved-source authority. P05's new department detail read owns the explicitly accepted historical relation. Do not broaden the existing P04 factory endpoint as an incidental fix.
- Existing `findOrderActivity` unions sales and approval ledgers; extend its owner/approval-scoped union with safe manufacturing events. Factory history uses a separate allowlisted safe projection, never the financial sales/approval snapshot reader.
- All reached cutting/production receipt/start labels consolidate onto RECEIVE_AND_START. Production has a reached repair START callback but no reachable RECEIPT setter. Do not activate dead receipt-only code or invent a separate backend receipt state/command. CONTINUE explicitly records a colleague's current work without replacing the original starter; completion/report does not require exclusive worker ownership.

## 3. Shared transaction, replay and authority protocol

This protocol applies to M02–M04. M05 keeps P04's separate command protocol. No remote I/O, mail, token work or provider side effect occurs in a manufacturing transaction.

1. Middleware runtime-parses strict department/command/query schemas and applies existing business authentication, department guards and CSRF for writes. A declared workspace department selects scope; the service rechecks current actor authority. Reject empty/duplicate IDs/unsupported fields and more than 200 total selected pieces or 200 order groups. The technical transport cap is not a new commercial order limit; do not silently split.
2. Compute canonical hash from operation, selected department and groups sorted by normalized order UUID, with expectedVersion and sorted exact piece UUIDs. Validate duplicates before sorting; sorting does not deduplicate or change physical selection. Bind actor separately in the retained row.
3. Begin `ReadCommitted` interactive transaction with `maxWait:5000`, `timeout:10000`; set local `lock_timeout=5000ms`, following current P03/P04 controls. Lock actor via `lockAccountRows(tx,[actorId],'read')`, load current account, assert current selected department (ADMIN passes with actual identity).
4. Acquire `pg_advisory_xact_lock` on signed 64-bit SHA-256 prefix of `p05-manufacturing-command:<commandId>`, the same key used by observe. Read retained command. If actor/department/operation/hash match, recheck original source-department receipt authority and return its original validated outcome with `replayed:true` before checking new current piece state or versions. Changed intent is a safe command conflict. A foreign actor never obtains the retained result.
5. For new intent lock every submitted root `sales_drafts` row with FOR UPDATE in ascending UUID order. Load current safe relationship/membership facts and selected pieces in bounded queries. Employees need current matching department piece, unresolved issue source or actual retained department work participation for order existence visibility; ADMIN retains broader read authority. Verify each selected piece belongs to its named order and is visible before any observable expected-version conflict. Unknown/unrelated resources return the contract's safe missing result, not their current versions.
6. Check every expectedVersion equals current root version and is below 2147483647; check approved header, current selected department, no cancellation/warehouse receipt/unresolved issue, matching open current visit and operation-specific state. Historical relation alone never passes a current-action predicate. Validate the entire selection **before** any work write. One failing order/piece rejects all.
7. Capture one server `occurredAt`; generate visit/event/order-event IDs server-side. Run the operation in M02/M03/M04 on the same tx. Use conditional writes with expected piece stage/state/pointer and expected visit state; require exact affected counts. Under the root lock, no cooperating P03/P04 write can change membership/state/version between these checks and updates.
8. Advance each root exactly once with `updateMany({where:{id,status:'SUBMITTED',version:expectedVersion},data:{version:{increment:1},updatedAt:occurredAt}})` and require count=1. No mutation of customer, capture, finance, submitted header status, membership, warehouse `receivedAt` or numbering is permitted.
9. Insert one immutable ManufacturingCommand, its per-order rows and each selected piece's event. Their deferred witnesses may be inserted after visit/pointer writes, but must exist and agree at commit. Runtime-validate the safe stored result against the contract and exact selected order/piece sets. Any failure, including later order/event/constraint failure, rolls back every earlier piece/visit/root/version/result.
10. Commit before HTTP success. Same-key concurrent requests serialize on the advisory lock; different keys competing on a root serialize on root locks and versions. Only recognized P2034 or the exact new command-PK race gets one complete retry with the same identity; then return the bounded transaction conflict. Recognized lock timeout becomes conflict/result-check guidance. Unexpected DB/connection/commit errors remain safe server failures and may be outcome-uncertain to the client; do not claim rollback solely from a disconnected response.

Disjoint pieces in one order still share its existing version protocol. Two commands captured from the same version may conflict; after authoritative refresh/review the losing worker may confirm their unchanged still-valid subset. This is deliberate stale-write protection, not loss of unrelated work or an assignment lock. P05 introduces no per-piece parallel version authority competing with P03/P04.

### Observation and full-reload recovery

`observe` uses **ReadCommitted**, actor lock/current authority and the same advisory command lock before looking up the result. It therefore waits behind a currently executing same-key transaction and reads the committed receipt on its next statement, rather than using an older RepeatableRead snapshot. Missing/foreign key is safe 404; current inactive/reassigned actors remain denied. Current actor plus original command department is sufficient after all pieces advance/cancel; do not require a still-current piece or version.

Same retained command identity always resolves its original outcome, not a newly rebuilt current-state snapshot. The result's actual original versions/states are labelled historical receipt; normal read refresh supplies current state.

In-memory pending intent is useful across dialog closure/navigation but does not survive a full reload. M07 activity with `actor=me` provides bounded, pageable retained P05 command IDs and P04 REPORT_ISSUE IDs for original-result discovery using the correct receipt kind/route. If no original key/payload remains and activity has no confirmed result, show unconfirmed/current-state review; do not invent a failed/pending ledger record or automatically resubmit. Absence from one page is not proof of nonexecution. P04 reports retain their own approval observation protocol. Browser storage must not persist private command payloads or credentials to simulate durability.

## M01 — Department read models

Traceability: FR-001–007,020–026; VR-001,002,005–007; SC-001,006–007.

Run each read in a RepeatableRead transaction with current actor FOR SHARE and department assertion, using the existing read retry pattern for one P2034. Row/count/summary queries use the same snapshot. No expensive query runs before current authority.

1. Build one shared SQL predicate for department, queue, type and search. Submitted/current lifecycle and actual related issue/work history scope it before filtering. Use parameterized Prisma SQL and allowlisted literal fragments; escape `%`, `_` and backslash for text contains. Never search private phone/email/address.
2. INCOMING: current stage matches, state INCOMING, active/unheld/unreceived, current open visit. IN_PROGRESS: same with IN_PROGRESS. RETURNED: current open visit whose origin is APPROVAL_RETURN/QUALITY_CORRECTION, including its incoming/in-progress phase, plus current unresolved P04 issues originating in this department. Held rows have no work actions. A resolved old issue is not independently returned; current correction disappears on transfer/cancellation. COMPLETED: latest visit for this piece **in this department** ended TRANSFERRED and no later same-department visit has begun; cancelled pieces are excluded from active queues, retained history remains.
3. Do not classify a downstream legacy piece as completed merely because of its location. Historical relation is exactly one of: (a) a retained P05 piece event whose command department is requested; (b) a real P04 REPORT_ISSUE for that exact order/piece whose retained `sourceDepartment` is requested, including its resolved history; (c) a source-bound INITIAL_APPROVAL cutting-entry witness, or RESOLVE_ISSUE/RETURN_TO_DEPARTMENT or REVIEW_CONTACT/ACCEPT witness whose exact issue/piece target is the requested department. Initial/positive source release proves an incoming entry/transfer fact only, never receipt/start/completion. An arbitrary approval command on the same order, inferred downstream location or unknown LEGACY_BASELINE grants no historical participation. Current department state grants current-resource reads separately. The same order can appear in several queues through different pieces; returned counts may overlap incoming/in-progress and are not additive totals.
4. Grouped list pages matching order IDs (max25), then loads only their bounded matching IDs/counts and safe header. Flat list pages pieces (max100; UI limit10), selects exact safe piece/work context and matching header. Both use identical underlying predicates. Default sort is `lastWorkAt DESC NULLS LAST, orderId DESC` for groups and `lastWorkAt DESC NULLS LAST, pieceId DESC` for flat; no additional position/order tie-breaker changes the canonical flat order. `lastWorkAt` is latest actual relevant command/report/source instant; unknown stays null. SQL count distinct order/piece identities, not joined event rows.
5. Dashboard reuses queue predicates/counts and five recent grouped summaries from the union of current INCOMING and IN_PROGRESS, preserving its reached waiting/working overview. Each `ManufacturingDashboardOrderSummary` includes `hasInProgress` derived by the same batched current-piece predicate, not an N+1 query or invented urgency. Production repairs count/list means INCOMING with type REPAIR, not a bypass/urgency rule; cutting repairs count is zero. Queue/type/search pagination metadata follows the contract and existing helpers: zero→zero pages; out-of-range→empty items with truthful metadata, never an arbitrary previous/first order.
6. Detail authorizes current relation, unresolved source issue or real retained department participation before fetching the safe paper and latest requested-department visit/context per piece. Return exactly one context per submitted piece with state-derived action hints. Explicit unknown piece/group/task references are rejected by consumers; no server first-piece substitute.
7. Use a new minimal safe selection and mapper for `FactoryOrderPaperData`, omitting finance/private contacts at selection and mapping. Reuse shared factory schemas and `deriveOrderCounts` from `sales-orders.rules.ts` on mapped physical fields. The existing `mapFactoryOrder` consumes broad `SALES_ORDER_SELECT`; do not fetch financial snapshots solely to call that convenience mapper. Existing P04 GET behavior remains unchanged. Read safe issues/instructions in bounded joins with the same approved meaning as P04, without exposing unaccepted proposal values/contact conversations.

Wire pagination/filter/field details remain in the contract. No N+1 piece/visit queries, unlimited historical nested arrays, fabricated `updatedAt` duration, timezone-dependent demo filters or new cache is introduced. Existing operational calendar-dependent values use validated server configuration; P05 instants/durations do not invent an OPS-01 business calendar.

## M02 — Receive and start

Traceability: FR-008–010,014–016,020,022–026; SC-002–003,005.

After the shared protocol validates **every** selected incoming piece, use its current visit. If receipt is absent, set manufacturing `receivedAt/receivedCommandId`; set original `startedAt/startedCommandId` once and physical workState IN_PROGRESS. Actual actor is the retained command actor. No worker input is accepted. A genuinely previously recorded receipt, if encountered in a migrated compatible record, is preserved rather than replaced. Record one RECEIVE_AND_START event per selected piece with before INCOMING and after IN_PROGRESS at the same stage.

The original visit/source/sequence, all unselected work and warehouse `SalesOrderPiece.receivedAt` remain unchanged. A second different-key start from the old version/state rejects; an exact replay returns the original receipt. No new receipt-only endpoint/state is necessary for the inspected reached surfaces.

## M03 — Colleague continuation

Traceability: FR-009–010,014–016,023–025; SC-002,005.

Validate current IN_PROGRESS piece/open visit with the common authority rules; original starter is not a permission restriction. Append CONTINUE event for the actual current actor, with unchanged stage/workState. Preserve original receipt/start and source/visit. `lastAction`/latest actual working actor derives from the new event, not a reassigned owner field. Legacy unknown start remains null; continuation establishes a real subsequent actor without pretending that actor started the earlier work.

The action is explicit, never generated by opening/refetching a task. Exact same-key replay is checked first and adds nothing. For a fresh command, derive the latest actual working actor from RECEIVE_AND_START/CONTINUE events for that active visit. If the actor is already that latest worker, reject the entire selection with `MANUFACTURING_WORK_UNCHANGED` (409) and expose `canContinue:false`; do not append redundant history. Unknown legacy latest actor permits continuation. A→B→A remains valid, while completion/report remains available to any eligible colleague regardless of original/latest actor. Version checks and pending controls reject other repeated stale intent. No supervisor, attendance, pause/resume or exclusive claim is created.

## M04 — Complete and forward exact pieces

Traceability: FR-011–016,019–020,024; SC-003,005.

1. Validate the whole confirmed selection is current IN_PROGRESS with open matching visits and no issue/cancellation/warehouse receipt. An INCOMING piece cannot be completed merely by a quantity dialog. LegacyUnknownStart permits honest missing earlier start evidence, not a different current state.
2. Close every acted visit with endReason TRANSFERRED, end instant/command and normal destination. Insert the one completion event for that visit. Set physical cutting pieces to PRODUCTION/INCOMING; production pieces to QUALITY/INCOMING. No type-specific branch.
3. For cutting transfers open one production visit per exact same physical piece, sourceDepartment CUTTING/sourceTransferEventId=that piece's completion event, enteredAt=actual transfer instant, no receipt/start/worker. Assign its pointer. Production→quality clears the manufacturing pointer and creates no quality inspection/acceptance/packing record.
4. Store outcome `visitId` for the visit acted upon; `nextVisitId` is the new production visit after cutting, otherwise null. Root increments and command/event rows complete under the common atomic protocol. Any one failed write returns no accepted subset.

No order-status shortcut, total/paid update, cancelled-count adjustment, segment quantity authority, warehouse receipt/completion percentage or delivery readiness is changed. Current P03 tracking reads already use physical piece state; M07 adds retained work events to history.

## M05 — Reuse P04 issue report and result observation

Traceability: FR-017–019,021–025; SC-004–007.

Use the existing POST `/manufacturing-orders/:orderId/pieces/:pieceId/issues`, `ReportIssueBody`, `ApprovalService.reportIssue` and approval command result/GET observation. Do not add a batch report command or wrap reports in ManufacturingCommand. Reason is required/nonwhitespace ≤4000; notes omitted/null/empty/whitespace become null, otherwise ≤4000. Preserve captured text; reject unsupported authority fields and over-limit text.

Existing P04 source/actor/state/version and one-unresolved-issue checks remain authoritative. Add only the M06 visit interruption call in that same transaction. On success the exact piece is BLOCKED/current issue set, prior open work visit ends ISSUE_REPORTED, companions stay unchanged, and P04 receipt identifies the original report. Repeated report, report-versus-completion and actor-reassignment races share actor/root locks and existing issue uniqueness; they cannot leave an active transferred-and-held piece. P05 factory action hints read P04 eligibility, never grant A/B/C/contact/approval/cancellation authority.

## M06 — Source-owned entry, hold, return and cancellation lifecycle

Traceability: FR-002,005–010,013,018–021; VR-004,008.

Proposed helper interfaces in `manufacturing-work.lifecycle.ts`, using server-only types from `manufacturing.types.ts`:

```text
openManufacturingVisit(tx: Prisma.TransactionClient, input: {
  orderId: string; pieceId: string; target: 'CUTTING'|'PRODUCTION';
  origin: InitialApprovalOrigin | ApprovalReturnOrigin | DepartmentTransferOrigin;
  occurredAt: Date
}): Promise<{visitId: string}>

interruptManufacturingVisit(tx, input: {
  orderId: string; pieceId: string; approvalCommandId: string; occurredAt: Date
}): Promise<void>

cancelManufacturingVisit(tx, input: {
  orderId: string; pieceId: string; approvalCommandId: string; occurredAt: Date
}): Promise<void>

openQualityCorrectionVisit(tx, input: {
  actor: AuthorityAccount; orderId: string; pieceId: string;
  expectedVersion: number; target: 'CUTTING'|'PRODUCTION';
  correctionId: string; correctionCycle: number;
  instructions: string; occurredAt: Date
}): Promise<{visitId: string}>
```

Origins are discriminated server values: InitialApprovalOrigin `{kind:'INITIAL_APPROVAL',approvalCommandId}`; ApprovalReturnOrigin `{kind:'APPROVAL_RETURN',approvalCommandId,issueId,instructions:string|null}`; DepartmentTransferOrigin `{kind:'DEPARTMENT_TRANSFER',transferEventId}`. They are never browser fields. `tx` always means the caller's locked transaction; helpers neither authenticate HTTP nor commit/increment root versions.

- `openManufacturingVisit` requires physical target INCOMING/no issue/cancellation/warehouse receipt and null current pointer; allocates sequence=max+1 under the already-held root lock, creates source-bound unstarted visit and sets pointer. Initial release invokes it for every retained piece after the existing all-piece release; no separate command/version.
- `interruptManufacturingVisit` after actual P04 report closes/clears the exact CUTTING/PRODUCTION visit with its report witness. QUALITY reporting has no current manufacturing visit and remains a no-op for this helper. Never mark work complete or create a new correction visit merely because it is reported.
- P04 `resolveIssue` RETURN_TO_DEPARTMENT and `reviewContact` ACCEPT first execute their existing issue/specification/physical-state logic, then open one fresh target visit with actual decision witness/issue/instructions. SEND_TO_SALES, SUBMIT_CONTACT and RETURN_TO_SALES keep the hold and create no work visit.
- P04 `cancelIssuePiece` invokes cancellation helper on its same tx. A current open visit, if present, closes CANCELLED; ordinary previously reported/held work already has no open visit, so preserve its ISSUE_REPORTED terminal facts and use P04 cancellation history rather than rewriting them. No new cancellation authority or financial behavior.
- `openQualityCorrectionVisit` is a **future P06 in-process seam**, not an endpoint or implemented quality domain. Caller holds actor/root locks and retains/verifies its real quality rejection decision record. Helper reasserts current quality/ADMIN, verifies locked root version=`expectedVersion` below overflow and active QUALITY/in-progress/no issue/cancellation/warehouse receipt/current manufacturing pointer. It changes physical target to INCOMING and opens source QUALITY visit with `sourceReferenceId=correctionId`, actual instructions/instant, `sourceCorrectionCycle=correctionCycle` and `sourceOrderVersion=expectedVersion+1`. The same correctionId identifies one order's retained rejection decision/command and is shared by all pieces returned by that order decision; the actual positive correctionCycle remains per-piece and separate from visit sequence/P04 cycles. Caller performs root CAS once after its returned pieces, retaining the source record in the same transaction. The narrow source head/transition check in data-model admits that exact QUALITY→target return and counts the shared reference/version once; it is not a browser-selected provenance bypass. P05 tests use an explicitly labelled isolated upstream source fixture, including a multiple-piece return under one root step; actual P06 origin-record binding/live quality acceptance waits for P06. No fictional quality table/FK or fake P04 witness is added now.

Deferred source-command FKs allow P04's executor to insert its witness after the callback's visit writes. Existing P04 facts/contracts do not gain a private visit graph or change approved values. If any helper fails, the owning P04 command rolls back its entire existing decision/report/cancellation and new lifecycle effects.

## M07 — Activity, safe history and compatibility

Traceability: FR-006–007,013,018–026; SC-001,004,006–007.

Persist one ManufacturingCommandOrder.eventId per affected order. Shared `ManufacturingActivityEvent` contains that ID, original commandId/department/operation, safe actor/time, order/version/business number and selected piece/visit transition facts. It carries no financial snapshot/private contacts. Extend `salesActivityItemSchema` with `kind:'manufacturing'`; extend `findOrderActivity` identities/count/page SQL under its existing owner/approval predicate. Add a matching event summary projection; no raw record spread or reference to the new factory history scope in owner-authority SQL.

Do not add a financial revision snapshot for manufacturing. Existing sales revision endpoint continues accepting only its actual P03 sales revisions, and approval event endpoint only its actual P04 events. Web consumers must handle the new discriminator and render safe movement summary, with no call to an old revision endpoint for the new kind. This is an additive wire change requiring producer/consumer deployment together; a strict old client cannot parse the new union member.

Department activity/history uses its own `ManufacturingHistoryItem` union for P05 work and safe P04 issue summaries. For P04 include real REPORT_ISSUE, released/held/cancelled disposition and accepted safe instructions/actor/time; omit raw before/after financial/proposal/contact snapshots. Current order relation grants safe overall state/issue context; historical access grants retained requested-department work, with other department movements limited to safe source/target tracking already admitted by accepted factory context. No historical reader gains a mutation permission.

`activity?actor=me` filters at SQL to actual authenticated actor before pagination. A per-order event's original command ID and kind enable result observation after reload; do not use eventId as a command key. P04 safe event IDs retain their existing commandId, observation kind `approval`. Page order is actual `occurredAt DESC,eventId DESC,kind ASC`; piece-filtered order history reuses exact authorized membership, never arbitrary first-piece selection. Only events are paged in the canonical activity/history result. Earlier visits remain traceable through their retained work/issue witnesses; detail returns one latest requested-department visit/context per piece, with no separate visits endpoint, unlimited visit list or nested history.

## 4. HTTP integration and failure rules

Follow the exact contract route table, request schemas, safe response schemas and codes. All new handlers require existing server actor and parsed validated context; absence is an InternalServerError wiring defect, not actor `''`. Set `Cache-Control: private, no-store` on private results and preserve request IDs. Use `ResponseHelper.ok(response,data,message,request.path,request.requestId)` for all accepted/replayed 200 results. GET uses no CSRF write, command POST includes existing CSRF. Existing API request/body/rate limits remain; no auth/CORS relaxation or new protocol.

Safe errors distinguish validation, missing resource/result, current account/department denial, stale root/piece/no-op work, changed command identity and transient transaction conflict. Include only safe known failure information; never private IDs/current versions for unrelated resources, raw Prisma/SQL, request bodies or retained financial facts. Frontend Arabic meanings come from spec failure matrix; stable codes are not translated.
