# P03 Data Model and Persistence Decisions

**Phase**: P03 — Client-confirmed catalogs, automatic pricing, submission, and sales tracking  
**Feature**: `specs/003-catalog-pricing-submission`  
**State**: Proposed implementation design, inspected against revision `665f794`; no schema, migration, catalog, application or database change has been executed.  
**Requirements**: FR-001–025; verification VR-001–004/007. The [specification](spec.md) owns product truth; [contracts](contracts/sales-orders.md) own wire fields. The operation algorithms and gate evidence live in [plan.md](plan.md).

## 1. Existing Owners and Preserved Facts

Existing persistence uses `SalesDraft`, `SalesDraftPiece`, `Customer`, `SalesCommand` and current account authority. Preserve their UUIDs, SQL table names, owner/customer links, captured fields, removed-piece evidence and immutable command snapshots. The initial migrations through `20261105000100_shared_customers_sales_drafts` remain byte-for-byte historical SQL.

The API currently composes `SalesDraftsService(database, commands)` with `SalesCommandExecutor(database)`. The executor takes the authenticated account lock, rechecks current authority, serializes the command ID, executes work and appends its immutable receipt in one transaction. `SalesDraftsService.save` already locks the owner-scoped aggregate and checks state/version before replacing captures. Extend those owners instead of copying their transaction or identity mechanisms.

Proposed P03 extensions form the same aggregate:

```text
SalesDraft (existing stable aggregate ID, owner, captures, sole version)
  ├─ SalesDraftPiece (existing stable physical-piece IDs and current captures)
  │    ├─ SalesPieceCatalogSelection (current field-to-source selections)
  │    └─ SalesOrderPiece (submitted frozen commercial terms and physical state)
  ├─ SalesOrder (submitted contact/number/lifecycle/financial extension)
  └─ SalesCommand (existing immutable confirmed intent/result history)

CatalogSource -> CatalogEntry <- SalesPieceCatalogSelection / SalesOrderPiece
CatalogActivation -> one active CatalogSource
BusinessOrderCounter -> one global transactional sequence
```

`SalesDraft.version` is the only order/draft aggregate version. There is no competing version on `SalesOrder`, `SalesOrderPiece` or selections. Internal order identity remains the root UUID. The business number and immutable first-submission year/sequence are separate values.

### Approved precision correction — 2026-11-06

The owner approved resolving G2-D1 with unconstrained PostgreSQL NUMERIC for the new P03 monetary columns: CatalogEntry.unitPrice, SalesOrder.totalAmount/paidAmount and SalesOrderPiece.unitPrice. Prisma represents them with `Decimal @db.Decimal` (no precision/scale arguments). Forward SQL uses `NUMERIC`, not `NUMERIC(p,2)`, so input is not rounded before a CHECK inspects it. Named rate/money constraints require finite nonnegative values within the existing unit/paid or total bounds and `scale(column) <= 2`; range comparisons also reject NaN/infinities. Raw SQL `1.001` and `1.000` must both fail with 23514 and leave the valid graph unchanged. Valid `1`, `1.5`, `1.00` and the exact upper bounds retain exact value; public output remains canonical two decimals. Service arithmetic remains bigint cents and constructs Prisma.Decimal only after strict input validation. This changes no price rule or wire contract.

The existing P02 SalesDraft.paidAmount stays Decimal(11,2), retaining existing data/migrations and permissive blank draft semantics. New submitted paid is copied from its validated exact capture into the independently constrained P03 column. No schema push/reset or historical migration rewrite is needed. T004 creates catalog native storage, T005 completes submitted native storage/checks, and T006 proves rejection at the actual migrated database boundary and preservation of populated P02 rows. The scoped Prisma migrate-diff probe emitted plain DECIMAL for `@db.Decimal`; disposable PostgreSQL 18.4 accepted 1.00/the unit upper bound and rejected excess scale, negative, overflow, NaN and Infinity with the proposed checks.

## 3. Proposed Models and Exact Fields

All models/fields below are proposed, not existing source exports. Implement in `packages/database/prisma/schema.prisma` and forward SQL; export intentional generated enums/types through the existing database package index only after generation.

### 3.1 CatalogSource, CatalogEntry and CatalogActivation

`CatalogSource` maps to `catalog_sources`:

| Field               | Type / invariant                                                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                | UUID primary key                                                                                                                                                          |
| `sha256`            | Char(64), lower-case hexadecimal, unique `catalog_sources_sha256_key`                                                                                                     |
| `worksheet`         | VarChar(100), exact reviewed worksheet label                                                                                                                              |
| `sourceExtent`      | VarChar(32), reviewed `A1:AA942` for the received source                                                                                                                  |
| `mappingVersion`    | Int, initially 1; identifies this fixed field/range interpretation, not a generic form engine                                                                             |
| `loadedAt`          | Timestamptz(6), actual confirmed load time                                                                                                                                |
| `loadedByReference` | VarChar(128), nonsecret scoped operator/reference; not an invented application user                                                                                       |
| `entryCount`        | Int, actual reconciled imported entry count; 1,874 entries for the currently accepted ten-kind mapping, calculated from its recorded counts                               |
| `manifest`          | JsonB containing only reviewed range/family counts and expected rate-pair/source-asymmetry checks; no workbook bytes, filesystem credential or arbitrary provider payload |

`CatalogEntry` maps to `catalog_entries`:

| Field                        | Type / invariant                                                                                                                              |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                         | UUID primary key; stable for a repeated load of the same source cell/kind                                                                     |
| `sourceId`                   | UUID, `CatalogSource` FK `ON DELETE RESTRICT`                                                                                                 |
| `kind`                       | `CatalogField` enum: `model`, `size`, `leatherBase`, `decoration`, `decorationColor`, `sole`, `soleAddition`, `soleColor`, `aField`, `fField` |
| `sourceCell`                 | VarChar(16), original cell coordinate; one row per supplied option cell, not one row per deduplicated display label                           |
| `displayValue`               | VarChar(200), evaluated source display text, preserved exactly                                                                                |
| `lookupValue`                | VarChar(200), normalized comparison/search value; never replaces `displayValue`                                                               |
| `familyCell` / `familyLabel` | VarChar(16) / VarChar(200), both nullable; required together only for `decorationColor`, retaining the exact L2:Y2 family source              |
| `position`                   | Int positive, source order within kind/family; do not alphabetically rewrite source identity                                                  |
| `unitPrice`                  | Unconstrained NUMERIC with unit range/scale CHECKs, only for `decoration`; null for other kinds                                               |
| `priceSourceCell`            | VarChar(16), same-row AA source for decoration; otherwise null                                                                                |

The loader excludes blank/nonoption/header/statistic cells according to the reviewed ranges and records formulas as evaluated values only. Distinct source rows/families remain distinct even when labels/short codes overlap. A repeated identical source load reuses the retained entries; it must not generate new IDs or rewrite original strings. Conflicting duplicate decoration lookup keys/rates cause rejection before activation.

`CatalogActivation` maps to `catalog_activation`: fixed primary key `id='active'` VarChar(6), `sourceId` nullable UUID FK RESTRICT, and `activatedAt` nullable Timestamptz(6). The schema migration creates the singleton with null source; that represents unavailable catalog, not a fabricated active source. `sourceId` and `activatedAt` are null together. After parsing/validating outside the transaction, apply locks this singleton `FOR UPDATE` before source lookup/inserts, reconciles an identical retained source or inserts the complete source/entry set, and atomically activates it. Concurrent identical applies therefore serialize before the hash-unique insert. Quote/submission reads take `FOR SHARE`; activation therefore cannot change reviewed terms midway through submission. No row deletion or source edit is part of the loader.

### 3.2 SalesPieceCatalogSelection: Current Typed Selections

`SalesPieceCatalogSelection` maps to `sales_piece_catalog_selections` with composite primary key `(pieceId, field)`, `pieceId` UUID FK to existing `sales_draft_pieces(id)` RESTRICT, `field CatalogField`, and `entryId` UUID FK to `catalog_entries(id)` RESTRICT. Wire `catalogSelections` is the corresponding strict optional field-to-entry-UUID-or-null map; null represents no selection row. It is not stored as unvalidated JSON.

Ten supported fields are the ten `CatalogField` values above. Text fields have no selection rows. Incomplete drafts may have zero/subset rows and arbitrary provisional capture text. On a selected field, the entry must have the same kind and its exact display value must equal that field's captured value. On cleared/free provisional input, the corresponding selection row is removed; the original capture remains governed by P02 rules. A replacement request with omitted/empty selection map clears current references rather than guessing entry identity from text; old clients may still save all captured values; quote/first submission may recover unique exact active kind/value matches, while ambiguous/unknown values require explicit selection. P03 quote/first submission requires a valid resolved reference for every supplied catalog selection. A missing reference may resolve only from exactly one active-source entry with the same kind and exact original display string; zero/multiple matches require explicit selection. Supplied references must match active kind/source/display. Resolve all fields in one bounded lookup and atomically persist the resolved map with first submission; do not choose the first match or normalize/translate display text to manufacture a match.

The submit/resubmit service validates the selection map in one bounded entry lookup. Draft save may preserve historical references without requiring the source to remain active; this retains incomplete draft compatibility. First submission requires the current active source. Returned corrections can keep unchanged historical selections; any changed selection must belong to the current active source. The decoration reference is immutable after first submission. Removed draft pieces have no new/changed selection writes; existing retained references remain available for history.

P02 input compatibility: the new map is optional; absence retains the historical wire shape and its payload hash behavior. Historical command result snapshots without the map continue parsing as historical P02 results. New map entries are hashed in fixed field order only when supplied. Do not rehash/rewrite persisted commands or change the hash of an old request that omits selections. PLAN's contract owner defines strict command projection and the producer/consumer rollout together.

### 3.3 SalesDraft and SalesDraftPiece Extensions

Extend `SalesDraftStatus` with `SUBMITTED` through a forward enum migration; keep `DRAFT` unchanged. `SUBMITTED` is only the P02 write/read fence; actual submitted lifecycle belongs to `SalesOrder.status`. Existing `SalesDraft` fields, UUID, owner, customer and `version` remain the authority for common captured data. Existing `paidAmount` is the provisional/initial paid capture, retained after submission; later cumulative payment updates change `SalesOrder.paidAmount`, not the captured original.

| `SalesOrder`                 | `draft: SalesDraft` through same-ID FK, `submittedBy: User`, `catalogSource: CatalogSource`, `pieces: SalesOrderPiece[]`. |
| `SalesOrderPiece`            | `piece: SalesDraftPiece`, `order: SalesOrder`, `decorationEntry: CatalogEntry`, `priceSource: CatalogSource`.             |
| `SalesPieceCatalogSelection` | `piece: SalesDraftPiece`, `entry: CatalogEntry`.                                                                          |

These are planned schema properties, not current generated exports. They fix `SALES_ORDER_SELECT`'s joined `order`, `pieces.orderPiece` and `pieces.catalogSelections.entry` paths without renaming existing relations.

Add only relations from existing roots/pieces to their extension/selection records. Do not rename/drop/recreate tables or regenerate IDs. `SalesDraftPiece` continues holding current permitted specification captures, position and quantity. Post-submission permitted corrections use the owning P03 command and advance the root version. No new base piece is created or removed after submission.

`SalesOrder` maps to `sales_orders`:

| Field                                       | Type / invariant                                                                                                                                                                   |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                        | UUID primary key and FK to `SalesDraft.id`, RESTRICT; no independent order ID                                                                                                      |
| `status`                                    | `SalesOrderStatus` enum; initial `AWAITING_APPROVAL`                                                                                                                               |
| `businessNumber`                            | VarChar(64), immutable unique `sales_orders_business_number_key`                                                                                                                   |
| `numberSequence`                            | BigInt, immutable globally unique `sales_orders_number_sequence_key`                                                                                                               |
| `numberYear`                                | Int 1–9999, immutable first-submission business-calendar year                                                                                                                      |
| `submittedAt`                               | Timestamptz(6), immutable first-submission instant                                                                                                                                 |
| `submittedById`                             | UUID FK to User RESTRICT; actual authenticated creator/owner                                                                                                                       |
| `ownerFullNameAtSubmission`                 | VarChar(150), actual retained salesperson name                                                                                                                                     |
| `customerName` / `customerPhone`            | VarChar(150) / VarChar(13), immutable nonblank snapshot                                                                                                                            |
| `customerEmail` / `customerAddress`         | Nullable VarChar(320) / VarChar(2000), immutable contact/address snapshot                                                                                                          |
| `catalogSourceId`                           | UUID FK to first-submission reviewed `CatalogSource`, RESTRICT                                                                                                                     |
| `totalAmount`                               | Unconstrained NUMERIC with total range/scale CHECKs, authoritative sum of noncancelled submitted piece prices                                                                      |
| `paidAmount`                                | Unconstrained NUMERIC with unit range/scale CHECKs, initial capture promoted with absent/null/blank as zero; later only the paid command or later explicitly authorized correction |
| `approvedAt`                                | Nullable Timestamptz(6); populated only by P04's actual approval writer, not P03 or UI                                                                                             |
| `currentReturnDecisionId`                   | Nullable UUID, canonical P04 return-decision identity; never accepted as standalone proof from the browser                                                                         |
| `currentReturnOrderVersion`                 | Nullable Int, root version produced by the current return decision                                                                                                                 |
| `currentReturnReason` / `currentReturnedAt` | Nullable VarChar(4000) / Timestamptz(6), free-text reason and actual P04 action time                                                                                               |

The order mapper exposes `numberYear` as wire `businessYear`, `numberSequence` as exact wire `sequence`, and current-return fields as `approval.returnDecisionId/returnReason/returnedAt/returnRevision`; absent current proof maps to null fields and returnRevision 0, while a returned proof maps its positive root version. It never manufactures an approval timestamp.

No `version`, copied `ownerId`, copied mutable `customerId`, piece count or progress counter is introduced here. The root owns shared links/version. All original contact and number/source fields above freeze on first submission. This protects the original snapshot; P08's separately authorized BR-19 notes/contact/address correction may later add a narrow audited current-value overlay through its own forward design/migration. P03 creates no such overlay and must not globally prohibit that later authorized operation or mutate the original snapshot. `approvedAt` remains meaningful after downstream transitions; a current `RETURNED` revision still denies paid updates. P03 resubmission clears the current-return fields as it moves to `AWAITING_APPROVAL`; the old proof/returned revision remains in the immutable command's `before` projection and P04's canonical retained decision owner. P04 must provide that immutable decision owner before its live workflows can be accepted.

`SalesOrderStatus` is the stable cross-phase wire/persistence vocabulary: `AWAITING_APPROVAL`, `RETURNED`, `APPROVED`, `READY_FOR_DELIVERY`, `OUT_FOR_DELIVERY`, `DELIVERY_FAILED`, `DELIVERED`, `CANCELLED`. P03 only creates awaiting approval, consumes authoritative returned state and resubmits to awaiting approval; it does not approve, cancel, mark ready or run delivery. P04 owns approval/return/cancellation, P05–P06 own piece manufacturing/quality changes, and P07 owns physical receipt/readiness/delivery. `APPROVED` remains the order root during partial manufacturing/receipt, with progress derived from pieces.

### 3.5 SalesOrderPiece: Frozen Terms and Physical State

`SalesOrderPiece` maps to `sales_order_pieces`:

| Field                                 | Type / invariant                                                                                                           |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `id`                                  | UUID primary key and FK to existing `SalesDraftPiece.id` RESTRICT                                                          |
| `orderId`                             | UUID FK to SalesOrder RESTRICT; must equal that base piece's `draftId`                                                     |
| `decorationEntryId` / `priceSourceId` | UUID FKs to frozen decoration entry and its source, RESTRICT                                                               |
| `decorationLabel`                     | VarChar(200), original evaluated selected display string, immutable                                                        |
| `unitPrice`                           | Unconstrained NUMERIC with unit range/scale CHECKs, immutable exact same-row rate                                          |
| `priceSourceCell`                     | VarChar(16), immutable AA provenance                                                                                       |
| `stage`                               | `SalesPieceStage`: `AWAITING_APPROVAL`, `CUTTING`, `PRODUCTION`, `QUALITY`, `WAREHOUSE`, `CANCELLED`                       |
| `workState`                           | `SalesPieceWorkState`: `INCOMING`, `IN_PROGRESS`, `COMPLETED`, `BLOCKED`                                                   |
| `issueId`                             | Nullable UUID reference reserved for the owning P04 issue record; no P03 issue creation or browser-controlled issue status |
| `receivedAt`                          | Nullable Timestamptz(6); actual physical warehouse receipt only                                                            |
| `cancelledAt` / `cancellationReason`  | Nullable Timestamptz(6) / VarChar(4000); retained together when cancelled                                                  |

The feature mapper deliberately exposes persistence `priceSourceId` as wire `catalogSourceId` on each piece; they are the same frozen source identity, not two columns or independently chosen sources.

P03 initial state is `stage=AWAITING_APPROVAL`, `workState=INCOMING`, no issue, receipt or cancellation. Selecting colors/floors does not change frozen price. P03 resubmission must preserve every submitted piece's stage, workState, issueId, receivedAt and cancellation evidence; it cannot reset physical state or start/resume manufacturing. Initial-return test fixtures have no manufactured work started. The same physical piece is later updated by P04–P07; there is no separate quantity/segment state authority. Later phase design must attach narrow FKs for its issue/decision records once those tables exist, preserving this data and IDs.

For each order, derive `originalCount=count(all submitted extension pieces)`, `cancelledCount=count(stage=CANCELLED)`, `activeCount=originalCount-cancelledCount`, and `receivedCount=count(nonCancelled and receivedAt not null)` from the same rows. Derive completion as received/active under the existing presentation convention; when active is zero expose a cancelled/not-deliverable outcome, never 100%-ready. Quality `COMPLETED` with a warehouse handoff does not set `receivedAt`. List aggregates group only the bounded selected order IDs; detail reads at most 200 pieces. No stored independent counter, segment ledger or copied progress percentage exists.

### 3.6 BusinessOrderCounter

`BusinessOrderCounter` maps to `business_order_counter`: `id='global'` VarChar(6) primary key and `lastIssued BigInt` default zero, range 0 through the signed BigInt maximum. The forward migration inserts the one empty singleton and no business number/order.

First submission locks the singleton `FOR UPDATE`, rejects exhaustion, computes `next=lastIssued+1`, records the first-submission year and immutable `TYPE-YYYY-padded(next)` (year padded to exactly four digits), and updates the counter inside the same transaction as the submitted root, pieces and command receipt. A transaction rollback restores the prior counter. Do not use a PostgreSQL sequence, auto-increment, array length, per-type partition or yearly reset. Confirmed issued numbers are never reused or reassigned.

### 3.7 SalesCommand Extension and History

Add `SUBMIT_NEW_ORDER`, `SUBMIT_DRAFT`, `RESUBMIT_ORDER`, `SET_ORDER_PAID` to the existing command operation enum in an earlier committed enum migration; use those values in a following schema/data migration. New order command receipts reuse `draftId` as the aggregate FK; do not add a competing `orderId` identity. The result kind is `order` and the validated `after` projection is `SalesOrderDto`. Existing customer/draft kinds/rows/snapshots remain unchanged.

- `SUBMIT_NEW_ORDER`: request target/expected/before version null; generated resource root version and receipt after version 1. One command creates the complete new order atomically; it must not first commit a draft creation command.
- `SUBMIT_DRAFT`: target existing draft ID; expected/before equal its current version; after version is before+1. Its `before` is the previous safe draft projection and `after` the safe submitted-order projection.
- `RESUBMIT_ORDER` and `SET_ORDER_PAID`: target root ID; expected/before current root revision; after before+1. Before/after are safe order projections. Resubmit records relevant correction and current return proof in its retained before snapshot.
- Paid unchanged: return the documented `ORDER_PAID_UNCHANGED` conflict without any write, version increment or retained receipt. This preserves the existing one-real-revision/receipt rule rather than introducing fake no-op history.

`hashSalesCommandIntent` must retain byte-identical explicit hashing for the four existing operations. New branches canonicalize the new operation's allowed payload in stable order; include origin, expected version, captured selections, reviewed quote binding or explicit cumulative amount as applicable. RESUBMIT_ORDER hashes only its accepted request `{ expectedVersion, corrections }` plus the standard operation/target binding; never hash newly fetched server-derived return proof. Otherwise a replay after the first command clears current proof could not recompute the original intent. Expected root version binds current-decision freshness; immutable before-image retains the proof. Never hash credentials or raw unbounded request objects. Existing advisory command-ID locking and immutable replay behavior remain. Replay rechecks current actor authority and resource visibility, then returns the historical accepted snapshot; UI must separately refetch the current root when needed.

Use retained SalesCommand rows for P03 submission/correction/paid activity; derive narrow safe summaries instead of returning raw before/after financial snapshots to factory users. P04's later decision history remains its owner; no generic event ledger or snapshot registry is added here.

## 5. Transaction and Lock Contract

P03 new writes reuse `SalesCommandExecutor`; no nested/root-client transaction escapes. Global order is account rows (ascending, FOR SHARE), command-ID advisory lock, existing root row FOR UPDATE when present, relevant customers in ascending order FOR SHARE, catalog activation FOR SHARE when current choices matter, counter FOR UPDATE only for first submission. P03 works with immutable catalog entries after locking activation; loader takes activation FOR UPDATE and never locks business roots. No external workbook parsing, filesystem access, network or expensive processing occurs inside a business transaction.

Existing duplicate/changed-payload replay takes the retained result path before mutable draft/order state checks, after current authority/visibility. Different command IDs racing for the same first submission still serialize on the root and state/version predicate; the loser cannot allocate another number or order. New-submit identity is generated inside the command's work after the command lock, and one committed receipt resolves a lost response.

Proposed shared writer `writeDraftCapture(tx, { draftId, capture, occurredAt, mode: 'create' | 'replace' })` lives in `apps/api/src/modules/sales-drafts/sales-draft-capture.writer.ts`, extracted from the current private header/piece helpers. It calls the existing pure `classifyDraftPieces`, writes explicit captured headers/pieces/current selections only, and never sets owner/version/status/number/snapshots. Sorted customer locks belong to callers. Both existing draft commands and proposed order commands reuse it. Plan OP-04 also fixes the same-file `toDraftCaptureHeaderValues` mapping export, extracted from the current private header mapping and reused by new-root callers; it cannot supply owner/state/version/time. Follow Plan OP-04's fixed branches: create inserts only initial pieces/refs after the caller has written the complete new header; replacement of a SUBMITTED root changes only permitted captures/refs/updatedAt and never writes base position, removedAt or quantity. Only actual DRAFT structural changes use temporary +200 resequencing. The writer reads root status and current piece positions within the caller's transaction to enforce structure, not authority/transitions. Resubmission checks exact retained piece IDs/order and the correction allowlist first; type/customer/initial paid captures remain identical to the locked saved root. This preserves one write algorithm without giving the writer authority to choose transitions.

The exact protected-write algorithm lives in the plan's operation blueprint. P03 must preserve executor's `ReadCommitted`, 5-second lock/max-wait, 10-second transaction timeout and one recognized transaction retry until evidence warrants a scoped change. Read models use the existing account-locked `RepeatableRead` transaction pattern for consistent rows/counts and one recognized transient retry. Unique business-number/sequence and resource/version checks are independent of a browser command ID.

### Narrow P04 return proof seam

Proposed internal type `P04ReturnProof = Readonly<{ orderId: string; decisionId: string; orderVersion: number; reason: string; returnedAt: Date }>` lives in `apps/api/src/modules/sales-orders/sales-orders.types.ts`; `readCurrentOrderReturnProof(tx: Prisma.TransactionClient, orderId: string): Promise<P04ReturnProof | null>` lives in `apps/api/src/modules/sales-orders/sales-orders.queries.ts`. P03 resubmit binds the accepted expected root version and checks this proof inside the same root lock; the request contains no independent return decision ID/revision authority. The server derives the proof from the locked current root and preserves it in the before-image.

P03 defines no approval/return HTTP endpoint and no fixture shortcut in production. Until P04 exists, tests use explicitly isolated returned/approved fixtures at this seam and cannot claim the actual P04 workflow.
