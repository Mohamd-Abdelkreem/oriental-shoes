## 3. Shared Query, Publication and Command Policy

### Exact keys

Let `root(scope) = ['customer-drafts', scope.actorId, scope.accessVersion, scope.epoch]`; reuse `customerKeys.root(scope)` rather than introducing another identity format. New keys are:

| Query                           | Key after `...root(scope)`                                                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Active reviewed catalog         | `['catalogs','active']`                                                                                                        |
| Current quote                   | `['orders','quote',catalogQuoteKey(input)]`                                                                                    |
| All own/broader orders          | `['orders','list',query.search ?? '',query.type ?? null,query.status ?? null,query.customerId ?? null,query.page,query.limit]` |
| Dashboard                       | `['orders','dashboard']`                                                                                                       |
| Submitted detail                | `['orders','detail',orderId]`                                                                                                  |
| Combined editor locator         | `['orders','editor',orderId]`                                                                                                  |
| Tracking                        | `['orders','tracking',orderId]`                                                                                                |
| Own activity                    | `['orders','activity',query.page,query.limit]`                                                                                 |
| Order activity                  | `['orders','activity',orderId,query.page,query.limit]`                                                                         |
| Customer submitted orders       | `['customers','orders',customerId,query.type ?? null,query.status ?? null,query.page,query.limit]`                             |
| Customer submitted measurements | `['customers','order-measurements',customerId,query.page,query.limit]`                                                         |

Both activity adapters/hooks accept the final strict `SalesOrderActivityQueryInput` containing page/limit only; no operation-filter input, UI control or query-key segment is introduced.

Expanded revision keys are exactly `[...root(scope),'orders','revision',orderId,eventId]`; retained snapshots never share the current detail key.

Parse/normalize query inputs once through their shared schemas before forming a key. `catalogQuoteKey` uses the current catalog source ID and canonical sorted tuples of stable piece ID, raw decoration capture and optional decoration entry reference; preserve absent versus explicit null reference consistently with the parsed request shape. Do not use a mutable row index, translated label, token or account name. Its deterministic representation is only a cache identity, not the server's authoritative reviewed fingerprint. Any changed input that can change the accepted quote/reference receives a different key. Request correlation UUID is excluded from this key: retain one UUID with the current canonical input in local hook state, replacing the pair only when that input changes; same-input refetch/retry uses the captured UUID. The outgoing wire body is exactly `{requestId,pieces}`, not the presentation-only sourceId wrapper. Validate the response correlation UUID, requested piece IDs/order and each returned decoration/ref before publishing.

The catalog query uses the normal 30-second freshness and no automatic interval. Available catalog data contains sourceId and 1,874 entries with exact displayValue/sourceCell/kind/family; `{availability:'unavailable',reason:'CATALOG_NOT_LOADED'}` is successful readiness, not an empty array. Quote queries use `staleTime: 0`, `gcTime: 0`, `refetchOnWindowFocus: false` and existing safe query retry policy; enable only with an eligible scope and parsed quote input. Unknown/blank decorations can still be sent in an otherwise valid bounded quote body to obtain explicit per-piece unavailable state. If the quote returns a different active sourceId from the input's reviewed catalog, invalidate/refetch the exact catalog key, reject amount publication with the proposed local `CatalogSourceChangedError`, and show refresh/review feedback; do not misclassify that expected source change as malformed/offline or loop automatic retries. Catalog/quote failures never replace current form captures with defaults. Quotes are not durable commands and create no receipts/numbers.

Submitted detail and editor options copy P02's explicit ID validation and monotonic-version structural sharing. A detail read must return the requested identity; an older resource version cannot replace a newer same-resource value. The editor union is exactly `draft | submitted`: submitted status/`allowedActions` determines returned versus locked presentation, without new wire tags. A matching draft receipt may now resolve through the editor to submitted state after promotion; never publish its historical `savedDraft` over the newer submitted resource. No draft-404-then-order fallback is allowed.

Every new read applies existing scope assertions before/after awaiting the API, calls `reconcileBusinessDenial` on failure, forwards cancellation, and checks scope again in `structuralSharing`. Current tracking/version mismatches against a newer detail trigger a current tracking refresh rather than replacing new facts with old counters. Pending/background reads remain distinct from initial loading and true empty success.

For any paged collection that shrinks, retain P02's two-part recovery: mark the exact normalized destination-page key stale with `refetchType:'none'`, then move the view's page to `max(1,totalPages)`. The destination must refetch even if its old cache was fresh. Independently page orders, order activity, customer cards and measurements; one panel must not change another's page. Reset a list page to 1 on an explicit filter/search change, not on an unrelated detail/background update.

### Shared command lifecycle

Use the existing `SalesCommandVariables = { scope, command }` owner. Freeze one parsed command body with one `commandId`, original expected version, full submitted capture/correction/paid value, reviewed quote/customer version as applicable, original scope and original form token. UI phases remain `editing | pending | unknown | confirmed | retryable | checking`.

1. Validate local intent, synchronously latch the action, freeze it and disable conflicting controls/all submit triggers.
2. `useSalesCommand.onMutate` cancels the captured operational root and rechecks scope; dispatch one current operation. Never retry writes automatically.
3. Validate the command result's kind/operation/command ID/actor/resource/version against the frozen intent. A malformed success is an unknown write outcome, not proof of rollback.
4. Read back the latest authoritative resource and require its version to be at least the receipt's `afterVersion`. New order command results synchronize with current submitted detail/editor; customer/draft branches preserve their existing semantics.
5. For a historical CREATE_DRAFT/SAVE_DRAFT receipt whose resource has since been submitted, use the combined editor locator, accept its newer submitted version, remove obsolete current draft-detail cache, and synchronize the submitted detail. The original immutable receipt remains observable and is not rewritten. Do not require an endpoint that correctly no longer serves a draft to return the old state. Extend the existing editor's `finish` branch to inspect that current locator result: a submitted result navigates/renders current submitted state without calling `makeDraftDefaults` or resetting it as an editable draft; a current draft result retains the existing draft-reset path.
6. Await invalidation of the same operational root with throwing refetch failures. It includes draft/order/customer summaries, measurement panels, dashboard, activities, quotes and current details. These bounded existing data families share real invalidation meaning; do not clear the whole QueryClient.
7. Only after confirmed synchronization may the original current form reset/navigate/announce complete success. If persistence is confirmed but refresh fails, retain `SalesSynchronizationError` and retry reads only. If the outcome is unknown, preserve the same immutable command and allow manual receipt observation or identical retry; a missing receipt does not prove the earlier request failed.
8. Deterministic validation/denial/conflict returns to editing with input and useful field/general feedback. Known transaction-retry rejection may retry the same frozen intent. Resource-version/quote/customer-version conflicts require explicit refresh/review, followed by a new accepted intent; never silently overwrite or silently reprice.
9. A disposed form/changed account cannot reset, navigate, toast, reselect a customer or publish old private results. Successful server work remains real even if the view closed; cancellation is not rollback.

Same-amount paid requests receive `ORDER_PAID_UNCHANGED` as defined by the wire owner: show an informational unchanged result and refresh current paid/detail data without claiming a write or waiting for a nonexistent new receipt. A replay of an already committed paid command is handled by its existing receipt before this no-op case.

The proposed `applyOrderCommandError` accepts only known top-level `body.capture.*`/`body.corrections.*` fields and `body.paidAmount`, plus `body.capture.pieces.N.FIELD`/`body.corrections.pieces.N.FIELD` with a known captured field. Also accept `body.capture.pieces.N.catalogSelections.FIELD` for the ten known catalog selector keys, and `body.corrections.pieces.N.catalogSelections.FIELD` for the nine permitted nondecoration correction selector keys. Resolve N through the frozen submitted piece ID and then locate that identity in the current local form before setting/focusing its error. A nested reference error maps to the corresponding visible capture field: for example, `.catalogSelections.sole` maps to the current piece's `sole` selector, not a hidden reference input. Unknown keys/nested paths remain safe general form feedback. Never interpret arbitrary server paths as typed RHF paths or attach a late row error to a replacement piece. Model/component verification must include nested selector errors after row reorder, unknown nested keys, and a removed/replaced piece without misdirected focus.

| Error / observation                                                                   | Explicit visible and reconciliation behavior                                                                                                                   |
| ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ORDER_VERSION_CONFLICT`, `ORDER_STATE_CONFLICT`                                      | Retain local input, disable blind repeat, refresh/review the combined editor/current detail. A promoted/locked result cannot be reset as an editable draft.    |
| `ORDER_CUSTOMER_CHANGED`                                                              | Retain paper/customer identity, refresh full customer detail and show current contacts for explicit review; bind the newly reviewed version to a new intent.   |
| `ORDER_QUOTE_CHANGED`, local `CatalogSourceChangedError`                              | Retain specifications, invalidate current catalog/quote and require current price/source review. No silent repricing or old amount publication.                |
| `ORDER_CORRECTION_CONFLICT`                                                           | Preserve saved terms and local permitted input; explain that fixed identities/terms changed or were prohibited; explicit review, no forced merge.              |
| `ORDER_PAID_UNCHANGED`                                                                | Informational already-current feedback and detail refresh; no fabricated receipt or saved event.                                                               |
| `ORDER_CATALOG_UNAVAILABLE`, `ORDER_CALENDAR_UNAVAILABLE`, `ORDER_NUMBER_UNAVAILABLE` | Submission readiness feedback; incomplete Save draft remains available. Do not invent catalog values, zero prices, calendar defaults or numbers.               |
| `ORDER_NOT_FOUND` or current authority denial                                         | Safe missing/denied presentation; existing business-denial/session reconciliation runs. Never probe an alternate resource or reveal another owner's existence. |
| `SALES_COMMAND_CONFLICT`, unknown transport/contract result                           | Preserve original immutable intent and show observation/identical-retry choices; no new command ID to bypass uncertain result.                                 |
| `SALES_TRANSACTION_CONFLICT`                                                          | Known retryable transaction rejection may retry the same frozen intent; changed expected terms require review.                                                 |
| `SalesSynchronizationError`                                                           | Persistence confirmed; retry current reads/invalidation only. Do not resend a confirmed write merely because a panel failed to refresh.                        |

## F01 — Bind Reviewed Catalogs to the Existing Paper

**Requirements**: FR-002–005, FR-026–029. **Backend prerequisite**: catalog source/read contract and authoritative loader/read acceptance. **Owners**: proposed catalog API/hook/model; existing paper prop/select/menu/cell/side/size components listed in F08.

1. Start `useCatalog()` independently of selected customer/draft detail once the operational scope is available. Respect the contract's explicit source unavailable result and real read errors; do not replace either with demonstration option arrays.
2. Convert each catalog kind into stable entry value/exact display label/source family options. A selected reference and raw display capture are separate form facts. Source text is never translated, trimmed or normalized on selection. Internal search normalization affects matching only.
3. Extend the typed optional `catalogSelections` map through existing draft model defaults/paper adapters/save/reload/duplication. Old P02 rows/receipts without the property remain valid and retain absence. Selecting a reviewed entry sets both its exact raw display capture and reference; typing a provisional custom draft value/clearing a selection clears that field's reference. Never infer a source identity from a loose normalized match.
4. Existing draft values with missing/unknown refs remain editable/saveable; no catalog completeness is imposed on ordinary draft save. They cannot silently become valid submitted selections. Matching exact legacy capture can be explicitly resolved using the source contract's unambiguous lookup rules; ambiguous choices require the salesperson's explicit selection.
5. Preserve free-text M1/M2/M3/face/final additions. Keep source-field membership separate: base is I, colors retain L–Y families, sole addition is B and not final additions, A is workbook F and paper F is workbook G. Do not filter color options by decoration family.
6. Add source values for A/F to the existing measurement positions and selection treatment. Keep the existing paper/table placement, row quantity one and lower box behavior. No new box persistence/business rule is introduced.
7. A catalog refresh never resets a dirty form, silently removes an obsolete submitted selection or alters frozen terms. Show readiness/source changes through existing inline feedback; users explicitly refresh/review when submission requires current source data.

**Verification design**: Proposed `catalogs.api.test.ts` validates malformed/unavailable/success envelopes; proposed `catalog-paper.model.test.ts` checks stable IDs, family separation, exact source text/case/leading zeroes, duplicate labels, original-language round trip, provisional custom capture clearing refs and old rows with absent refs. Extend `paper-cell-select.test.tsx`, `draft-form.model.test.ts`, `side-table-columns.test.tsx`, `order-mixing-text-fields.test.tsx` and `draft-paper-state.test.tsx`. A transport double may prove UI binding but not actual catalog loading; real persisted source evidence belongs to the backend gate.

## F02 — Calculate and Review Current Quotes

**Requirements**: FR-006–008, FR-027–028. **Backend prerequisite**: all 14 same-row rates, unavailable/ambiguous-rate behavior and quote fingerprint acceptance. **Owners**: proposed `catalogsApi.quote`, `useOrderQuote`, `makeCatalogQuoteInput`, authoritative paper finance props.

1. Derive presentation input from the current active catalog source and stable pieces, including only raw decoration plus optional decoration reference per piece. The hook adds its retained correlation UUID and sends the strict `{requestId,pieces}` body. Read-only calculated monetary values never enter draft capture or a command as authoritative price input.
2. On a decoration, decoration-reference, physical-piece membership/identity or reviewed source change, immediately treat the prior quote as not current for submission; the new exact key receives its own request. Nondecoration specification/reference edits neither change this quote key/server fingerprint nor introduce a price modifier; their current catalog membership still validates independently at first submission. Display-only row reordering leaves the canonical quote unchanged.
3. Display current request progress in the existing amount cells/inline form status. Retain entered specifications while pending. A slower old request cannot become the new selection's price because keys, source/identity checks and current-scope publication all match the captured request.
4. Render each per-piece ready amount, and render a ready aggregate only when the contract says all relevant amounts are available. Blank/unknown decoration, bad/missing/conflicting rate or absent source yields a dash/unavailable explanation, never `0`, a free product or a manual price input. Do not borrow a ready amount from another piece.
5. Preserve exact amount strings supplied by the API; client `Number`/legacy `calculateOrderTotals` must not decide an authoritative total/due/surplus. Draft provisional paid remains a capture, not proof of payment. The quote response supplies total but no authoritative paid/due/surplus: render total and provisional paid, keeping the remaining balance explicitly unavailable until the submitted monetary projection exists rather than inventing a float-derived balance.
6. Freeze `{ sourceId, fingerprint }` from the current accepted available quote into the submission intent. It is a reviewed reference, not authority to set prices. `ORDER_QUOTE_CHANGED` invalidates catalog/current quote as applicable, retains the entire paper and requests explicit refresh/review before another submission; no silent new price is accepted.
7. A quote read/contract error shows safe retry/error feedback without replacing draft data or claiming a successful submission. The quote itself creates no persistent sale, number or command receipt.

**Verification design**: Proposed `catalogs.hooks.test.tsx` uses a real isolated QueryClient and deferred transport replies to test old source/old piece/old account publication, removed/duplicated rows, request cancellation, unavailable aggregate and exact key separation. Extend read-only money tests to observe Z3/Z4/Z12 amounts and nondecoration changes; full 14-rate and persistence evidence stays backend.
