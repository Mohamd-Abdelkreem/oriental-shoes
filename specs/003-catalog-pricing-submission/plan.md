## Summary

Extend the working P01/P02 foundations instead of rebuilding identity, customers, drafts or command reconciliation. Preserve `SalesDraft` and `SalesDraftPiece` identities/captured specifications, fence promoted aggregates with `SUBMITTED`, and attach one-to-one submitted commercial/lifecycle records. There is one aggregate version and one physical piece identity. Preserve original command snapshots and every existing migration.

The reviewed catalog has immutable source/entry identity and one active-source pointer. Current selections use explicit source-entry references while retaining original display strings; provisional draft text remains allowed. Quotes are server-calculated, stateless reviewed-intent fingerprints. A new paper or saved draft can submit atomically without an implicit earlier save. Submitted customer/price terms stay fixed; returned edits commit only with explicit resubmission. Exact cumulative paid is a separate authorized action within the existing finance surface.

The companion owners form one design, not competing schemas:

- [contracts/sales-orders.md](contracts/sales-orders.md): executable-schema design, exact wire fields/HTTP/errors, compatibility, parser/loader boundary and public service interfaces.
- [data-model.md](data-model.md): fields, relations, constraints/indexes, transaction/lock order, migration/recovery and future lifecycle ingress.
- [frontend-design.md](frontend-design.md): reached consumers, exact API/hooks/model/UI interfaces, cache/epoch/draft/error algorithms and browser cases.

All source paths marked CREATE/proposed below are planned outputs, not files claimed present. Reference a companion's named section instead of copying its wire definitions. Technical planning readiness is distinct from executable backend/frontend/phase acceptance.

## Contracts, Authority and Failure Design

The [contract](contracts/sales-orders.md) owns every body/query/param/result schema, exact status/code, operation union and DTO/service signature. The [data model](data-model.md) owns concrete field/check/index/lock/migration definitions. The [frontend design](frontend-design.md) owns query keys and UI states. These owners are normative parts of each OP blueprint.

Common HTTP order: current business authentication → `authorizeDepartments(Department.SALES)` (ADMIN handled by existing authority) → CSRF for POST/PUT/PATCH including read-like quote POST → strict query/params/body validation → controller's required actor/parsed context → service → safe DTO → existing `ResponseHelper`. Route existence never grants business eligibility. Foreign/private order IDs use the same safe not-found result as missing resources; customer directory sharing does not widen order visibility. No new factory price route is introduced.

Read transactions follow existing `RepeatableRead`, actor account read lock/current authority, 5-second lock/max-wait and 10-second transaction timeout, one recognized transaction retry. Commands reuse `SalesCommandExecutor`'s `ReadCommitted`, same account/command lock protocol and recognized retry policy. Counter/pointer/root/customer operations use the transaction client and fixed lock order in the data owner. Workbook I/O, parser work and public response serialization do not hold long database locks.

Immutable receipts remain the committed after-image, not the latest resource. Extend the result union for order operations without changing old P02 snapshots. Replay lookup precedes current version/state/no-op checks, while current authority and resource visibility still apply. Command observation remains original-actor-only. Unknown response recovery uses the same frozen identity/body; no new key can be used to evade an unresolved original action.

### Exact calendar configuration seam

Proposed `core/config/order.config.ts` exports `parseOrderBusinessTimeZone(value: string | undefined): string | null` and frozen `orderConfig = { businessTimeZone }`. Reuse `getEnvVariable('ORDER_BUSINESS_TIME_ZONE', '')` so a missing setting does not throw during unrelated startup; blank/invalid values normalize to unavailable null, never a guessed zone. `core/config/index.ts` exports the config; router composition injects it into the proposed `SalesOrdersService(database, commands, businessTimeZone)` constructor. Proposed `sales-orders.calendar.ts` exports `getOrderBusinessYear(instant: Date, timeZone: string | null): number`, uses explicit Gregorian calendar/Latin digits and validates the 1–9999 result. It uses the executor's one captured `occurredAt` instant and raises the safe calendar-unavailable error for absent/invalid configuration. `.env.example` documents the blank unresolved operational setting without supplying an accepted default. Unit cases cover absent/invalid/explicit zones and a year boundary; no protected Next fetch or client configuration is introduced.

Read the existing API environment/config, database client factory, CLI entry conventions and test harness before implementing. Only the CLI imports ExcelJS; API composition imports the small catalog service/query/rules owners.

**Ordered algorithm**:

1. Validate exact CLI arguments/target mode and file-size/resource bounds. Read one immutable byte buffer; compute SHA-256 before parsing and compare the reviewed expected source hash. Missing/changed file or invalid workbook rejects without writes. No macro/external-link evaluation, network retrieval or automatic workbook recalculation.
2. Parse the named worksheet, explicit ranges and evaluated/cached scalar values through the pinned adapter. Preserve original strings/rich-text joining as specified; reject unexpected source types/missing caches instead of inventing display labels or zero-padding. Numeric selection columns use only accepted sets; prices reconcile all 14 same-row pairs. Exclude headers/color statistics without losing I104, retain 14 color families and the two source asymmetries, and produce bounded preview diagnostics.
3. Validate counts, exact mapping/rates, duplicate identities/ambiguous rates and all retained labels before obtaining any write transaction. Preview is read-only and reveals no database credentials or customer data.
4. For separately authorized apply, use the data owner's singleton pointer lock/unique source hash. Recheck reviewed manifest identity, insert one source and its validated entries in bounded batches, or verify/reuse the existing same-hash source. Activate only after all entries/rates and counts agree. Any dependent-write failure rolls back source/entries/pointer; repeat apply creates no duplicates and never rewrites old submitted snapshots.
5. A different workbook is never silently made authoritative: compare/review its manifest first, preserve the previous source/entries for retained references, then apply the explicitly accepted revision. Do not create a generic revision-management platform or activate data from test fixtures in production.

**Frontend**: No CLI UI. Catalog query consumers expose only authoritative source readiness/entries. No real options fall back to demo arrays. Background source changes invalidate quotes and require price review on changed terms (F02).

**Cases**: Pinned adapter fixtures with cached formula strings/numbers, missing cached results, mixed-language/trailing-space/leading-zero/rich text, bad source hash, exact ranges/families/counts, I104 and color statistics; real DB repeat-load and failure-after-entry-insert rollback; concurrent apply/submit pointer locking; actual reviewed file hash/content verification separately. ### OP-03 — Catalog reads, source-bound selections and current quote

**Requirements/examples**: FR-003–009/027–029; US1/2, 1800/1500/650 and 3300 examples.  
**Interfaces**: Proposed `CatalogsService(database: DatabaseClient)` exposes `get(actorId: string): Promise<CatalogData>` and `quote(actorId: string, input: CatalogQuoteBody): Promise<CatalogQuoteData>`. Draft selection reference storage is in data-model; source-aware paper props/selection model are in F01/F02.

**Ordered algorithm**:

1. Authorize current SALES/ADMIN, read one active catalog source in a repeatable-read snapshot, fetch only its bounded ordered entries/families and return exact display values with stable IDs/source cells. A missing active source returns the documented unavailable readiness, never demonstration values or false empty success.
2. For a quote, validate distinct stable piece IDs/max200 and known selector fields. Resolve supplied entry references by the correct kind/source; if a provisional label has no ref, resolve only one exact active-kind match. No match/ambiguous match is visible invalid selection; do not silently select the first. Keep original display values intact.
3. Price only selected decoration entries from Z and same-row AA. Missing/unknown/ambiguous/invalid rate yields the contract's unavailable piece/quote outcome; do not fabricate zero. Other fields never modify amount. Sum exact bigint cents, serialize two decimals and produce source ID plus canonical quote fingerprint. Fingerprint binds sorted piece ID, decoration entry ID, source ID and server amount; it is a review reference, not user authority and needs no quote table/session secret.
4. Return all per-piece quote states and ready total only as designed; no persistent order/number/history write occurs. Reads/quote POST use the actual route guards/strict schema and bounded result. No email/provider side effect.

**Frontend**: F01/F02 use source-record IDs/group labels and per-piece stable identity, clears refs on provisional custom text, validates exact membership only at submission, and keeps draft saving permissive. **Requirements/examples**: FR-004–005/009–011/015–017/028; upstream P02 incomplete-save/row identity and old-receipt cases.

**Shared header mapping interface**: Proposed `toDraftCaptureHeaderValues(capture: DraftCapture): Pick<Prisma.SalesDraftUncheckedCreateInput, 'type' | 'customerId' | 'deliveryDate' | 'generalNotes' | 'repairNote' | 'adjustmentRequested' | 'adjustmentReason' | 'adjustmentActionTaken' | 'responsibleSignature' | 'paidAmount'>` in `apps/api/src/modules/sales-drafts/sales-draft-capture.writer.ts` extracts the current `SalesDraftsService.headerValues` mapping with existing `parseDateOnly`/exact Prisma decimal conversion. Its output contains only the ten captured header fields, never identity/owner/version/status/action timestamps. Existing draft callers and T014 direct-new creation use this same helper; replacement writer branches apply their explicit field allowlists to it.

**Algorithm and fixed write branches**:

1. The caller establishes current account/command locks, the existing root lock where applicable, sorted customer locks and strict capture. For `mode:'create'`, the caller has just inserted the new root with its complete captured header, owner, timestamps and version (DRAFT for ordinary create; SUBMITTED/version1 for direct new submission). No preliminary committed draft is introduced. The writer does not update that new root header again.
2. Inside the same supplied transaction, read that root's status and bounded piece identities including `position`; retain the existing OR lookup for own active pieces plus requested IDs. Reuse `classifyDraftPieces` unchanged for duplicate/foreign/tombstone failures. Sort own active rows by position then ID and compare their ordered IDs with the requested IDs. Reading status enforces structure; the writer never grants authority, chooses a transition or updates owner/version/status.
3. `mode:'create'` requires a caller-created root with no existing pieces (including tombstones), no order extension yet and entirely fresh requested piece IDs. Prove piece absence with a bounded `salesDraftPiece.findFirst({where:{draftId},select:{id:true}})` existence check; the active/requested-ID lookup alone does not see unrequested tombstones. Insert initial rows at positions 1..N and their selections. This branch supports a new SUBMITTED root because these are initial INSERTs, not changes to frozen piece positions. Inconsistent internal creation preconditions fail closed with the existing InternalServerError; known client identity conflicts retain the current classifier/caller mapping.
4. `mode:'replace'` on SUBMITTED requires no new/removed IDs and exactly the retained ordered membership. Update only permitted nonprice header/piece captures, current selection rows and updatedAt. Exclude type/customer/original paid from header writes and exclude piece position, removedAt and quantity from SQL writes entirely, even if their values would be equal. The resubmit service already rejects client fixed-term/membership/order changes with `ORDER_CORRECTION_CONFLICT`; the writer treats a remaining structural mismatch as a violated internal precondition and fails closed. Fixed values, prices, snapshots and physical state stay unchanged.
5. `mode:'replace'` on DRAFT uses the same capture-only path when membership/order is unchanged, with the existing permissive draft header fields. Only actual DRAFT membership/order changes use the existing tombstone → temporary retained-position +200 → restored positions/new-row inserts algorithm. Check affected counts and preserve stable identities and removed-row evidence. There is no temporary position/removedAt/quantity UPDATE on a SUBMITTED root.
6. All branches retain current reference replacement semantics, exact original text and incomplete-draft compatibility; no external I/O. The caller owns root state/version CAS and immutable receipt in the same transaction. Resubmission constructs its capture from fixed saved values plus the correction allowlist. Direct-new submission writes extensions only after the initial capture rows; deferred final-graph constraints still see one valid complete aggregate.

**Required branch cases**: In existing draft service integration tests, unchanged and reordered DRAFT captures preserve save/tombstone behavior. In returned-order service integration tests with all migrated triggers enabled, size40→40.5 and header-only correction succeed without any base position/removedAt/quantity write and retain IDs/order/frozen terms. New direct submission from an initially SUBMITTED/version1 root still succeeds with fresh pieces. Forged add/remove/reorder is rejected before writes; forced dependent failure restores captures, selections, version and receipt.

**Failure behavior**: Foreign/removed/reused piece IDs, bad refs or affected-row mismatch roll back all work; losing stale editor retains local input. Customer/draft state authority remains server-enforced. Current P02 lists/counts/measurements/detail/cards include only DRAFT roots; command history explicitly discriminates historical DRAFT receipts from live submitted projections.

**Frontend/cases**: Keep existing draft manual-save/pending/replay/dirty/inline-customer behavior through frontend section 3/F03. Extend existing draft tests for partial unknown values and optional refs; migration/HTTP tests prove blank save, identity/tombstones and unchanged historical receipts after promotion. No autosave or returned-to-DRAFT workflow.
