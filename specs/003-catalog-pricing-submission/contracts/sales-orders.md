# P03 Contract and Interface Blueprint

This is the proposed executable-contract design for [P03](../spec.md), not implemented endpoints or generated API code. Read alongside the persistence owner [data-model.md](../data-model.md), operation algorithms in [plan.md](../plan.md), and consumer owner [frontend-design.md](../frontend-design.md). All paths/symbols marked proposed must be produced by later implementation before their consumers run.

## 1. Existing boundaries and compatibility

Verified existing owners are `packages/contracts/src/http/http.schema.ts` (strict success/error envelopes, `paginationQueryFields`, `isSafePaginationWindow`, `paginationMetaSchema`), `sales-drafts/sales-draft-values.schema.ts` (UUID/version/instant/type and draft limits), `sales-drafts/sales-drafts.schema.ts` (captures, responses and historical draft receipts), `customers/customers.schema.ts` (Saudi phone/customer/version), and `sales-commands/command-receipt.schema.ts` plus `sales-commands.schema.ts` (receipt and discriminated result).

Use `successEnvelopeSchema` plus the operation's data schema through the existing `parseApiResponse` in `apps/web/src/services/api/api-client.ts`. Controllers retain `ResponseHelper.ok(response,data,message,path,requestId)` and `.created(...)`; errors retain the existing safe envelope and target-prefixed field errors. No second transport, protocol, credential scheme or generic repository is introduced.

- Proposed contracts are `packages/contracts/src/catalogs/catalogs.schema.ts` and `packages/contracts/src/sales-orders/sales-orders.schema.ts`, deliberately exported through the existing contracts index. API DTO files alias these symbols; browser code imports contracts only.
- Extend existing command operation/result unions with explicit order branches. Never let a final `else` classify a new operation as a draft. Existing P02 command payload hashes, historical JSON snapshots and legacy result parsing remain valid and byte-for-byte unmodified in storage. For new CREATE_DRAFT/SAVE_DRAFT intents, conditionally append the ten-key sorted catalogSelections map only when supplied; omission must produce the exact old hash bytes. Supplied reference changes must be bound to the command ID rather than ignored by the old hash algorithm.
- `SUBMIT_NEW_ORDER` is a creation receipt: `beforeVersion=null`, `afterVersion=1`. `SUBMIT_DRAFT`, `RESUBMIT_ORDER`, `SET_ORDER_PAID` are updates: nonnull before version and after version exactly before plus one. Existing CREATE/UPDATE/SAVE rules remain unchanged.
- Live draft responses use the exact catalog/calendar readiness unions below, while retained `P03_NOT_IMPLEMENTED`/`P03_NOT_READY` variants remain accepted historical branches. Do not inject new defaults into old snapshots. The additive `catalogSelections` field described below is optional without a parser default.
- P02 `/sales-drafts` list/detail/customer-draft/measurement queries explicitly filter `DRAFT` after promotion. Retained command observation still returns original snapshots, never an invented latest result. Submitted reads use this owner. Producer, browser consumers, OpenAPI and tests deploy coherently; no independent old-client support is asserted for new order variants.

## 2. Scalar and capture rules

All object schemas are strict. Reject unknown authority fields rather than stripping or accepting them. UUIDs reuse `salesUuidSchema`, instants `salesInstantSchema`, versions `salesVersionSchema`; promised dates retain the actual calendar-date validation in the existing draft schema. Existing known order types are exactly SHOP, EXTERNAL, REPAIR, GIFT, READY, ACCESSORY and ADJUSTMENT.

| Value                    | Wire / bound / meaning                                                                                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Money output             | Canonical nonnegative decimal string with exactly two fractional digits; no exponent, comma or float-based calculation                                                                                                                                 |
| Paid/unit amount         | Range `0.00`–`999999999.99`, preserving existing P02 capacity; new P03 columns use unconstrained NUMERIC with range/scale CHECKs; paid input accepts existing one/two-decimal forms then canonicalizes, but an update requires explicit nonblank input |
| Total/due/surplus        | Canonical two-decimal string within the same 14-digit/two-decimal capacity enforced by NUMERIC range/scale CHECKs; sums use bigint cents; maximum 200 pieces at the accepted unit bound fits                                                           |
| Global sequence          | Positive decimal string representing the persisted bigint, no leading zeroes, at most 19 digits and at most `9223372036854775807`; display number applies minimum four-digit padding separately; never JSON bigint/unsafe Number                       |
| Number                   | `TYPE-YYYY-NNNN`, uppercase accepted type, Gregorian four-digit first-submission year, minimum four sequence digits, no truncation; server derived                                                                                                     |
| Fingerprint / source SHA | Lowercase 64-character hexadecimal SHA-256 string; a fingerprint expresses reviewed terms, not authority or a credential                                                                                                                               |
| Piece collections        | 1–200 distinct stable piece UUIDs; quantity always literal 1; body remains within the existing 262,144-byte capture bound                                                                                                                              |
| Existing captures        | Preserve existing nullable text limits (piece text 200, side/general/type notes 4,000, signature 150), whitespace-to-absence behavior and real dates; do not trim an accepted source display label into a replacement value                            |
| Search / paging          | Search at most 150 characters with no null character; trim outer search whitespace, blank means omitted; page 1 and limit 25 defaults, max limit 100; safe offset arithmetic; customer panels max limit 25                                             |

### Additive selected-source references

Proposed `catalogFieldSchema` / `CatalogField` has exactly ten values: `model`, `size`, `leatherBase`, `decoration`, `decorationColor`, `sole`, `soleAddition`, `soleColor`, `aField`, `fField`.

Proposed `pieceCatalogSelectionsSchema` / `PieceCatalogSelections` is a strict partial object with those ten keys; each present value is an entry UUID or null. Add optional `catalogSelections` to draft piece capture/replacement/output. Do not give it a default: omission in an old receipt stays omission. Omitted/null references are provisional, not a fallback catalog. A changed text capture with no matching reference must not accidentally reuse a previous reference.

Draft saves remain permissive about catalog membership. During quote/first submission, a supplied reference must identify the correct active-source/kind entry and its exact display value must match the captured string. If no reference is supplied, only a unique exact active-source/kind/value match may resolve it; zero or multiple matches require visible correction. Do not choose the first match, merge kinds/families, translate or fabricate a value. Source coordinate identity distinguishes duplicate display strings. Optional absent fields remain absent, not the first option.

Proposed `submissionCaptureSchema` / `SubmissionCapture` refines the extended draft capture: customerId nonnull; each row requires model, size, leatherBase, nonblank face and priced decoration; all provided selections/dates must validate. It does not make delivery date, customer email/address, remaining selectors/text, repair or adjustment text mandatory. Signature is captured text, not approval/actor authority.

### Live draft readiness and retained receipt compatibility

Export proposed `draftPricingReadinessSchema` / `DraftPricingReadiness` and `draftSubmissionReadinessSchema` / `DraftSubmissionReadiness` from the existing sales-drafts contract owner, and use them in draft detail/summary.

- Pricing is exactly one of historical `{availability:'unavailable',reason:'P03_NOT_IMPLEMENTED'}`, live `{availability:'unavailable',reason:'CATALOG_NOT_LOADED'}`, or live `{availability:'available',sourceId:UUID}`. Available means the quote capability has an active reviewed source; it contains no unit price or total and does not prove a particular decoration is priced.
- Submission is exactly one of historical `{available:false,reason:'P03_NOT_READY'}`, live `{available:false,reason:'CATALOG_NOT_LOADED'}`, live `{available:false,reason:'ORDER_CALENDAR_UNAVAILABLE'}`, or live `{available:true}`. Test source readiness first, then configured calendar. Available means environment admission only; required fields, current customer/quote, owner/state/version and all command validation still apply.
- New live draft reads derive both fields from one active-source snapshot and current calendar configuration without per-row catalog lookup. Historical receipt snapshots retain their recorded old variants and omission of catalogSelections. The generic retained snapshot parser accepts all these strict branches; the live mapper does not manufacture the old not-implemented variant once P03 is installed.

## 3. Catalog and quote wire shapes

Proposed `catalogEntrySchema` / `CatalogEntry` has `{id,kind,sourceCell,displayValue,family,position}`. `id` is the retained entry UUID; `kind` is CatalogField; `sourceCell` is its actual reviewed cell; `displayValue` preserves the evaluated source string exactly; `family` is null except decoration colors, which use `{key,label}` with source column L through Y as key and its exact row-2 label; position preserves source ordering. No formula, filesystem path, database object or rate is returned in an entry.

`catalogDataSchema` / `CatalogData` is:

- Available: `{availability:'available',sourceId,sourceSha256,activatedAt,entries:CatalogEntry[]}`. The reviewed source has 1,874 selectable entries across the ten kinds: 7 models, 55 sizes, 590 bases, 14 decorations, 1,010 decoration colors, 12 floor models, 5 middle additions, 40 floor colors, 81 A values and 60 F values. Validate the approved source-specific counts, not an arbitrary generic catalog size.
- Unavailable: `{availability:'unavailable',reason:'CATALOG_NOT_LOADED'}`. This is a successful readiness observation, not an empty catalog or a failed network request. A database/contract failure remains an error.

`catalogQuoteBodySchema` / `CatalogQuoteBody` is `{requestId,pieces}`. requestId is a caller-generated UUID used only to correlate the read result, not a persistent command key. Each piece is `{id,decoration,catalogSelections?}`; decoration is nullable capture text, and the optional strict map permits only the decoration key. An empty decoration is a valid quote request yielding an unavailable item. Other unknown fields, duplicates or over-limit input fail validation. The frontend does not put the random requestId in the stable query key.

`catalogQuoteDataSchema` / `CatalogQuoteData` echoes requestId and every requested piece identity in requested order. A priced item is `{pieceId,availability:'available',decorationEntryId,decoration,unitPrice}`; decoration is the exact resolved source label. An unpriced item is `{pieceId,availability:'unavailable',reason}` where reason is `CATALOG_UNAVAILABLE`, `DECORATION_REQUIRED`, `DECORATION_UNKNOWN`, `DECORATION_AMBIGUOUS`, `RATE_UNAVAILABLE` or `RATE_AMBIGUOUS`.

- All priced: `{availability:'available',requestId,sourceId,fingerprint,items,total}`.
- Any unpriced: `{availability:'unavailable',requestId,sourceId:UUID|null,fingerprint:null,items,total:null}`; priced peers may still display their prices. Never sum unknown prices as zero.

The fingerprint is SHA-256 of a versioned canonical JSON array containing sorted tuples `(pieceId,decorationEntryId,sourceId,canonicalUnitPrice)`, with distinct IDs and stable property/array ordering. No quote table, expiry job, additional secret or token authority is introduced. On submission, re-resolve from the locked active source and compare fingerprint/sourceId; changed terms yield 409 rather than silent repricing. Rates are never accepted as request authority. Match requestId, piece identities and the current stable query/input scope before publishing a response; the server envelope requestId remains independent diagnostic correlation.

## 4. Submitted read models

Proposed order status enum is exactly `AWAITING_APPROVAL`, `RETURNED`, `APPROVED`, `READY_FOR_DELIVERY`, `OUT_FOR_DELIVERY`, `DELIVERY_FAILED`, `DELIVERED`, `CANCELLED`. Piece stage is `AWAITING_APPROVAL`, `CUTTING`, `PRODUCTION`, `QUALITY`, `WAREHOUSE`, `CANCELLED`; workState is `INCOMING`, `IN_PROGRESS`, `COMPLETED`, `BLOCKED`. P03 writes only initial awaiting/incoming state and its resubmission transition. Future phase services own their actual state/decision writers; there are no P03 manufacturing/approval endpoints.

`salesOrderPieceSchema` / `SalesOrderPiece` includes the existing captured piece fields, optional catalogSelections, stable `id`, `position`, quantity literal 1, immutable `decorationEntryId`, `catalogSourceId`, `unitPrice`, plus `stage`, `workState`, `receivedAt`, `cancelledAt`, `cancellationReason`. receivedAt represents explicit physical receipt only. A cancelled piece retains specification/price/identity and history; cancelled count is deducted once. An unchanged obsolete selected source entry stays readable from retained data and may survive resubmission, but a newly changed selection must resolve to the current allowed source.

`salesOrderSummarySchema` / `SalesOrderSummary` omits pieces, approval proof fields and free-text notes/signature; it retains identity/version/owner/type/status/number/year/sequence/customerId/customerSnapshot/dates/money/counts/allowedActions. `salesOrderDataSchema` / `SalesOrderData` is `{order:SalesOrderDto}`.

### Approved returned-queue summary projection

SalesOrderSummary additionally requires `returnInfo: { reason: string; returnedAt: string } | null`. It is nonnull exactly when status is RETURNED; reason is the canonical current return reason, nonblank and at most4000 characters, and returnedAt is the canonical currentReturnedAt ISO instant. All other statuses require null. This bounded read projection has no reviewer/decision authority and does not change SalesOrderDto, stored receipts or persistence. The existing selected return fields supply it through `mapSalesOrderSummary(record,actor)` in the same scoped snapshot for unified lists, dashboard and customer history. The returned queue reads these fields without per-row detail requests or fabricated fallbacks. Update strict summary producers/consumers together before release; no deployed compatibility or actual P04 workflow is claimed.

### Exact submitted selection, record and safe mappers

Proposed owner `apps/api/src/modules/sales-orders/sales-orders.mapper.ts` exports `SALES_ORDER_SELECT`, `SalesOrderRecord`, `mapSalesOrder(record:SalesOrderRecord,actor:AuthorityAccount):SalesOrderDto` and `mapFactoryOrder(record:SalesOrderRecord):FactoryOrderProjection`. `AuthorityAccount` is the existing server-only current-account type, not a wire import. `SalesOrderRecord` is inferred as `Prisma.SalesDraftGetPayload<{select:typeof SALES_ORDER_SELECT}>`; do not hand-maintain an approximate database interface or cast a partial record into it.

The proposed Prisma relation names are root `order` (one SalesOrder), base piece `orderPiece` (one SalesOrderPiece), and base piece `catalogSelections` (selection rows). `SALES_ORDER_SELECT` is an explicit `satisfies Prisma.SalesDraftSelect` projection with this fixed content:

| Selection branch         | Explicit selected fields / predicates                                                                                                                                                                                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Root SalesDraft          | id, version, status, ownerId, customerId, type, deliveryDate, generalNotes, responsibleSignature, repairNote, adjustmentRequested, adjustmentReason, adjustmentActionTaken, createdAt, updatedAt; no mutable master contact relation or arbitrary spread                                                                     |
| owner                    | id, fullName only; no account email/phone/status/token/password fields                                                                                                                                                                                                                                                       |
| order                    | id, status, businessNumber, numberSequence, numberYear, submittedAt, submittedById, ownerFullNameAtSubmission, customerName, customerPhone, customerEmail, customerAddress, catalogSourceId, totalAmount, paidAmount, approvedAt, currentReturnDecisionId, currentReturnOrderVersion, currentReturnReason, currentReturnedAt |
| pieces                   | `where:{removedAt:null}`, `orderBy:[{position:'asc'},{id:'asc'}]`; id, position, quantity and every existing captured specification/measurement/sideNotes field; no tombstone resurrection                                                                                                                                   |
| pieces.catalogSelections | field, entryId only; convert rows into the optional typed map in fixed field order                                                                                                                                                                                                                                           |
| pieces.orderPiece        | id, orderId, decorationEntryId, priceSourceId, decorationLabel, unitPrice, priceSourceCell, stage, workState, issueId, receivedAt, cancelledAt, cancellationReason                                                                                                                                                           |

Map only a root in SUBMITTED state with a nonnull order and a matching nonnull orderPiece for every retained submitted piece; inconsistent persisted joins are safe internal defects, not silent omissions/default prices. Derive output version from the root. Map wire businessYear/sequence from numberYear/numberSequence, customerSnapshot from frozen header fields, owner.fullName from ownerFullNameAtSubmission, and piece catalogSourceId from frozen priceSourceId. Derive counts from the same selected extension pieces. Money uses frozen active prices and canonical submitted paid; do not read the old provisional root paid capture as current paid or use current master/rates. Action hints derive from the passed current eligible actor and persisted owner/state/proof; they never replace the service's authority checks.

### Factory-safe published producer boundary

Proposed `factoryOrderPieceSchema` / `FactoryOrderPiece` is a strict allowlist of `id`, `position`, quantity literal 1, the captured fields `model`, `size`, `leatherBase`, `decoration`, `decorationColor`, `faceRight`, `faceLeft`, `mixing`, `face`, `sole`, `soleAddition`, `soleColor`, `additions`, `aField`, `fField`, `sideNotes`, and `stage`, `workState`, `receivedAt`, `cancelledAt`, `cancellationReason`.

Proposed `factoryOrderSchema` / `FactoryOrderProjection` is strict `{id,version,type,status,businessNumber,customerName,deliveryDate,generalNotes,repairNote,adjustmentRequested,adjustmentReason,adjustmentActionTaken,counts,pieces:FactoryOrderPiece[]}`. customerName is the frozen header name and counts follows the same nonfinancial derived count rules; pieces remain bounded by 200. Every field is mapped explicitly from SalesOrderRecord. Both strict schemas reject extra financial/private fields in boundary tests.

Neither factory DTO contains unit/row prices, money, paid/due/surplus, catalog/price provenance IDs/cells, customer phone/email/address, raw financial history, responsible-signature approval claims or raw before/after snapshots. Do not build a financial DTO and delete a few keys, pass a pricing DTO through CSS hiding, or spread a raw joined record. `mapFactoryOrder` takes the same selected record but returns only this allowlist; strict-schema producer and private-nested-field regression tests prove it.

P03 publishes/tests this pure producer boundary only; it adds no factory endpoint or permission. Current factory callers to every P03 sales/catalog route remain denied by current business/department guards. P04–P07 own real factory HTTP routes, their current department/resource authorization and safe history projections; future wiring must consume this allowlist rather than expose sales revision snapshots. The factory projection does not itself authorize access or certify those later routes.

### Lists, dashboard and editor resolution

`salesOrderListQuerySchema` / `SalesOrderListQueryInput` accepts `{page?,limit?,search?,type?,status?,customerId?}`. status is DRAFT or an order status; omitted means ALL. Search matches the scoped technical UUID/business number/customer snapshot name or phone/model, plus current linked contact for drafts; escape SQL pattern characters. Type/customer/search scope applies before status counts; owner scope always applies first. Sort by updatedAt descending then id descending. Page total obeys all supplied filters including status; out-of-range page returns empty items plus accurate metadata and the caller explicitly recovers to the last/page-one destination.

`salesOrderListDataSchema` / `SalesOrderListData` is `{items,pagination,totalOrders,totalPieces,statusCounts}`. Items are a strict union `{kind:'draft',draft:DraftSummary}` or `{kind:'submitted',order:SalesOrderSummary}`. totalOrders/totalPieces and statusCounts use owner/type/customer/search base without status; pagination.total uses the selected status too. statusCounts has every DRAFT/order-status key, including zero values. Do not client-merge two independently paged stores.

`salesDashboardDataSchema` / `SalesDashboardData` is `{counts:{totalOrders,totalPieces,drafts,draftPieces,awaitingApproval,returned,approved},recentOrders}`. Counts use current actor scope without page/search; approved counts status APPROVED, not finished delivery states. recentOrders has at most five same tagged list items sorted by updatedAt/id descending. Existing shared customer-card query remains independent (limit four); no financial-reporting aggregate is added.

`salesOrderEditorDataSchema` / `SalesOrderEditorData` has exactly two tags: `{kind:'draft',draft:DraftDto}` or `{kind:'submitted',order:SalesOrderDto}`. A single authorized locator resolves the stable ID atomically; submitted status/allowedActions distinguish returned from locked UI. No 404-triggered alternate API fallback, fixture fallback, hidden-ID disclosure or extra tag is permitted.

`salesOrderTrackingDataSchema` / `SalesOrderTrackingData` is `{orderId,orderVersion,counts,pieces}`; each tracking piece is `{pieceId,stage,workState,receivedAt,cancelledAt,cancellationReason}` and the collection is bounded by 200. No event history is duplicated here. A lower-version late tracking result must not override newer detail/summary state.

### Activity and customer history

`salesOrderActivityQuerySchema` / `SalesOrderActivityQueryInput` reuses bounded page/limit only; no raw arbitrary filter/actor override. `salesOrderActivityDataSchema` / `SalesOrderActivityData` is `{events,pagination}` sorted occurredAt descending then stable event ID descending. Unified sales activity includes tagged `{kind:'draft',change:DraftChange}` or `{kind:'order',event:OrderActivityEvent}`; scoped detail activity exposes only that order's events. Draft snapshots remain parsed by existing P02 owners.

`OrderActivityEvent` has `{id,orderId,orderVersion,businessNumber,operation,pieceIds,actor,occurredAt,notes,changedFields,paidChange}`. actor reuses `SalesCommandActor`; notes is nullable bounded 4,000 text; pieceIds is distinct and <=200. changedFields is a distinct bounded array of accepted capture/header keys plus `pieces`, `catalogSelections`, `paidAmount`, `status`, `businessNumber`, `customerSnapshot` and `prices`; it identifies the changed responsibility rather than serializing arbitrarily large per-cell history. paidChange is null or `{before,after}` with canonical amounts, present for SET_ORDER_PAID. Actual relevant before/after business values remain in the immutable retained command snapshot; the original actor can observe that exact accepted result through the existing command endpoint. Current P03 order operations are SUBMIT_NEW_ORDER, SUBMIT_DRAFT, RESUBMIT_ORDER and SET_ORDER_PAID, derived from retained command snapshots. No raw private JSON, fabricated future movement, generic event bus or duplicated tracking ledger is returned. P04–P07 extend the operation enum/mapper against their real retained decisions/movements when implemented; the stable IDs/time/actor/piece shape remains this owner.

`salesOrderRevisionDataSchema` / `SalesOrderRevisionData` exposes scoped prior values on demand in the existing history tab: `{event:OrderActivityEvent,before,after:SalesOrderDto}`. before is null for SUBMIT_NEW_ORDER, `{kind:'draft',draft:DraftDto}` for SUBMIT_DRAFT, or `{kind:'order',order:SalesOrderDto}` for RESUBMIT_ORDER/SET_ORDER_PAID. Event ID is the retained SalesCommand commandId. Recheck current owner/ADMIN order visibility, then require that command's draftId equals the requested order and operation is one of the four order operations. Missing/foreign/wrong-kind event is 404 ORDER_REVISION_NOT_FOUND without disclosure. Parse historical JSON through the strict owning snapshot schemas and explicitly project safe fields; never spread database JSON or return credentials/private account data. Each snapshot retains the existing 200-piece/capture bounds. after.id and event.orderId must match the route; after.version must equal event.orderVersion, and before/after versions must follow the receipt. Do not refetch current terms into a historical snapshot. This read is available to current owner/ADMIN even when another authorized actor made the event; it does not widen original-actor command reconciliation or add factory finance access. The browser expands a history entry inline and fetches this result lazily, without a new page/modal or preloading every revision into a paged list.

`customerOrdersQuerySchema` / `CustomerOrdersQueryInput` is strict `{page?,limit?,type?,status?}` with submitted statuses only and maximum limit 25; customer identity comes only from the route, ownership from actor. `customerOrdersDataSchema` / `CustomerOrdersData` is `{orders:SalesOrderSummary[],pagination,totalOrders,totalPieces}` with scoped, fully filtered totals and submittedAt/id descending ordering. Existing customer `/drafts` remains separate and draft-only.

`customerOrderMeasurementsQuerySchema` / `CustomerOrderMeasurementsQueryInput` is strict bounded page/limit, max 25. `customerOrderMeasurementsDataSchema` / `CustomerOrderMeasurementsData` is `{measurements,pagination}`; each row has `{source:'SUBMITTED',orderId,orderVersion,businessNumber,pieceId,submittedAt,model,size,aField,fField,cancelled}` using retained specifications and nullable optional A/F. Sort submittedAt descending, orderId descending, piece position ascending then pieceId ascending. Retain cancelled historical pieces with cancelled=true rather than erasing their history or presenting them as current active work. No automatic measurement-reuse workflow is introduced. Existing `/customers/:customerId/measurements` keeps its P02 provisional DRAFT meaning; do not silently relabel it approved or include other owners' records.

## 5. Command bodies and outcomes

`submitOrderBodySchema` / `SubmitOrderBody` is a strict discriminated union:

- New: `{origin:'new',commandId,capture:SubmissionCapture,expectedCustomerVersion,reviewedQuote:{sourceId,fingerprint}}`.
- Saved draft: `{origin:'draft',commandId,draftId,expectedVersion,capture:SubmissionCapture,expectedCustomerVersion,reviewedQuote:{sourceId,fingerprint}}`.

The new branch creates the root and submitted extension together at version 1 without an earlier committed draft or fake CREATE_DRAFT event. The saved branch verifies current DRAFT owner/version and promotes the same aggregate/pieces at version+1; full capture may include the existing draft row operations, but never foreign/removed IDs. Revalidate/reconcile captured source selections, freeze current customer at expectedCustomerVersion and compare current reviewed quote before number allocation. Customer summaries currently lack a revision: fetch the existing full customer detail before enabling/reviewing submission rather than inventing a version or changing historical summary schemas.

`returnedOrderCorrectionsSchema` / `ReturnedOrderCorrections` is a full replacement of only permitted correction captures: deliveryDate, generalNotes, responsibleSignature, repairNote, adjustmentRequested, adjustmentReason, adjustmentActionTaken and pieces. Each piece requires existing id and every nullable nonprice captured field except decoration; optional catalogSelections permits only the other nine selector keys. Customer/type/paid/number/decoration/prices/state/quantity/actor are unsupported and rejected. Pieces must exactly equal the existing active physical set: no add/remove/reorder into different identities; preserve existing positions. Preserve immutable decoration selection in storage when updating other selection rows.

`resubmitOrderBodySchema` / `ResubmitOrderBody` is `{commandId,expectedVersion,corrections:ReturnedOrderCorrections}`. Missing or incomplete current return proof is a conflict. Corrections persist only atomically with successful explicit resubmission and its history/version; no standalone correction-save or returned-to-draft command exists.

The resubmission command hash binds the request operation, target, expectedVersion and normalized corrections only. Do not hash the current server-fetched return decision ID or other mutable proof: an accepted replay must still match after the command clears current return fields. The locked current proof is an execution precondition and its relevant values remain in the retained before snapshot, not a changing input to replay identity.

`setOrderPaidBodySchema` / `SetOrderPaidBody` is `{commandId,expectedVersion,paidAmount}`. Paid amount is explicit valid nonnegative <=2-decimal input; omission/null/blank is rejected, unlike initial submission's unpaid zero. Receipt replay runs before new-intent validation against current aggregate state. For a fresh current-version request equal to stored paid, return 409 ORDER_PAID_UNCHANGED with no write/receipt/version/event; render useful already-current feedback and refetch. A stale version is ORDER_VERSION_CONFLICT, not a silent noop. A changed valid amount may be lower; record it as a cumulative correction without external refund.

`salesOrderCommandDataSchema` / `SalesOrderCommandData` is `{kind:'order',receipt,replayed,savedOrder:SalesOrderDto}`. Receipt operation must be an order operation, resourceId must equal savedOrder.id, afterVersion must equal savedOrder.version, and the retained result is the confirmed historical snapshot. The generic SalesCommandData union adds this branch, so existing `/sales-commands/:commandId` reconciles lost P03 responses using its current original-actor/resource checks. Different command ID targeting the same stale submitted intent cannot create another business effect.

### Stable failure mapping

| Status / code                                                | Meaning and unchanged outcome                                                                                                                                             |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400 VALIDATION_ERROR                                         | Existing schema/domain field errors; paths such as `body.capture.pieces.0.size`, `body.corrections.pieces.0.catalogSelections.sole`, `body.paidAmount`; no business write |
| Existing 401 / ACCOUNT_RESTRICTED / DEPARTMENT_ACCESS_DENIED | Preserve current authentication/eligibility/department protocol and safe errors                                                                                           |
| 404 ORDER_NOT_FOUND                                          | Missing/inaccessible aggregate or illegal foreign piece identity; no existence disclosure                                                                                 |
| 404 ORDER_REVISION_NOT_FOUND                                 | Missing/inaccessible/wrong-order/wrong-operation historical event; no foreign snapshot disclosure                                                                         |
| Existing 404 CUSTOMER_NOT_FOUND                              | Customer does not exist, without implicit fallback/create/link                                                                                                            |
| 409 ORDER_VERSION_CONFLICT                                   | Aggregate changed; retain input, reload/review; no losing write                                                                                                           |
| 409 ORDER_STATE_CONFLICT                                     | Not DRAFT for first submit, not currently RETURNED for resubmit, or not approved/eligible for paid                                                                        |
| 409 ORDER_CUSTOMER_CHANGED                                   | Linked customer's version changed from the reviewed contact; refresh/review contact and retry intentionally                                                               |
| 409 ORDER_QUOTE_CHANGED                                      | Active source or recomputed price fingerprint differs; refresh/review quote, no number/submission                                                                         |
| 409 ORDER_CORRECTION_CONFLICT                                | Piece set or immutable submitted terms differ; reject without changing original terms                                                                                     |
| 409 ORDER_PAID_UNCHANGED                                     | Already-current fresh paid amount; no receipt/write/version/event; informational refetch                                                                                  |
| Existing 409 SALES_COMMAND_CONFLICT                          | Same command ID bound to another actor/operation/target/version/payload                                                                                                   |
| Existing 409 SALES_TRANSACTION_CONFLICT                      | Recognized exhausted transaction/lock contention; observe original command before retry                                                                                   |
| 503 ORDER_CATALOG_UNAVAILABLE                                | First submission requires a reviewed active catalog/rate set; partial draft save/quote readiness remain usable                                                            |
| 503 ORDER_NUMBER_UNAVAILABLE                                 | Global counter is missing or exhausted; no root, issued number, counter advance or receipt; drafts/catalogs remain usable                                                 |
| 503 ORDER_CALENDAR_UNAVAILABLE                               | ORDER_BUSINESS_TIME_ZONE is absent/invalid, so no first-submission year/number can be established; no default timezone/number/write                                       |

A normal validation/missing/denied/conflict response confirms that rejected operation made no write; a disconnected/lost response does not establish rollback. Preserve command identity and reconcile before retry. Error body never includes current foreign data, SQL/Prisma objects, raw snapshots, workbook paths or secrets. OpenAPI must register every actual method/schema/status/security rule together with implementation.

## 8. Workbook parser design decision and evidence

No XLSX/ZIP/XML reader is currently installed in the inspected API/database/contracts manifests or lockfile. Plan a pinned `exceljs@4.4.0` API development dependency used only by the scoped loader/tests, not API request paths or browser imports. Its maintained parser boundary is preferable to handwritten ZIP/XML decoding or an undeclared Python/office runtime. Installation and Node 24 compilation/runtime compatibility verification are later implementation work, not achieved evidence.

The [pinned README](https://github.com/exceljs/exceljs/blob/v4.4.0/README.md#formula-value), [type declarations](https://raw.githubusercontent.com/exceljs/exceljs/v4.4.0/index.d.ts) and [package metadata](https://raw.githubusercontent.com/exceljs/exceljs/v4.4.0/package.json) were inspected during planning. They establish cached formula-result access, `xlsx.read(stream, options?)`, and pinned package identity; they do not establish implemented parser execution or Node 24 tests. The identical root workbook has since been inspected read-only as recorded in Plan Authorized Preparation Amendment; the proposed adapter/CLI remains unexecuted.

The proposed adapter consumes the same bounded bytes whose SHA-256 was checked against the reviewed source before parsing: `new ExcelJS.Workbook()` then `workbook.xlsx.read(Readable.from([verifiedBuffer]))`. This uses the documented nonstreaming workbook parser interface through a Node stream and avoids relying on its legacy Buffer declaration. No formula evaluation, external-link fetching, source rewriting or recalculation is performed.

Read only the exact allowed cells/ranges in root roadmap Section 4. Label/code columns A/B/C/I/L:Y/Z must resolve to original strings or joined rich-text runs; a formula requires a present valid cached string. Unexpected dates/booleans/errors/numeric label forms fail preview instead of guessing display text/zero-padding. D/E/F/G numeric source sets and AA rates accept only the explicit reviewed values with exact canonical decimal conversion. Preserve source strings including trailing spaces/case/leading zeroes; do not use generic `.text` formatting as proof of numeric code fidelity. Missing/error cache, changed digest, invalid counts/rates or unexpected source types leave activation closed. The identical repository-root workbook is available with source inspection recorded in Plan Authorized Preparation Amendment. Actual adapter/CLI reconciliation is still an explicit execution/loading gate.
