# P02 Data Model and Transaction Design

**Status**: Proposed design, 2026-11-05; no schema, migration or runtime change has been executed. This document owns persistence and concurrency decisions for [P02](spec.md). The [wire contract](contracts/customers-drafts.md) owns accepted values, DTOs and endpoints. The feature plan owns operation sequencing and delivery gates.

## 1. Models and stable identity

Extend `packages/database/prisma/schema.prisma`; preserve its generator, PostgreSQL datasource and existing P01 models/enums/relations. New UUIDs use existing UUID conventions. The four proposed tables below are P02 domain storage, not a generic event or snapshot platform. Server-generated customer/draft IDs remain stable when phone, type or display labels change. P03 must extend/share the same draft identity when adding submission; it must not derive a new order identity from a business number.

### Customer / `customers`

| Field                    | Prisma / PostgreSQL                                          | Meaning                                                    |
| ------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------- |
| `id`                     | `String @id @default(uuid()) @db.Uuid`                       | Stable customer identity                                   |
| `name`                   | `String @db.VarChar(150)`                                    | Trimmed required name                                      |
| `phone`                  | `String @unique(map: "customers_phone_key") @db.VarChar(13)` | Canonical Saudi `+966` contact; no raw formatting identity |
| `email`                  | `String? @db.VarChar(320)`                                   | Optional normalized email; deliberately nonunique          |
| `address`                | `String? @db.VarChar(2000)`                                  | Optional basic address                                     |
| `notes`                  | `String? @db.VarChar(4000)`                                  | Optional shared customer notes                             |
| `version`                | `Int @default(1)`                                            | Edit revision, 1 through 2,147,483,647                     |
| `createdAt`, `updatedAt` | `DateTime @db.Timestamptz(6)`                                | Server instants, explicit update time from command         |

No customer owner, deleted flag or merge relation is introduced. All eligible sales/ADMIN share contacts. Name/email are not unique. Customer relations to drafts/commands use `onDelete: Restrict`; this phase has no customer deletion. Canonical phone changes in place, freeing the old phone, while all relations follow `id`.

### SalesCommand / `sales_commands`

One retained row is both the idempotency receipt and bounded business change evidence for a customer/draft command. There is no independent generic event ledger.

| Field                              | Prisma / PostgreSQL                                | Meaning                                                            |
| ---------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------ |
| `commandId`                        | UUID primary key, constraint `sales_commands_pkey` | Global command identity                                            |
| `operation`                        | New `SalesCommandOperation` enum                   | `CREATE_CUSTOMER`, `UPDATE_CUSTOMER`, `CREATE_DRAFT`, `SAVE_DRAFT` |
| `actorId`                          | UUID FK `User`, Restrict                           | Real authenticated actor                                           |
| `actorFullName`                    | `String @db.VarChar(150)`                          | Name at action time                                                |
| `actorRole`                        | Existing `UserRole`                                | Role at action time                                                |
| `actorDepartment`                  | Existing `Department?`                             | SALES for employee; ADMIN records its real nullable department     |
| `requestTargetId`                  | Nullable UUID                                      | Null for create, exact route ID for update                         |
| `customerId`, `draftId`            | Nullable UUID FKs, Restrict                        | Exactly one affected resource according to operation               |
| `expectedVersion`, `beforeVersion` | Nullable `Int`                                     | Null for creation; expected/current pre-update revision otherwise  |
| `afterVersion`                     | `Int`                                              | Resulting revision                                                 |
| `payloadHash`                      | `String @db.Char(64)`                              | Server SHA-256 of canonical accepted intent                        |
| `before`                           | `Json? @db.JsonB`                                  | Null on create; safe resource DTO before update                    |
| `after`                            | `Json @db.JsonB`                                   | Exact safe committed resource DTO; replay result owner             |
| `occurredAt`                       | `DateTime @db.Timestamptz(6)`                      | Same instant as resource update and removed-row timestamp          |

Use `Prisma.DbNull` for absent `before`, not a string or JSON sentinel. JSON images are built from explicit DTO mappers and validated with the appropriate shared response schema before insertion; they never spread Prisma records, credentials or unrelated entities. A draft image includes ordered active rows and the customer summary observed for that command, not a frozen customer contract for future submission. Current draft reads resolve the current customer master. Receipt replies label this image `savedDraft`/`savedCustomer` and never pass it off as current data after subsequent changes.

A valid new save, including an intentional unchanged-content save, advances the revision by one and records the explicit save action. Only the same command ID/payload is a replay and appends nothing. Version exhaustion is a conflict before any write. Receipt histories therefore distinguish intentional saves from transport repeats without guessing user intent.

Create narrowly scoped SQL triggers with explicitly named constraint errors: `ck_sales_draft_identity_immutable` rejects changes to an existing draft's id/ownerId; `ck_sales_draft_piece_identity_immutable` rejects changed id/draftId, resurrection or any mutation of an already removed row; `ck_sales_command_immutable` rejects UPDATE/DELETE of retained receipts. No speculative text-search/trigram/provider index is required for this initial bounded directory. Follow actual query plans before adding one.

The partial indexes/triggers remain authored SQL because Prisma declarations do not express these exact invariants. Schema inventory tests must intentionally include all four tables and three new enums; generated client output is generated normally during later implementation, never hand edited.

## 3. Protected transactions and command algorithm

### Existing reusable authority seam

`apps/api/src/modules/auth/account-authority.ts` already exports `lockAccountRows(tx,userIds,mode)`, `loadIdentityAccount(tx,userId)` and `assertBusinessAuthority(account,department?)`. Account IDs are sorted by the existing helper; `read` uses parameterized `FOR SHARE`, `write` uses `FOR UPDATE`. Staff changes use these same account locks in `StaffService`. P02 locks the actor in read mode for the entire protected read/write and calls `assertBusinessAuthority(actor, Department.SALES)` after loading the locked current account. No body owner/actor or token-carried department grants authority.

Set transaction-local `lock_timeout` to5000ms with the fixed parameterized `SELECT set_config('lock_timeout', '5000ms', true)` before acquiring account/domain/advisory locks; it never changes another session. Writes use the current Prisma 7 `$transaction(callback,{isolationLevel:ReadCommitted,maxWait:5000,timeout:10000})` shape already used by `StaffService`. Reads use the existing RepeatableRead pattern and the same bounds. All helper queries use the transaction client, never the root client. On recognized P2034 retry the whole transaction once, then return safe `409 SALES_TRANSACTION_CONFLICT`; no arbitrary network/uniqueness blanket retry.

### Shared SalesCommandExecutor

Proposed `apps/api/src/modules/sales-commands/sales-command-executor.ts` owns the one transaction/receipt algorithm; services supply typed resource work. Its two overloads and discriminated execution types are in contract §6. This is shared domain orchestration for these four commands, not a generic repository, queue or workflow engine.

1. Canonical parsed input and target/expectedVersion enter the executor. Compute the fixed-key payload hash described in contract §5 outside the transaction; hashing has no external side effect.
2. Begin transaction. Lock actor account in read mode, reload, assert current SALES/ADMIN authority.
3. Acquire a transaction-scoped advisory lock for the canonical commandId before looking for a receipt or executing domain work. Derive the signed64-bit key from the first16 hex digits of SHA-256 over `p02-sales-command:` plus canonical command UUID, using `BigInt.asIntN(64, BigInt('0x'+hex))`; bind the key's decimal string, not SQL text. Execute parameterized `$queryRaw<Array<{locked:number}>>` with `SELECT 1 AS locked FROM pg_advisory_xact_lock(${keyString}::bigint)`, projecting an integer rather than decoding the function's void return. The lock releases automatically at transaction end. A hash collision only serializes unrelated UUIDs; the full UUID receipt binding still decides identity. Current actor read lock precedes this command lock; domain locks follow it. After a same-command competitor commits, ReadCommitted's next statement sees its receipt before touching phone uniqueness or stale draft state. Then read `SalesCommand` by commandId. If present, require same actorId, operation, requestTargetId, expectedVersion and payloadHash; mismatch gives `409 SALES_COMMAND_CONFLICT` with no retained payload/private detail. Recheck current resource visibility (draft owner or ADMIN; customer shared). Map/validate the retained `after` DTO and return it with the receipt and `replayed:true`; do not run work or create history. Replay need not match the resource's latest version because `saved*` is explicitly historical; current resource is separately refetched.
4. If no receipt, create one `occurredAt = new Date()` after the receipt check, then invoke the operation's work callback with this transaction, locked actor and that exact Date. Customer update first locks its customer row FOR UPDATE. Draft update first loads/locks the scoped draft FOR UPDATE, then any linked customer rows FOR SHARE in ascending customer-ID order. Account locks always precede domain locks. Customer updates do not lock drafts, so this domain ordering creates no customer→draft cycle.
5. Callback validates current target/owner/state/version, applies the entire resource change and returns explicit safe before/after images. Foreign/missing draft selection is the same `404 DRAFT_NOT_FOUND`; customer missing is `404 CUSTOMER_NOT_FOUND`. A wrong version is the resource-specific 409, with no write.
6. Append exactly one SalesCommand row using real actor snapshot, affected IDs, canonical hash, before/after revision/images and the operation's server instant. Validate the receipt projection. The transaction commits resource and retained evidence together; any failure rolls both back.
7. Return `{kind,receipt,replayed:false,savedCustomer|savedDraft}` only after transaction success. No provider/network work or detached promise occurs inside/outside this operation.
8. Catch outside the failed transaction. A lock timeout SQLSTATE55P03 from the recognized lock query is a safe `409 SALES_TRANSACTION_CONFLICT`, with no partial effect; do not expose raw SQL. Require outer Prisma code `P2010`, then inspect current adapter-pg nested `meta.driverAdapterError.cause` where `kind=postgres` and `code/originalCode=55P03`; a code-like arbitrary message is not recognition. Pin this real emitted shape in integration evidence and preserve central fallback for an unexpected shape. The configured transaction deadline still bounds the whole operation. Only a P2002 whose adapter-pg `meta.driverAdapterError.cause.constraint.fields` identifies this command primary key permits one whole retry with the same intent. That fresh attempt finds/replays the winner; do not query inside an aborted transaction. Phone uniqueness and piece collisions have their separate narrow outcomes. If a recognized retry has already been used, return `SALES_TRANSACTION_CONFLICT`; the client can reconcile commandId.

P01's `isStaffCommandIdConflict` demonstrates the inspected nested adapter-pg shape, but is staff-specific and is not imported as a P02 classifier. Add narrowly owned sales/customer/piece classifiers; a top-level `meta.target` guess or all-P2002 replay is prohibited. Preserve central fallback mapping for unexpected errors. Phone P2002 on the unique `phone` field is `CUSTOMER_PHONE_CONFLICT`; a piece-primary-key collision is generic `DRAFT_NOT_FOUND` without foreign identity details. All other invariant failures remain safe internal errors.

### Customer write details

Create generates its UUID and version1 in the transaction, uses canonical phone and optional normalized data, and returns the mapped record. A competing phone claimant loses the unique constraint; the whole transaction rolls back with no command row. Update acquires the customer lock, checks version, refuses version exhaustion, computes the explicit patch (omitted unchanged, optional null clears), and runs a conditional `updateMany({where:{id,version:expectedVersion},data:{...allowedFields,version:{increment:1},updatedAt:occurredAt}})`. Affected count must be one. Requery the explicit selection and append command. Neither operation searches/merges by email or writes any draft/customer snapshot.

### Draft aggregate write details

Create derives ownerId from actor, validates optional customer existence under a read lock, generates draft UUID, and adopts only new piece UUIDs. Update loads only `id AND (ownerId=actor OR actor ADMIN)` before any unscoped child access, locks that draft row, reloads/checks `status=DRAFT` and expectedVersion, and refuses version exhaustion.

For both operations, validate unique submitted piece IDs and 1–200 rows. Query all submitted IDs once to classify them: active rows belonging to this draft may be updated; IDs absent globally may be inserted; foreign rows return generic `DRAFT_NOT_FOUND`; this draft's tombstones return `409 DRAFT_PIECE_CONFLICT`. Duplicate IDs in one request are `400 VALIDATION_ERROR` before writes. IDs cannot be reparented. No piece price, workflow state or quantity is accepted.

Save uses the parsed full replacement and immutable original owner. Resolve new customer explicitly; null clears the relation. Capture type-specific text independently so changing type does not silently erase the other optional capture fields. A single server `occurredAt` is used for the aggregate, changed pieces, tombstones and receipt. First tombstone omitted active rows; then move retained active positions above the active range by adding 200 in one SQL update. With at most 200 current positions, this creates no temporary position collision. Update retained rows into desired 1..N positions and insert new rows at their desired positions; removed historical positions are excluded by the partial index. The temporary positions are transaction-local and never returned. Update parent with owner/state/version predicates and increment revision; inspect affected count. Map active rows ordered by position, append receipt; any row/parent/audit failure rolls back the full aggregate.

No physical deletion, status transition or customer-master write occurs. A failed save cannot leave half a piece list, a changed paid entry, or a receipt for an uncommitted paper.

### Receipt observation

`GET /sales-commands/:commandId` requires current SALES/ADMIN authority, exact same actor as recorded, and current resource visibility. Absent/other-actor/inaccessible result is one `404 SALES_COMMAND_NOT_FOUND`. A found receipt returns its immutable saved result with `replayed:true`. An absent row does not prove rollback: the original transaction may still be pending. Client may observe again or resend the exact same bound intent; the unique command identity ensures one effect. No in-progress row, TTL purge, automatic retry loop or external provider is added.

## 4. Read projections and bounded work

All protected reads run through a short actor-locked RepeatableRead transaction, so authorization, rows, counts and summaries in one response share a snapshot. Current account changes serialize through P01's user lock protocol. Customer reads are shared; related draft/piece/command reads always add the owner predicate unless actor is ADMIN. ADMIN's wider read does not alter stored owner.

- Customer directory uses one filtered count, one 1–100-row page, one unfiltered `totalCustomers`, and one grouped query for draft counts/latest update over only page customer IDs and authorized drafts. Reuse the single filter for rows/counts; no per-customer query loop.
- Customer exact detail resolves by stable ID or canonical current phone; no first-customer/default fallback. Return full customer, scoped draftCount/latestDraftAt and latest provisional measurement. Submitted history is explicitly unavailable until P03; it has no fabricated count.
- Draft directory filters owner scope first, then optional customerId/type. `totalDrafts`/`totalPieces` aggregate that base scope; pagination total additionally applies search. Search covers literal name/phone/model and an exact syntactically valid draft UUID, not nonexistent business numbers. Page order `updatedAt DESC,id DESC`.
- Draft detail selects only permitted owner/header, current customer summary and active piece capture fields. It returns no receipt/hash/private credential or manufacturing/financial authority.
- Provisional measurements are active pieces with any nonnull size/A/F, joined to authorized drafts for the exact shared customer. Page order `draft.updatedAt DESC,draft.id DESC,piece.position ASC`; output calls the timestamp `draftUpdatedAt`, not an invented measurement capture time. Source is `DRAFT`, never approved.
- Global/per-draft activity queries committed draft operations only, joined to the currently authorized parent. Order `occurredAt DESC,commandId DESC`, default page1/25 max100. Output a bounded summary (header changed-field names, added/removed IDs, actual actor/time and versions), not full before/after paper JSON. Customer command history has no new UI/endpoint in P02.
- LIKE searches escape backslash/percent/underscore as literal input using each owning query's focused helper, following the existing staff query pattern. Phone search maps accepted Arabic digits/formatting and recognizes Saudi local/international prefix fragments; name/email matching keeps their own semantics. Do not treat an unparseable phone fragment as a selected customer.

Index and query count assumptions are design requirements, not measured performance claims. No new latency/throughput/SLA is asserted.

## 5. Migration, existing data and recovery

This is an additive P02 migration: no user approval/backfill, no modification of staff history, no catalog import and no browser-local fixture migration. Existing P01 rows, authority versions, credentials and migration checksums remain unchanged. New domain tables start empty. Add explicit User relations for draft ownership/command actor with Restrict; no CASCADE from User removal is introduced.

During later authorized implementation: inspect reviewed SQL, deploy all existing plus the one new migration into a fresh owned PostgreSQL target; separately upgrade an owned representative P01-populated target; compare existing rows/history and migration checksums; verify all new constraints/triggers/indexes; rerun deploy to verify no pending action. Do not run `db:push`, resets or seeds against a preserved target. Application order is additive DB, backend acceptance, then dependent UI; P03 may extend this model under its own plan.

Rollback/recovery before release is forward correction while preserving new customer/draft/audit data. A destructive downgrade that drops populated domain tables is not an accepted recovery. Target-specific backup/restore and production application remain OPS-01/P08 with separate authorization/evidence. This plan applies no migration to any target.

New FKs intentionally require a reviewed extension of the fixed owned-test cleanup graph. Update `apps/api/src/test-support/reset-test-data.ts` to include `sales_commands`, `sales_draft_pieces`, `sales_drafts`, `customers` in the same static TRUNCATE statement with the four existing tables, preserving NODE_ENV/test marker/URI/current_database guards and no CASCADE. Extend `reset-test-data.test.ts` and `.integration.test.ts`; update the fixed isolated cleanup owners in database integration suites where their User deletes would otherwise hit Restrict. No dynamic identifier discovery or wider unowned cleanup is permitted.

## 7. Customer draft card read amendment

OP-04A adds no persisted model/index/write. Reuse customers and owner/customer draft indexes, existing current-authority read transaction and active-piece ordering/200-piece invariant. `findCustomerDraftPage` counts scoped drafts then runs one parent findMany with nested bounded active-piece select (Prisma relation batching, never a loop of per-draft queries).
