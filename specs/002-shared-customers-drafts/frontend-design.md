## F02 — Identity Scope, Query Keys and Read Lifecycle

### One current scope

1. `readOperationalScope` reads the existing session Query state. Require `status==='success'`, `error===null`, successful `authUserDataSchema` parsing, `hasBusinessAccess(user)` and `user.role==='ADMIN' || user.department==='SALES'`. An errored cached session does not qualify.
2. Derive actor ID/accessVersion from that record and epoch from `getAuthSessionEpoch()`. Require restore policy `restore` and `assertAuthSessionSubject(actorId,epoch)`. Expected obsolete/identity/reauthentication errors mean no scope; unexpected exceptions propagate safely.
3. `isCurrentOperationalScope` repeats these checks and compares all three captured fields, not a stale render closure. `assertCurrentOperationalScope` throws Axios `CanceledError` if false. This helper owns only operation scoping: no second session, QueryClient, transport, token store or refresh mechanism.
4. Hooks use `useSession()`/`useOperationalScope()` only as subscriptions to that same owner. Without a scope, queries are disabled and private cached content is not rendered. Auth/account error/denial surfaces remain the existing protected-route behavior.
5. Before a read and after its awaited response, assert the captured scope; on a business denial await `reconcileBusinessDenial` with captured actor/epoch, then rethrow the original operation error. Every query's `structuralSharing(previous,incoming)` rechecks scope at commit; obsolete work returns `previous` without publishing incoming private data. Expected resource IDs/phone resolution and strict data schemas are checked before commit.
6. Detail merges compare the same stable target and record version: a lower incoming version cannot replace a newer cached customer/draft. Equal version may update current contact/count projections. List/history reads use validated same-query data with structural sharing; affected reads are cancelled around successful mutations before fresh invalidation, preventing pre-write replies from restoring old aggregates.
7. On scope change, cancel/remove only the captured old `['customer-drafts',actorId,accessVersion,epoch]` subtree after checking it differs from the current root. Never remove the current root in an old cleanup callback. The render gate hides old data synchronously, and a new epoch gives a distinct key even for the same actor/accessVersion. Existing auth identity-boundary cleanup is retained. A late settled mutation cannot publish, navigate, select a customer or display a notice under the new scope.

### Exact keys

`root(scope) = ['customer-drafts', scope.actorId, scope.accessVersion, scope.epoch]`. Epoch is the existing nonsecret lifecycle counter, included to separate same-actor reauthentication; it is also checked during execution and publication. Credentials never appear in keys. All keys are built in the named hook modules from canonical parsed query values; absent search is `''`, default page is `1`, default limit is `25`, absent type/customer filter is `null`.

| Reader                                         | Key appended to root                                  | Request                                   |
| ---------------------------------------------- | ----------------------------------------------------- | ----------------------------------------- |
| Shared directory                               | `['customers','list',search,page,limit]`              | `GET /customers`                          |
| Exact phone resolver                           | `['customers','phone',canonicalPhone]`                | `GET /customers/by-phone/:phone`          |
| Stable contact detail                          | `['customers','detail',customerId]`                   | `GET /customers/:customerId`              |
| Provisional measurements                       | `['customers','measurements',customerId,page,limit]`  | `GET /customers/:customerId/measurements` |
| Draft list, including dashboard/reached panels | `['drafts','list',search,type,customerId,page,limit]` | `GET /sales-drafts`                       |
| Stable draft detail                            | `['drafts','detail',draftId]`                         | `GET /sales-drafts/:draftId`              |
| One draft's change summaries                   | `['drafts','changes',draftId,page,limit]`             | `GET /sales-drafts/:draftId/changes`      |
| Scoped draft activity                          | `['drafts','activity',page,limit]`                    | `GET /sales-drafts/changes`               |
| Manual reconciliation                          | `['commands',commandId]`                              | `GET /sales-commands/:commandId`          |

Use the contract's UUID/phone/query schema before enabling a selected target. Invalid targets show safe validation/missing feedback; no fallback ID or first-customer lookup. Reader APIs forward `{signal}` to the existing Axios client. Normal reads inherit existing 30-second stale time/retry policy, have no cross-key placeholder data, and do not turn errors into `[]`. Changes/activity queries accept page/limit only, matching their existing surfaces; no search/type filter is silently discarded or invented. Manual receipt reads use `enabled:false`, `retry:false`, `staleTime:0`, `gcTime:0`; only the originating intent's explicit check/retry control dispatches them. Receipt data is never persisted in browser storage.

Search updates reset page to 1 and issue a bounded server query; abort superseded reads. Do not download all customers/drafts to run browser search/counts. A successful out-of-range page with `totalPages>0` moves to `totalPages` and refetches once; zero results keeps page 1 and the real empty state. Feed `OrientalTable.pagination` directly. Empty data, unavailable P03 data and read errors are three distinct states.

## F03 — Shared Write Intent, Receipt and Synchronization Protocol

### Frozen command shape

`SalesCommandIntent` is exactly one of:

- `{operation:'CREATE_CUSTOMER';body:CreateCustomerBody}`.
- `{operation:'UPDATE_CUSTOMER';customerId:string;body:UpdateCustomerBody}`.
- `{operation:'CREATE_DRAFT';body:CreateDraftBody}`.
- `{operation:'SAVE_DRAFT';draftId:string;body:SaveDraftBody}`.

The body contains the one `crypto.randomUUID()` commandId created at explicit submit, and the update's base `expectedVersion`. The form stores that immutable parsed intent plus original form-instance token and captured scope in memory until resolved. Mutation keys never include the command body, contact text, paper values or credentials. Read keys deliberately include their normalized search/phone selector, which is required to distinguish results; the Query cache is not persisted to browser storage. The API dispatcher sends the body only, not scope/UI state. No automatic mutation retry, new idempotency key on retry or localStorage autosave is permitted.

### Ordered mutation algorithm

1. Both top and sticky Save buttons call the same RHF `handleSubmit`; one synchronous form-intent ref blocks repeated click/Enter before React pending state updates. Validate the capture schema and current scope. Freeze parsed payload, command UUID, target/base version and submitted piece IDs.
2. `useSalesCommand` asserts captured scope before dispatch, cancels affected pre-write reads within that scope, and calls the one matching `customersApi`/`draftsApi` method. All four operations use this one concrete lifecycle; read hooks remain separate.
3. Parse the full envelope/data with existing `parseApiResponse` and the shared command schema. Verify returned `kind`, `receipt.operation`, `receipt.commandId` and `receipt.actor.id` against the frozen intent/scope; `receipt.resourceId` equals the `savedCustomer.id`/`savedDraft.id`, and update/save targets equal the submitted ID. Wrong/malformed result is `ApiContractError`, not confirmation.
4. The server after-image in `savedCustomer`/`savedDraft` is a receipt snapshot. It can be older on replay. Never overwrite a newer cache/form with it or represent it as a fresh read. Retain the confirmed result first, then invoke `synchronizeSalesCommand`.
5. Synchronization asserts scope before each publication, cancels affected reads, and fetches the current resource by stable ID with `staleTime:0`. Reuse each read hook module's exported `customerDetailOptions(queryClient:QueryClient,scope:OperationalScope,customerId:string)` or `draftDetailOptions(queryClient:QueryClient,scope:OperationalScope,draftId:string)` query-options builder, so explicit fetches and observers share one guarded query/merge owner. The returned current record must match the receipt resource and be no older than `receipt.afterVersion`. Publish through the monotonic detail owner, then invalidate affected active list/detail/history/summary queries with `{throwOnError:true}` and await completion. Repeat scope checks inside cache updaters and after awaited work.
6. On any skipped/undefined publication, unavailable scope or failed synchronization, throw `SalesSynchronizationError(result, safeErrorOrNull)`. The command is confirmed; keep the receipt and form. Show “تم الحفظ؛ تعذّر تحديث العرض” with a read-only refresh action. Do not issue the command again. One notice owner in the originating form prevents duplicate hook/toast announcements.
7. On successful current read/synchronization, only the still-mounted same form-instance/target/scope may reset its base values/version, close inline UI, select a customer, navigate or show saved success. Inputs are locked during pending/reconciling, so overlapping edits cannot be discarded. A closed form has no local callback; its current shared queries can still be reconciled under the same scope.
8. Non-confirmed denial invokes existing business-denial reconciliation. Validated 400/404/409 leaves persisted state unchanged and retains form input. Unknown write classifications are a network/lost response, 500–504 response or malformed success with no trusted receipt: retain the same frozen command and display uncertainty. A transport error is not rollback evidence.

### Intent state transitions

| State/event                                    | Next action and visible behavior                                                                                                                                     |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Editing → explicit save                        | Freeze one intent; pending state; disable all conflicting form/row/dialog saves                                                                                      |
| Definite validation/denial/not-found rejection | Keep entered values, show mapped error; unlock editing; no success or navigation                                                                                     |
| Customer/draft version conflict                | Retain input/base revision; show explicit reload/review; never auto-merge or silently resave                                                                         |
| Unknown outcome                                | Keep frozen intent; expose “التحقق من الحفظ”; allow leaving without claiming rollback; no automatic repeat                                                           |
| Manual receipt found                           | Retain receipt, then synchronize current stable resource; receipt replay does not repeat mutation                                                                    |
| Manual receipt 404                             | State remains unconfirmed because a concurrent transaction may still be running; offer explicit retry of the identical frozen body/commandId, not a new intent       |
| Confirmed write, refresh failed                | Retain `SalesSynchronizationError.result`; retry observation/synchronization only                                                                                    |
| Confirmed and synchronized                     | Reset matching form/base version and show one confirmed success; new paper save navigates via `router.replace(draftEditRoute(id))` to avoid another create on reload |
| Account/resource/form changed while pending    | Complete/observe only within captured allowed scope; no old result enters the new UI or selection                                                                    |

`synchronizeSalesCommand` invalidation scopes are fixed: customer command invalidates all customer directory/phone/detail entries and draft list/detail projections in the captured root because customer contact can be displayed there. Remove the old-phone resolver key when a confirmed update changes phone, then fetch the current stable ID. Draft command invalidates draft lists/detail/activity/changes plus customer directory/detail/measurement entries because link/measurements/counts may change. Broadly invalidating this bounded feature root is permitted; clearing the whole QueryClient is not. No cache update writes to the MVP provider.

## F04 — Customer Directory, Contact Forms and Inline Creation

### Directory/detail algorithm

1. Sales/admin directories call `useCustomerList({search,page,limit:25})` and render returned `customer.id`, scoped `draftCount`, real filtered pagination and `totalCustomers`. Existing name/email/phone/address cells and actions stay in place; email remains optional and searchable.
2. Phone route wrappers pass the actual route segment. Normalize with shared `normalizeSaudiCustomerPhone`; invalid/absent resolution has explicit missing feedback. `useCustomerByPhone` resolves one saved record, then the detail/editor fixes its stable ID for that mounted record. All subsequent reads/writes use `useCustomer(id)`.
3. Phone mutation/refetch cannot retarget a dirty editor to another customer who later acquired the old number. Keep the resolved stable ID, show the newer contact/conflict, and navigate to that record's current encoded phone after successful save. Unknown phone never selects the first result.
4. T029 customer-linked draft cards use the owner-authorized F10 `useCustomerDrafts` binding; generic summaries elsewhere retain `useDraftList({customerId:id,page,limit:25})`; provisional size history uses its separate bounded measurements query and `CustomerData.latestMeasurement`. Counts/latest values come from the same server scope; no `getCustomerSizeProfile(store.orders)` or browser counts. Labels say draft/provisional, never approved.
5. Retained admin customer rows that represent drafts link to existing `/sales/orders/:draftId` or its edit route; ADMIN already has cross-department access. Do not route real drafts into P08's local `AdminOrderDetailView`, implement an admin editor or expand admin cancellation/reopen scope.

### Contact form algorithm

Use `useZodForm` with `customerCaptureSchema`, deliberate defaults and existing Arabic/classes. Name/phone requiredness, optional null handling, normalized phone and bounds come from the shared owner. Render errors with associated labels/IDs and safe request ID in general feedback. Initial load mounts an editor only once the exact record is available; a missing record is not an empty editable form.

- Create builds `CreateCustomerBody` from parsed capture plus commandId. Update sends only supported dirty fields in `patch`, the fixed stable ID and original `expectedVersion`; an optional field explicitly emptied is included as null, omission preserves it. No-op edit performs no mutation and shows that no change was needed.
- Duplicate phone hints are advisory exact lookups; server conflict remains authority. On `CUSTOMER_PHONE_CONFLICT`, retain the form and resolve the submitted canonical phone to show the accessible actual customer. If it changed concurrently, retain duplicate feedback plus safe retry; do not invent duplicate data or auto-select. Duplicate email is warning-only and never blocks/merges.
- Ordinary background data does not call `reset` on a dirty form. Show newer-data notice; “reload/review” explicitly resets from a successful current detail read and loses local edits only on that chosen action. Confirmed save resets after F03 synchronization.
- Correct copy that calls phone an internal ID or promises to rewrite historical orders. Display stable customer ID separately if the existing ID badge remains, and state that relationships survive while submitted contact snapshots remain historical.

### Inline modal interface and sequence

Modify the retained `InlineCustomerModal` to accept `{onClose():void;onCreated(customer:CustomerDto):void;originScope:OperationalScope;originFormToken:object}`. It owns its RHF customer capture and calls the same `useSalesCommand` create operation; its parent retains the paper. The callback receives the confirmed resource after current-resource synchronization, not submitted text.

On success, verify the original form token/scope and read the validated synchronized `CustomerData` from `customerKeys.detail(scope, receipt.resourceId)`; a missing/wrong-target/older value is synchronization failure, not permission to use `savedCustomer` as current data. Pass that current customer to `onCreated`, set the paper's `customerId` to its stable ID, retain all paper values, close the modal and restore focus to the create-customer trigger. It does not save the paper. A duplicate result may show the existing customer with explicit “اختيار هذا العميل”; this action reads/selects that confirmed record without creating another one. Cancel/Escape/backdrop before dispatch closes/reset only the dialog, leaving selection/paper unchanged. While pending/unknown, the dialog cannot claim cancel/rollback; disable dismiss controls during the active dispatch and expose observation/retry as F03. A route/account departure never aborts a dispatched business write or calls an obsolete parent callback.

`SalesCustomerSection` becomes controlled with `search`, `onSearchChange`, `selectedCustomer:CustomerSummary|null`, `results:readonly CustomerSummary[]`, query state, `onSelect(customer)`, `onClear()` and `onCreateCustomer()`. Keep its current input/card/columns and add the needed keyboard-operable result choice within that surface. Typing invalidates the old selection unless text still represents it; names can produce several choices, so typed name text alone never supplies `customerId`. Clearing customer is allowed in a draft. Prefill query resolves an exact phone once; unmatched prefill stays unselected and shows feedback.
