# P02 Customer, Draft and Command Contracts

**Status**: Proposed producer/consumer contract, 2026-11-05. None of these domain endpoints/symbols exists yet. ## 1. Existing foundations and proposed owners

Reuse `@template/contracts` Zod 4.4.3, existing `successEnvelopeSchema`, `errorEnvelopeSchema`, `paginationMetaSchema`, `nonEmptyBoundedString`, `emailSchema` and account role/department schemas. Inspect actual exports in `packages/contracts/src/index.ts` when implementing. Existing API uses Express 5.2.1, Prisma 7.9.1/adapter-pg, configured `/api/v1`, central `ResponseHelper`, `validationMiddleware` and current-account guards. These values were source inspected, not execution tested here.

Proposed contract files and dependency direction:

1. `packages/contracts/src/sales-commands/command-receipt.schema.ts` owns only common receipt/actor schemas and inferred types; it imports existing account/http values, never customer/draft schemas.
2. `packages/contracts/src/sales-drafts/sales-draft-values.schema.ts` owns `salesOrderTypeSchema`/`SalesOrderType` and common draft scalar limits. It imports no customer schema.
3. `packages/contracts/src/customers/customers.schema.ts` owns customer input/read/command and provisional measurement shapes; it imports the two common value owners above.
4. `packages/contracts/src/sales-drafts/sales-drafts.schema.ts` owns draft input/read/command/activity shapes and imports customer summary plus common receipt/type values.
5. `packages/contracts/src/sales-commands/sales-commands.schema.ts` owns `salesCommandDataSchema`/`SalesCommandData`, the customer/draft result union. It imports both domain command schemas; those files do not import this union file. This avoids a circular schema graph.
6. `packages/contracts/src/index.ts` explicitly exports the intended schemas and types below. No Prisma/Express/Node crypto import belongs in any contract file. Extend the existing `http/http.schema.ts` with shared `paginationQueryFields` and pure `isSafePaginationWindow(value:Readonly<{page:number;limit:number}>):boolean`; new domain queries reuse them rather than copy parser defaults or import API code.

API DTO files alias shared schemas/types; they do not duplicate validation. OpenAPI operations are added to `apps/api/src/infrastructure/openapi/openapi.ts` using these same schemas. Web adapters use the existing central Axios client and validate unknown success envelope, then operation data. Invalid output becomes a safe contract failure via the existing centralized error owner; never a network/offline or empty-success fallback.

## 2. Values, normalization and technical bounds

These are technical safety bounds permitted by the spec, not new commercial capacity targets. Reject unknown fields at every object level. UUIDs are parsed with existing Zod `z.uuid()` convention and normalized lower-case. Versions are integers 1..2147483647. All instants are offset-aware ISO, emitted UTC; calendar dates are nullable `YYYY-MM-DD` real dates in years 0001..9999 with explicit leap-day validation and no host/browser timezone interpretation. Past dates are not rejected merely for being past.

### Saudi phone algorithm

Export proposed pure `normalizeSaudiCustomerPhone(value: string): string | null` from the customer schema owner and `customerPhoneSchema` using it. Convert U+0660–0669/U+06F0–06F9 to ASCII, strip whitespace/hyphens/parentheses, then accept exactly one of national leading `0`, `+966` or `00966`. Remove that one prefix only. National portion must match `(?:5[013-9][0-9]{7}|1[123467][0-9]{7})`; output `+966` plus that portion. Do not repeatedly strip zeroes, accept bare country-code/national-without-trunk forms, or infer foreign countries/extensions. Empty/letters/multiple prefixes/incorrect length/short codes are invalid.

This is an explicit ordinary Saudi contact-number shape, not subscriber allocation, reachability or possession verification. No new phone library/provider is needed for these bounded transforms. Geographic codes/national examples are documented by [CST](https://www.cst.gov.sa/en/about/Numbering); mobile network-code forms were checked in the [stc reference offer](https://www.stc.com.sa/content/dam/corporatesite/common/individual/pdf/Reference-Offer-of-Saudi-Telecom-Company-stc-Nxx-Number-Ranges-of-stc-Exchanges.pdf). Changes to national numbering metadata require a narrow validation amendment/regression, not silently wider country scope. No more than these format facts are derived from those sources.

Search treats phone fragments separately: convert supported digit scripts/formatting; when a fragment begins with `+966`/`00966`, compare its canonical prefix; a local fragment beginning `0` and containing further digits compares without that trunk zero. Keep a lone `0` literal, rather than turn it into match-all. Name/email search is literal case-insensitive substring; percent/underscore/backslash are escaped. A search result is never an implicit selected customer.

## 3. Schemas and DTOs

All response objects are strict, have all documented keys (nullable means present with null), and use `z.infer` output types. Public raw aliases use `z.input<typeof schema>` to preserve nullable/blank form input separately from normalized command output. No endpoint returns raw database records.

### Customer shapes

- `customerCaptureSchema` → `CustomerCapture` / `CustomerCaptureInput`: `{name,phone,email?,address?,notes?}` with normalization above; optional fields default to null in output. Used by new-customer and inline forms.
- `customerPatchSchema` → `CustomerPatch`: any nonempty subset of name/phone/email/address/notes. Omitted remains omitted; optional blank/null clears, required name/phone cannot clear. Reject empty object.
- `createCustomerBodySchema` → `CreateCustomerBody`: `{commandId:UUID,customer:CustomerCapture}`.
- `updateCustomerBodySchema` → `UpdateCustomerBody`: `{commandId:UUID,expectedVersion:Version,patch:CustomerPatch}`.
- `customerSummarySchema` → `CustomerSummary`: `{id:UUID,name,phone,email:nullable,address:nullable}`. No notes/revisions/credentials in a selection summary.
- `customerSchema` → `CustomerDto`: `{id,name,phone,email,address,notes,version,createdAt,updatedAt}`.
- `customerListQuerySchema` → `CustomerListQuery` / `CustomerListQueryInput`: `{search?,page?,limit?}`.
- `customerListDataSchema` → `CustomerListData`: `{customers:[{customer:CustomerSummary,draftCount:nonnegativeInt,lastDraftAt:ISO|null}],pagination:PaginationMeta,totalCustomers:nonnegativeInt}`. `pagination.total` uses search; totalCustomers counts the shared directory without search. Each related count is actor-scoped.
- `customerParamsSchema` → `CustomerParams`: `{customerId:UUID}`; `customerPhoneParamsSchema` → `CustomerPhoneParams`: `{phone:canonicalPhone}` after decoding the path once through Express and applying phone schema. Encode canonical phone in URL; do not double-decode.
- `customerMeasurementsQuerySchema` → `CustomerMeasurementsQuery` / `CustomerMeasurementsQueryInput`: `{page?,limit?}`.
- `customerMeasurementSchema` → `CustomerMeasurement`: `{draftId:UUID,pieceId:UUID,owner:{id,fullName},type:SalesOrderType,model:string|null,size:string|null,aField:string|null,fField:string|null,draftUpdatedAt:ISO,source:'DRAFT'}`. Include only active rows with at least one of size/A/F nonnull.
- `customerMeasurementsDataSchema` → `CustomerMeasurementsData`: `{measurements:CustomerMeasurement[],pagination}`; scope and order follow data-model §4.
- `customerDataSchema` → `CustomerData`: `{customer:CustomerDto,draftCount,latestDraftAt:ISO|null,latestMeasurement:CustomerMeasurement|null,submittedHistory:{availability:'not_available',reason:'P03_NOT_IMPLEMENTED'}}`. Latest measurement is first under the same defined sort, not an approved measurement or a fabricated recording time.

### Draft captures and reads

`draftPieceCaptureSchema` → `DraftPieceCapture` / input: `{id:UUID,model?,size?,leatherBase?,decoration?,decorationColor?,faceRight?,faceLeft?,mixing?,face?,sole?,soleAddition?,soleColor?,additions?,aField?,fField?,sideNotes?}`. All capture fields normalize to present nullable values; id is required. No prices, quantity, position, lifecycle or privileged fields accepted.

`draftCaptureSchema` → `DraftCapture` / `DraftCaptureInput`:

- Required `type:SalesOrderType`, `pieces:DraftPieceCapture[]`.
- Nullable `customerId:UUID`, `deliveryDate:calendarDate`, `generalNotes`, `responsibleSignature`, `repairNote`, `adjustmentRequested`, `adjustmentReason`, `adjustmentActionTaken`, `paidAmount`.
- On creation/raw form input, these nullable fields and individual nullable piece captures may be omitted and default to null. Full normalized output has every editable key.
- `draftReplacementSchema` has the same normalized `DraftCapture` output but requires every header and piece-capture key in raw input, each explicitly null/string as appropriate. This fixes PUT omission semantics; a frontend mapper sends the complete parsed form object. No hidden type-specific value is silently deleted when type changes.

`createDraftBodySchema` → `CreateDraftBody`: `{commandId:UUID,draft:DraftCapture}`. `saveDraftBodySchema` → `SaveDraftBody`: `{commandId:UUID,expectedVersion:Version,draft:draftReplacementSchema}`.

`draftPieceSchema` → `DraftPieceDto`: `{id,position:positiveInt,quantity:1,...all nullable piece captures}`. `draftSchema` → `DraftDto`: `{id,version,status:'DRAFT',owner:{id,fullName},type,customer:CustomerSummary|null,deliveryDate,generalNotes,responsibleSignature,repairNote,adjustmentRequested,adjustmentReason,adjustmentActionTaken,paidAmount,pieces:DraftPieceDto[],createdAt,updatedAt,pricing:{availability:'unavailable',reason:'P03_NOT_IMPLEMENTED'},submission:{available:false,reason:'P03_NOT_READY'}}`. No business number/authoritative total exists.

`draftDataSchema` → `DraftData`: `{draft:DraftDto}`. `draftSummarySchema` → `DraftSummary`: draft identity/version/status/owner/type/customer/deliveryDate/createdAt/updatedAt plus `pieceCount`, pricing and submission objects; omit capture notes/signature/paid/pieces. `draftListQuerySchema` → `DraftListQuery` / input: `{search?,type?:SalesOrderType,customerId?:UUID,page?,limit?}`. `draftListDataSchema` → `DraftListData`: `{drafts:DraftSummary[],pagination,totalDrafts,totalPieces}`. Aggregate totals apply authority/customerId/type, excluding text search/page; pagination totals also apply search. Order `updatedAt DESC,id DESC`. Search covers literal customer name/phone/model and exact UUID. A supplied absent customer filter returns `CUSTOMER_NOT_FOUND`, not all drafts.

`draftParamsSchema` → `DraftParams`: `{draftId:UUID}`. `draftChangesQuerySchema` → `DraftChangesQuery` / `DraftChangesQueryInput`: `{page?,limit?}` raw, canonical numeric page/limit output. Current activity has no filters, so no new filter workflow is added. `draftChangeSchema`: `{commandId,operation:'CREATE_DRAFT'|'SAVE_DRAFT',draftId,actor:SalesCommandActor,occurredAt,beforeVersion:Version|null,afterVersion:Version,changedFields:string[],addedPieceIds:UUID[],removedPieceIds:UUID[]}`. changedFields is a subset of header names plus literal `pieces` (at most11 entries), never an unbounded field-per-cell list. ID arrays max200. `draftChangesDataSchema` → `DraftChangesData`: `{changes:DraftChange[],pagination}`. Global/per-draft rows use current parent ownership; history remains a recorded save, not manufactured progress. No global activity search/type filter is introduced because current activity has neither. No full before/after PII blob is returned by list endpoints.

### Command results

`SalesCommandActor` / `salesCommandActorSchema`: `{id:UUID,fullName:string,role:'USER'|'ADMIN',department:existingDepartment|null}`; employee is SALES, ADMIN records its actual context. `SalesCommandReceipt` / `salesCommandReceiptSchema`: `{commandId,operation:fourOperationEnum,resourceId:UUID,actor:SalesCommandActor,beforeVersion:Version|null,afterVersion:Version,occurredAt:ISO}`.

- `customerCommandDataSchema` → `CustomerCommandData`: `{kind:'customer',receipt:SalesCommandReceipt,replayed:boolean,savedCustomer:CustomerDto}` with customer operation/ID/version consistency refinements.
- `draftCommandDataSchema` → `DraftCommandData`: `{kind:'draft',receipt,replayed:boolean,savedDraft:DraftDto}` with draft operation/ID/version consistency refinements.
- `salesCommandDataSchema` → `SalesCommandData`: the discriminated `kind` union above.
- `salesCommandParamsSchema` → `SalesCommandParams`: `{commandId:UUID}`; `salesEmptyQuerySchema`: strict empty object for single-resource reads and writes.

The saved resource is the exact committed after-image. A later replay/receipt read may contain an older version; its naming and receipt make this explicit. Client must refetch the current GET resource after confirming a receipt and handle any newer data without overwriting dirty input. `replayed:false` means first effective write; true means returned retained result (including GET receipt); it never claims the image is latest.

## 5. Authority, errors, binding and unknown outcomes

Sales see shared contacts and only their own draft-related rows/counts/activity/measurements; ADMIN sees broader data. Never return another salesperson's draft after loading by unscoped ID. Customer phone routes are compatibility resolvers to stable ID; edit navigation uses the saved current phone. Old phones have no permanent alias and cannot detach links. Actual actor/name/time/owner and pricing/readiness constants are server-derived.

| HTTP / code                                                | Meaning and unchanged-state rule                                                                                                                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400 `VALIDATION_ERROR`                                     | Shared schema failure (including duplicate request piece IDs, >200 rows, >256KiB normalized capture, required null, unsupported authority); known field paths e.g. `body.draft.pieces.0.size`; no write |
| 400 `INVALID_JSON`                                         | Proposed bounded correction: known parser `entity.parse.failed`/status400; safe fixed message, no raw body/stack                                                                                        |
| 413 `PAYLOAD_TOO_LARGE`                                    | Proposed bounded correction: known parser `entity.too.large`/status413 at existing global body limit; safe fixed message, no raw body/stack                                                             |
| 401 `UNAUTHORIZED`                                         | Existing missing/invalid identity behavior                                                                                                                                                              |
| 403 `ACCOUNT_RESTRICTED` / `DEPARTMENT_ACCESS_DENIED`      | Existing current P01 restriction/department denial                                                                                                                                                      |
| 404 `CUSTOMER_NOT_FOUND`                                   | Exact customer missing, including supplied create/save relation; do not silently discard relation                                                                                                       |

Error messages use fixed bounded safe text; UI maps stable codes to existing Arabic feedback. `AppError` subclasses live with the corresponding customers/drafts/sales-command domain; CSRF/rate/session codes remain their existing owner. Do not insert custom `existingCustomer`/receipt objects into the existing strict error envelope. Phone duplicate resolution uses a separately authorized GET and explicit selection.

The parser correction modifies existing `apps/api/src/middlewares/error-handler.middleware.ts` and adds `HTTP_STATUS.PAYLOAD_TOO_LARGE=413` in existing constants. Source inspection found that current parser errors otherwise fall through to generic500. Recognize an `Error` object with the exact known `type` and numeric status pair, construct a fresh safe operational AppError without raw cause/body, and omit stack in these two responses even in development. Operational logging receives only the fresh safe classification/requestId, never the parser object. Preserve all other existing AppError/Prisma mappings. Installed body-parser2.3.0/read.js and raw-body3.0.2/index.js confirm these type/status pairs. This is proposed shared-boundary correction, not an already installed capability.

### Canonical command binding

Compute server SHA-256 with Node `createHash` in the API executor owner, never contracts/browser. Construct JSON by an explicit fixed field order:

1. `{operation,targetId,expectedVersion,payload}`; create target/version are null; actorId and commandId are separately bound columns.
2. Customer creation payload contains normalized name/phone/email/address/notes in that order. Patch contains only supplied keys in name/phone/email/address/notes order; omitted differs from explicit clear.
3. Draft payload contains every canonical DraftCapture header in the order defined above followed by pieces; every piece is id then the declared capture keys in fixed order. Array order is material; null is explicit; no undefined/property-spread order is allowed.
4. Thus equivalent phone/email formatting or paid decimal spelling parses to the same intent; changing piece UUID/order or a significant nonblank catalog/text character is a changed intent. Do not hash raw request JSON, current customer values or response timestamps.

A transaction-scoped commandId advisory lock is acquired after the actor lock and before receipt lookup/domain work, with exact key/SQL/timeouts fixed in data-model §3. This prevents same-intent competitors failing a domain uniqueness/CAS check before they see the receipt. Replay checks binding before calling operation work and returns its immutable after-image with no new effect/evidence. This remains true if a later command advanced the current record. Receipt observation always rechecks current actor and resource scope. A connection error can occur after commit; keep the bound command+input, observe receipt, then current GET. If no receipt is visible, the same bound command may be resent; never regenerate commandId for an uncertain action. New IDs are generated only for a new deliberate action after success/reconciliation or explicit stale-data review. A confirmed receipt plus failed refetch is synchronization failure, not failed persistence.

Current validation middleware stores parsed values as `unknown`; current staff controller uses a parsed-body assertion. A failure here is an internal wiring/contract error, not a second client validation response.
