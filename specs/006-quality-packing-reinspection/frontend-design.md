# P06 frontend design

This is a proposed technical blueprint for [the P06 specification](spec.md), not implemented behavior or executed acceptance. The canonical wire ledger is [contracts/quality.md](contracts/quality.md); it owns every shared schema, field, limit, endpoint, discriminator and error code. Do not copy a second wire definition into this document or frontend code. The [backend design](backend-design.md) owns authoritative transitions, transaction/replay behavior and P04/P05 participation. Backend implementation, review and real database/HTTP acceptance must complete before dependent frontend wiring.

All source paths in this document are relative to `apps/web/src/` unless prefixed otherwise. New files/symbols and new branches described below are **proposed**. Existing owners were inspected during PLAN. Later TASKS must give each implementation task an exact bounded brief referring to these sections; this document creates no task list or implementation authorization.

## F01. Inspected baseline, boundaries and preserved surfaces

- `features/manufacturing/screens/quality-workspace.tsx` currently reads browser-local orders/events and calls local receipt/inspection operations with fixed actors. It reaches quantity inspection and shared tables, while the per-piece modal reaches a separate local action. No quality consumer may keep a fixture fallback after conversion.
- `quality-inspection-dialog.tsx` currently captures optional carton count/reference text and inspector note, with quantity split and required rejection reason/instructions. `quality-inspect-piece-modal.tsx` offers accept/reject and rejection notes but no packing controls. Preserve that distinction; remove demonstration defaults rather than recording them.
- The current quantity callback stores latest order-level packing values. The per-piece rejection replaces its previous object. Both are migration inputs, not a history model to reproduce.
- Shared `DepartmentOrderTable`, `DepartmentPieceTable`, `DepartmentOrderCard`, `DepartmentPieceActions`, `DepartmentBatchActions` and dashboard/task/order owners already contain closed P05 persisted branches and legacy quality/warehouse branches. Add explicitly typed quality branches; keep P05 and warehouse contracts and behavior intact. Do not broaden `ManufacturingDepartment`, construct a fake `MvpOrder`, or force quality data through P05 visit types.
- The legacy task view declares but never consumes quality's `onStartWork` callback. New quality task actions call the real quality command owner directly, including recording inspection results. An invalid task reference never selects the first available piece.
- The quality detail legacy branch renders full paper/print links. Replace only that data/action branch with `FactoryOrderPaper` and safe tracking/history; quality employees receive no official finance-bearing print link or permission.
- Quality accepted/correction views must query retained department participation after pieces leave quality. Do not derive their source orders by filtering only pieces currently in quality. Removed special operations is not an accepted target.
- Keep Arabic/RTL/Cairo, all existing quality routes/aliases, navigation, headers, four KPI cards, grouped/flat views, expansion, selection, table/dialog classes, specification/tracking/history tabs and paper layout. Only necessary functional/privacy/state changes below are planned. There is no new screen, warehouse UI conversion, provider, upload, PDF service, alternate transport, QueryClient or state store.

Read before dependent edits: root/web `AGENTS.md`, constitution VIII/XI, engineering frontend §§1–9, contracts §§2–7, security authority/errors, testing and code-review guides, this document, the canonical contracts and the affected current component/callers. Existing application foundations remain owned by their earlier phases.

## F03. API parsing, target/result binding and request behavior

`qualityApi` uses existing `apiClient`, `parseApiResponse` and `ApiContractError`. Reads/observation accept optional `AbortSignal`; commands do not receive a cancellation signal that might be misrepresented as rollback. Paths below are relative to the existing configured API prefix.

| Method signature                                                                                         | Transport and canonical data schema                                                                       |
| -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `dashboard(signal?): Promise<QualityDashboardData>`                                                      | GET `/quality/dashboard`, `qualityDashboardDataSchema`                                                    |
| `orders(query: QualityOrdersQueryInput, signal?): Promise<QualityOrdersData>`                            | GET `/quality/orders`, parsed `qualityOrdersQuerySchema`, `qualityOrdersDataSchema`                       |
| `pieces(query: QualityPiecesQueryInput, signal?): Promise<QualityPiecesData>`                            | GET `/quality/pieces`, parsed `qualityPiecesQuerySchema`, `qualityPiecesDataSchema`                       |
| `order(orderId: string, signal?): Promise<QualityOrderData>`                                             | GET `/quality/orders/:orderId`, `salesUuidSchema`, `qualityOrderDataSchema`                               |
| `activity(query: QualityActivityQueryInput, signal?): Promise<QualityActivityData>`                      | GET `/quality/activity`, `qualityActivityQuerySchema`, `qualityActivityDataSchema`                        |
| `orderHistory(orderId, query: QualityOrderHistoryQueryInput, signal?): Promise<QualityOrderHistoryData>` | GET `/quality/orders/:orderId/history`, `qualityOrderHistoryQuerySchema`, `qualityOrderHistoryDataSchema` |
| `command(body: QualityCommandBody): Promise<QualityCommandData>`                                         | POST `/quality/commands`, `qualityCommandBodySchema`, `qualityCommandDataSchema`                          |
| `observe(commandId: string, signal?): Promise<QualityCommandData>`                                       | GET `/quality-commands/:commandId`, `salesUuidSchema`, `qualityCommandDataSchema`                         |

For each successful response: treat `response.data` as unknown, parse envelope then exact data, bind department/target/view/page/limit to the request, and only then return. Detail binds `paper.order.id`; history binds requested order and optional piece filter; a filtered pieces page cannot contain another requested order. Canonical schemas enforce unique complete context membership and safe nested outputs. A malformed/mismatched success throws `ApiContractError`; never convert it into empty data, zero counts or a confirmed action.

A piece-filtered order history returns original per-order event payloads containing that piece, including complete decision/member/packing groups. Bind **event contains requested piece**, not every event member equals it. Do not truncate another accepted member from a retained inspection group, rewrite carton membership or manufacture a smaller event to fit the filter. Same-order safe context is already authorized.

`bindQualityCommandResult` compares distinct sets rather than array positions. Bind kind, command ID, operation, actor ID when supplied, order membership, before versions, operation-specific after versions, exact selected piece membership and each input decision/target to its canonical outcome. REPORT_ISSUES advances each order by its selected piece count under the shared P04 writer; other quality operations advance it once. Bind visit/correction/issue/packing identities as required by the canonical operation. An INSPECT result must neither change a requested ACCEPT into REJECT nor report another target. A receipt from another actor/operation/order cannot confirm this intent. Observation for an in-memory unknown command applies that same immutable original-intent binding. Post-reload observation-only history mode has no reconstructed body and binds the requested command, current actor and returned schema instead; it cannot submit or retry any write.

## F04. Current scope, exact query keys and publication

`QualityOperationalScope = OperationalScope & Readonly<{department: 'QUALITY'}>`. Proposed scope functions take `(client: QueryClient)` and return `QualityOperationalScope | null`; current/assert functions take `(client, scope)`. `qualityScopeKey(scope)` returns `['p06', actorId, accessVersion, epoch]`.

1. Use the existing successful error-free parsed session, `hasBusinessAccess`, current auth subject, restore policy and epoch through the existing scope owner's business-session reader.
2. Permit active QUALITY employees or ADMIN. Route/name supplied by a caller is not permission. `useQualityOperationalScope()` subscribes to the existing `useSession`; no session context or token persistence is added.
3. After actor/accessVersion/epoch becomes obsolete, cancel old prefix queries; for each retained query call `query.reset()` to notify mounted disabled observers, then remove it only if the same query object remains empty and the old scope is still obsolete. This includes command-session/receipt observers; mere removal must not leave their private result rendered.
4. Normal route/filter/task navigation with the same current identity is not an access boundary and never clears the command slot. Recheck scope before dispatch, after awaited work and inside manual publication/structural sharing. An old subject's result cannot recreate its removed data.
5. On recognized `ACCOUNT_RESTRICTED` or `DEPARTMENT_ACCESS_DENIED`, call existing `reconcileBusinessDenial(client, error, scope)`, then recheck scope. Read and observation paths require this, not only POST. A transient quality read error cannot sign a user out or publish an anonymous session.

Let `R = qualityScopeKey(scope)`. Canonical parsed inputs, including defaults, form every key:

| Resource            | Exact key suffix after `R`                                                   |
| ------------------- | ---------------------------------------------------------------------------- |
| dashboard           | `['dashboard']`                                                              |
| grouped orders      | `['orders', view, search ?? '', type ?? null, page, limit]`                  |
| flat pieces         | `['pieces', view, search ?? '', type ?? null, orderId ?? null, page, limit]` |
| detail              | `['order', orderId]`                                                         |
| activity            | `['activity', page, limit]`                                                  |
| order history       | `['order-history', orderId, pieceId ?? null, page, limit]`                   |
| command session     | `['command-session']`                                                        |
| command observation | `['command-receipt', commandId ?? null]`                                     |

Normal reads inherit the existing 30-second freshness and at most two allowed network/500–504 retries; `ApiContractError` and cancellation do not qualify for retry. A null list input uses an inactive key and `skipToken`; no absent scope starts a request or displays old data. No previous-account/filter placeholder data is published. Pass Query's abort signal into the adapter.

`qualityOrderOptions` validates the ID, asserts current scope in the query function and structural-sharing callback, validates incoming/previous detail, and retains a newer same-order root version over a delayed older result. `fetchQualityOrder` uses `fetchQuery({...options, staleTime: 0})`, rechecks scope, then parses and returns the **published cache value**, not the older transport value that `fetchQuery` can resolve with despite structural sharing. This is required by confirmation preparation.

List/dashboard/history publication revalidates the canonical schema and fixed QUALITY context before `replaceEqualDeep`. Matching detail/summary versions are required to expand/select group pieces. A mismatch renders stale/review feedback and blocks actions, never silently rebases expected versions. Out-of-range list/history pages move to `max(1,totalPages)` with an explicit fresh destination read; total zero remains an honest empty result with zero pages. No unsupported sort/date/worker controls are added.

## F05. Safe view models and exact selection preparation

`QualityPieceTarget` is readonly `{orderId: string; expectedVersion: number; pieceId: string}`. `QualityWorkRow` is readonly `{key, target, order, piece, work}`, where `order` is the canonical safe quality header, `piece` is the canonical safe factory piece and `work` is the canonical `QualityPieceContext`. `key = orderId + '/' + pieceId` is display identity only; do not split it to construct a command.

`QualityWorkGroup` contains the captured safe order header, exact matching piece IDs and readonly rows. `QualityGroupDetailState` is loading/error/ready/refreshing with nullable group/failure; `QualitySelectionPresentation` is empty/loading/error/stale/ready. Error/stale variants expose no actionable rows. These are presentation types, not a second authoritative quantity model.

The pure exported signatures are `toQualityRows(data: QualityPiecesData): readonly QualityWorkRow[]`, `resolveQualityTargets(data: QualityOrderData, targets: readonly QualityPieceTarget[]): readonly QualityWorkRow[]`, `toQualityGroup(summary: QualityOrderSummary, data: QualityOrderData): QualityWorkGroup`, `freezeQualityRows(rows: readonly QualityWorkRow[]): readonly QualityWorkRow[]`, `toQualityWorkSummary(row: QualityWorkRow): string`, `toQualityTracking(data: QualityOrderData): AuthoritativeOrderTracking`, and `toQualityRail(data: QualityOrderData): QualityRailProjection`. The existing tracking type is a type-only import from `features/sales/model/order-view.model.ts`. `QualityRailProjection` has the same safe rail count/status shape as the existing projection with `currentDepartment: 'QUALITY'`; this is a local presentation type, not a shared contract extension.

Pure models:

- `toQualityRows(data: QualityPiecesData)` maps every validated row without filtering IDs or reading local state.
- `resolveQualityTargets(data: QualityOrderData, targets: readonly QualityPieceTarget[])` requires a nonempty distinct set for that exact order/version, complete physical-piece/context membership and no substitute. A single mismatch rejects the whole supplied selection. It returns safe rows only.
- `toQualityGroup(summary: QualityOrderSummary, data)` verifies version and exact matching membership through the resolver; never fabricate a list DTO to reuse a mapper.
- `freezeQualityRows(rows)` deep clones/freezes the resolved safe selection. Confirmation owns this snapshot independently of later query refreshes.
- `captureQualitySelection(operation, rows)` validates canonical allowed-action hints, current requested visit where applicable, distinct IDs, coherent per-order versions, maximum total selection and canonical strict command shape; sorts order/piece IDs deterministically and returns canonical base `orders`. It never filters ineligible rows or splits one intended operation into several requests.
- `toQualityWorkSummary(row)` describes current incoming/inspection, current correction location/reinspection, accepted handoff, blocked/cancelled and historical-only contexts distinctly. Retained rejection history alone is not an open correction. Missing actors/times are displayed as unrecorded rather than guessed.
- `toQualityTracking(data)` produces the existing `AuthoritativeOrderTracking` directly from safe physical pieces/counts; `ready` derives only from active > 0 and physically received === active. `toQualityRail(data)` counts stable uncancelled pieces by actual stage and uses the canonical current quality context, not generic historical rejection flags. `QualityRailProjection` is a presentation overload with QUALITY current department; it does not widen P05 wire types.

Preparation algorithm shared by queue, group, piece and task actions:

1. Require current scope, idle command slot, no preparation in flight and a live initiating UI context. Capture exact target objects, initiating element and a preparation token. Set busy state before any await.
2. Accept only explicitly selected current-page rows/groups. Grouped display uses page size 10, expansion demands at most those 10 groups; flat display uses page size 100. Canonical contracts still cap grouped queries at 25, flat at 100 and commands at 200 physical pieces. Reject oversize whole selection; never clip it or auto-submit chunks.
3. Fetch each demanded detail fresh. Use at most 10 concurrent detail requests; if a flat selection spans more than 10 orders, process sorted blocks of 10 until all demanded details are obtained or one fails. Do not load every order globally or issue unbounded Promise.all. Cancellation/context change abandons preparation, not an already issued command.
4. Resolve every captured target against its published authoritative detail and captured expected version. Require exact cardinality before allowed-action validation. Missing, changed, duplicate, foreign or ineligible members stop the whole preparation with review guidance. Existing expected versions cannot be replaced automatically with newly fetched versions.
5. Only if scope, mounted state, route/filter/page token, original selected set and preparation token are still current and the command slot remains idle, publish immutable confirmation rows. A delayed preparation cannot open a dialog for another selection.
6. Keep selection when a later refresh makes it stale; show stale/error and require explicit review/clear. Changing route/filter/mode/page intentionally clears page selection/expansion and unsent confirmation; warn that unsent input is being discarded if dirty. No write is issued by a selection change.

Task selection uses internal order ID in the route and optional `pieceId`; legacy `itemId` may alias the same exact piece only when equal. A legacy `segmentId` must identify a retained quality visit for the supplied piece; malformed, inconsistent, absent or foreign visit membership shows an unavailable task. With no piece/visit parameter, show existing order task context and explicit piece links; issue no implicit action. Never use first-piece/first-segment fallback. A historical visit can be read but never authorizes a current downstream action.

## F06. One command slot, known failure and uncertain result

All operations, including REPORT_ISSUES, use `QualityCommandBody` through one POST and one quality receipt. The browser never loops over P04 per-piece report POSTs. The sole slot key is `R + ['command-session']`; subscribe through a disabled `useQuery` with `skipToken` and `gcTime: Infinity`. It is in-memory QueryClient state, not localStorage/sessionStorage. It survives dialog close and quality route navigation; reload recovery uses activity/receipt observation.

The proposed `QualityCommandState` is a closed discriminated union:

| phase        | Retained values / permitted operation                                                                                 |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| idle         | No intent/result; a new explicit submit may acquire the slot                                                          |
| pending      | Frozen origin scope and exact canonical body; no second submit                                                        |
| unknown      | Same origin/body and safe failure; explicit observe or retry identical body/ID                                        |
| confirmed    | Same origin/body and validated canonical result, optional synchronization failure; retry display synchronization only |
| synchronized | Same origin/body/result; user or still-live initiating confirmation may acknowledge                                   |

The session schema validates body/data, actor/context, command/operation and result bindings on every read; unexpected local state is an invariant failure, not permission to clear unknown work. The mutation uses `retry: false`, `gcTime: 0`. A hook's transient mutation cleanup resets its local observer state only; never clear the shared pending/unknown/confirmed slot on unmount.

`useQualityCommand()` returns `{state, submit(body): Promise<QualityCommandData>, observe(): Promise<void>, retrySame(): Promise<void>, synchronize(): Promise<void>, acknowledge(): void}`. Algorithms:

1. `submit`: recheck scope and idle slot immediately, parse/deep-freeze exact body, acquire pending slot before network dispatch; generate `crypto.randomUUID()` once at explicit valid confirmation, never during render/query/preparation. Preserve captured versions/decisions/text for every retry.
2. On valid result, bind it to original intent/scope, publish confirmed before refreshing any view, then run F09. Successful refresh publishes synchronized. Saving succeeded even if display refresh fails; throw `QualitySynchronizationError` carrying result and safe refresh error, without resending POST.
3. A known noncommitting 4xx validation/eligibility/version/access failure returns pending to idle only if the exact same pending entry remains. Retain safe form data; conflicts require review. Never clear a newer slot. Reconcile recognized account denial before any further scoped work.
4. A network/no-response/server/contract/recognized uncertain-transaction failure publishes unknown with the same immutable body. `isUnknownQualityWrite` follows canonical code classification; it does not call every 409 unknown. Local validation/busy/invariant and synchronization errors are not unknown saves.
5. `observe` explicitly refetches disabled receipt query (`retry:false`, `staleTime:0`, `gcTime:0`), binds result to original body/scope, publishes confirmed and synchronizes. A 404 or observation error preserves unknown: absence of a receipt is not proof that the original action failed.
6. `retrySame` is offered only for unknown and only by explicit user action. Publish pending and send exactly the original body/ID; never recapture versions or modify text. A retry failure remains unknown even when a replay path cannot establish the old outcome. No automatic polling or automatic POST retry is introduced.
7. `synchronize` requires confirmed; `acknowledge` requires synchronized. Reset the exact slot Query object to notify subscribers before conditional removal. Stale callbacks may not clear current work.

UI callbacks after await separately check the current mounted/route/resource/dialog snapshot before clearing form/selection or acknowledging. A callback from an unmounted old queue/task cannot acknowledge the globally synchronized result; its destination recovery notice stays until explicit acknowledgment. React StrictMode cleanup/replay follows the same live token rule.

`QualityCommandRecovery` appears on dashboard, queues, activity, task and order details. Pending states explain that closing does not cancel. Unknown shows original operation and exact selected order/piece summary, observation and identical retry actions. Confirmed-needs-refresh states distinguish saved work from stale display. Synchronized is a persisted-success notice with acknowledge. One component owns the success notice; hooks and toasts do not announce it again.

After a full reload no in-memory intent is reconstructed or retried. Activity paginates department history using page/limit only, with no actor filter or new filter widget. Offer original-result observation only on returned quality events whose actual `event.actor.id === scope.actorId`, using that exact event's `commandId`. That read-only mode validates command ID, current actor and canonical result without requiring a frozen body that no longer exists; it never constructs a POST or exposes a retry-write button. Display absence as inconclusive. Old-account activity observations are aborted/ignored and cannot announce another actor's result.
