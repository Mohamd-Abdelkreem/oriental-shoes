## F01. Capability scope and one session owner

Existing `OperationalScope` is `{actorId,accessVersion,epoch}` and `readOperationalScope` only admits SALES/ADMIN. Existing `useCatalog`, sales/customer keys and command hooks depend on that restriction. Do not broaden its default or repurpose the sales command result union.

Inside the same `shared/query/operational-scope.ts`, extract private `readBusinessSessionScope(client: QueryClient): {scope: OperationalScope; user: SafeUser} | null` from the existing session-status/schema/business-access/epoch/restore-policy/subject checks. Existing exports continue calling that helper followed by their unchanged SALES/ADMIN check. No new session cache, token store, auth provider or global authorization source is introduced.

Add these proposed public symbols in that owner:

- `P04Capability = "APPROVAL" | "SALES_CONTACT" | "OFFICIAL_PAPER"`.
- `P04OperationalScope = OperationalScope & Readonly<{capability: P04Capability}>`.
- `readP04OperationalScope(client: QueryClient, capability: P04Capability): P04OperationalScope | null`.
- `isCurrentP04OperationalScope(client: QueryClient, scope: P04OperationalScope): boolean` and `assertCurrentP04OperationalScope(client, scope): void`, where failed assertion throws the existing Axios `CanceledError` class.
- `useP04OperationalScope(capability: P04Capability): P04OperationalScope | null` and `p04ScopeKey(scope: P04OperationalScope): readonly ["p04", P04Capability, string, number, number]`.

APPROVAL admits eligible ADMIN/APPROVAL employees; SALES_CONTACT reads admit eligible ADMIN/SALES employees; OFFICIAL_PAPER admits eligible ADMIN/SALES/APPROVAL. Contact submission requires immutable owner equality plus eligible SALES employee or eligible ADMIN and server `canSubmitContact`; an ADMIN reading another owner's work gains no on-behalf response. Scope is UI eligibility/correlation, not a server authorization guarantee.

`useP04OperationalScope` observes the existing `useSession` and captures capability plus actor/accessVersion/epoch. Its cleanup cancels/removes only `p04ScopeKey(captured)` when that exact tuple ceases to be current. Await cancellation, recheck obsolescence before removal and never remove a replacement capability tuple. Existing sales cleanup stays unchanged. The new helpers are necessary because existing current-scope checks intentionally reject approval-only accounts; share private identity extraction, not duplicate credential logic.

For captured P04 command-session queries, removal must also notify a still-mounted subscriber in the other capability. After cancellation and the obsolescence recheck, enumerate only queries under the captured prefix whose exact tail is `['command-session',orderId]`. For each captured Query object, call its public synchronous `reset()` with no initialData, then remove that exact key only if the captured scope is still obsolete, cache lookup still returns the same Query object and its data remains undefined. Do not await between reset/recheck/removal. Remove remaining obsolete read queries with a predicate excluding command-session tails, so a replacement preserved by the exact guard cannot be deleted by a later broad removal. Keep this small cache-shape cleanup in `operational-scope.ts`, without a shared-to-feature import or a new store; apply the current-scope check before publishing any recovered session.

Every API completion, structural-sharing callback, cache publication, form completion callback and command transition checks the captured P04 scope. For direct API calls outside a hook the caller owns this check. Call existing `reconcileBusinessDenial(client,error,scope)` for ACCOUNT_RESTRICTED/DEPARTMENT_ACCESS_DENIED; preserve its same-actor/epoch checks and session error behavior. A generic network/read error never becomes successful anonymous state.

## F03. Commands, uncertainty and synchronization

### Exact frontend command interfaces

Proposed `ApprovalCommandIntent` in `approval-command-state.ts` is a readonly discriminated union over APPROVE_INITIAL, RETURN_INITIAL, RESOLVE_ISSUE, SUBMIT_CONTACT and REVIEW_CONTACT. Each variant contains `operation`, `orderId`, applicable `pieceId`/`issueId` and its exact shared `body`. REVIEW_CONTACT body retains the current `proposalId`; SUBMIT_CONTACT body is the AMEND/CANCEL_REQUEST discriminated union. REPORT_ISSUE is reserved to the contract/backend and is not dispatched by these P04 screens.

Define `ApprovalCommandCapability = "APPROVAL" | "SALES_CONTACT"` and `ApprovalCommandScope = P04OperationalScope & Readonly<{capability:ApprovalCommandCapability}>` in `approval-command-state.ts`. `ApprovalCommandVariables = Readonly<{scope: ApprovalCommandScope; command: ApprovalCommandIntent}>`. The fixed operation mapping is SUBMIT_CONTACT → SALES_CONTACT; APPROVE_INITIAL, RETURN_INITIAL, RESOLVE_ISSUE and REVIEW_CONTACT → APPROVAL. OFFICIAL_PAPER and REPORT_ISSUE cannot enter this hook. Capability is local correlation metadata, never a request field, server authority or receipt/URL/database change.

`ApprovalSynchronizationError` extends Error and carries confirmed `ApprovalCommandData` plus safe `ApiError | null`. `isUnknownApprovalWrite(error: unknown): boolean` treats contract-malformed success, no transport status, 500–504 and `APPROVAL_TRANSACTION_CONFLICT` as uncertain; safe 400/401/403/404/other known 409 precondition rejection is definitive unless the same frozen command was already uncertain. `APPROVAL_COMMAND_CONFLICT` after uncertainty remains observation-required, not permission to create a replacement key. The explicit 503 `ORDER_CATALOG_UNAVAILABLE` is a definitive no-write validation/readiness result when no prior uncertainty exists; retain input and retry catalog/read review rather than claiming an unknown submission. Local busy, capability-mismatch and recovery-invariant errors occur before transport and are never classified as uncertain server writes.

Proposed `useApprovalCommand(orderId: string, capability: ApprovalCommandCapability)` returns `{state,submit(command),observe(),retrySame(),synchronize(),acknowledge()}`. The required capability describes this view's new actions; it never reclassifies a recovered command. `state` is a typed discriminated `ApprovalCommandState` whose exact phase values are `idle`, `pending`, `unknown`, `confirmed` and `synchronized`; `confirmed` means persisted metadata retained but current synchronization is pending/failed. Every non-idle variant retains `originScope:ApprovalCommandScope` and the frozen command; confirmed/synchronized variants also retain the parsed result. Unknown retains its safe failure context, confirmed its optional safe synchronization error. Form editing remains RHF state, not a sixth command phase. `submit(command:ApprovalCommandIntent):Promise<ApprovalCommandData>` resolves only after confirmed synchronization and throws definitive/unknown/synchronization errors for the owning form to handle. `observe()`, `retrySame()` and `synchronize()` return `Promise<void>`; `acknowledge():void` is allowed only after synchronized success. The hook owns the low-level `useMutation` and shared `retry:false`; components do not dispatch ad hoc POST requests.

T026's `useApprovalCommandReceipt(commandId: string | null, originScope: ApprovalCommandScope | null)` is the sole manual receipt query hook. Its exact key is `[...p04ScopeKey(originScope),'command-receipt',commandId]`, using a disabled empty/epoch -1 sentinel when either input is absent or invalid. It never infers scope from the current screen or ADMIN role. Even manual refetch must validate ID/current origin scope before transport and again before publication, then correlate receipt command ID, actor ID and operation's mapped capability; orchestration additionally checks the full frozen order/version/child binding. The command hook mounts this observer at its top level for the selected session; `observe()` refetches that bound observer rather than calling a React Hook inside a callback. `synchronizeApprovalCommand(client: QueryClient,scope: ApprovalCommandScope,result: ApprovalCommandData): Promise<void>` receives that same retained origin scope.

Maintain one occupied local command slot per actor/accessVersion/epoch/order across APPROVAL and SALES_CONTACT. A QueryClient recovery entry at `[...p04ScopeKey(originScope),'command-session',orderId]` holds only originScope, immutable submitted command/body, command ID, confirmed metadata if any and phase. Each hook subscribes to both exact command-session keys for its current identity tuple, with `queryFn:skipToken`, `enabled:false`, `gcTime:Infinity` and no initialData; the installed `@tanstack/react-query` exports skipToken and these memory-only queries never perform a request. Select the one existing non-idle session whose stored origin scope remains current and whose operation maps to that capability. ADMIN navigating between eligible views therefore observes the same entry. An existing synchronized entry also occupies the slot until acknowledgment. No entry means idle; do not persist an idle placeholder as an occupied command.

The two-key selector and synchronous reservation belong only to `approval-commands.hooks.ts`; there is no second cache, mutable global lock map or separate command registry. Before dispatch, validate the requested view capability/operation and current tuple, inspect both exact keys, then insert pending into the mapped origin key synchronously, with no await or mutation dispatch between inspection and insertion. An occupied slot gives local busy without changing either entry or sending a POST. If two valid entries or inconsistent stored bindings are encountered, fail closed with a local invariant error: no automatic selection/merge, new write, replay, synchronization or acknowledgment. Surface that local error through the existing error boundary/general-error pattern; it does not add a command phase. Unissued local UUIDs created by form shaping are not accepted intents and cannot replace recovery state.

Recovery methods always re-read the exact stored origin key and command ID before action and after every await. `retrySame` may transition only that unknown session to pending synchronously before dispatch, so two subscribed views cannot concurrently start retries. Acknowledge and definitive no-write failure use one private synchronous clear helper in `approval-commands.hooks.ts`: find the exact origin Query through `client.getQueryCache().find({queryKey:originKey,exact:true})`, verify the matching command ID/permitted phase, call its public `reset():void` to notify both observers of empty data, then remove that exact key only if lookup still returns the captured Query object and its data remains undefined. There is no await or transport in this sequence. Acknowledge requires synchronized; definitive-failure cleanup applies only before uncertainty and preserves RHF input. A replacement inserted during reset/notification is preserved by the identity/data guard. Plain removeQueries alone is insufficient because the installed QueryCache removal does not dispatch an empty result to QueryObservers. ### Ordered submission algorithm

1. Open from a canonical wrapper and capture scope/order version, selected issue ID/current proposal ID and the relevant allowed-action hint. Keep identity/version outside editable RHF fields. A stale row must load current detail before authoring.
2. After local form validation, shape one UUID-bearing command through its shared body schema. `submit` requires its order ID to equal the hook order and its operation to match the explicit requested capability, rechecks current scope and scans both exact current-tuple session keys. No occupied slot may be replaced, including one originating in the other capability.
3. Freeze canonical body/path IDs/originScope/operation and insert pending synchronously before the first await or `mutateAsync`. Disable conflicting buttons/Enter/nested confirmation and dispatch one API method. No optimistic stage, cancellation or price update is published.
4. Parse/correlate receipt command ID/operation/order/actor/beforeVersion/afterVersion and expected piece/issue/proposal outcome. For a new accepted command, afterVersion is expectedVersion+1. A replay is still that original effect, not a claim that the returned outcome is current state.
5. On a confirmed result set confirmed-needs-sync before fetching. Synchronize current projection. Only after successful synchronization may the owning screen show success/close/navigate; one component owns its toast/notice.
6. If a recognized definitive validation/permission/state/version failure occurs before uncertainty, keep form values and show safe field/general errors; clear the frozen command only after recording the failure. A conflict requires explicit current-data review before a newly numbered intent. Never silently update captured base version under dirty input.
7. If a write may have committed, set unknown, keep exact frozen intent and show observation plus explicit same-intent retry. A missing receipt is not proof of failure. Do not clear entered text or create another command ID to get around uncertainty.
8. If confirmed persistence succeeded but refresh failed, retain confirmed metadata and show “saved; current view could not be refreshed.” Only synchronization/read retry is offered; never repeat the write. Closing/unmounting does not erase this result or claim rollback.
9. Every continuation checks current capability/actor/accessVersion/epoch, selected order and stored command ID before updating recovery, cache, error, navigation or toast. Obsolete completions may not repopulate current state. Scope loss removes private recovery entries through F01.

### Observation/retry algorithm

`observe()` uses T026's receipt hook with the selected session's exact captured command ID and originScope, then checks operation/order/actor/version/selected resource correlation. If found, transition to confirmed-needs-sync and synchronize; no write occurs. If receipt is absent or read fails, retain unknown and safe context; an explicit `retrySame()` reuses identical operation/path/body/ID/originScope, allowing the server to return the one committed receipt or enforce the original preconditions. Repeated unknown then changed-payload/state failure never authorizes a new command until the original outcome is reconciled. After synchronized success `acknowledge()` removes only the matching origin entry and releases the shared same-order slot across both capabilities.

### Synchronization algorithm

Cancel only in-scope P04 reads before fresh publication; check the retained origin scope after cancellation. Fetch the current wrapper through `approvalOrderOptions` for approval actions or `salesContactOrderOptions` for owner contact submission, using the stored operation/originScope even if observation was initiated on the other view; force staleTime 0. Validate both received and actually published root version are at least receipt.afterVersion; a higher current version is valid. Current wrapper, not receipt outcome, determines displayed actions/counts/print state.

Invalidate affected P04 dashboard/orders/issues/history/order-history/event and current contact-list/detail prefixes for the same actor/session where those capabilities are currently eligible. For SALES/ADMIN current sales scope, also invalidate existing `customerKeys.root(salesScope)` so order/editor/tracking/activity/customer histories/paid projection reconcile through existing owners. Do not construct an approval actor's forbidden sales key or clear the whole cache. Invalidate/remove official-paper entries for this order immediately because current eligibility may have changed. Await active invalidations with `throwOnError:true` when the UI would otherwise announce a fully refreshed success. Wrap failed refresh as `ApprovalSynchronizationError`; retain confirmed command.
