## Shared command protocol

### Identity, authority and replay

`ApprovalCommandExecution` is a discriminated six-operation union with common `{operation,actorId:string,commandId:string,orderId:string,expectedVersion:number,payloadHash:string,work(tx:Prisma.TransactionClient,actor:AuthorityAccount,occurredAt:Date):Promise<ApprovalCommandWorkResult>}`. Initial operations have no selected child target; REPORT adds pieceId; RESOLVE/SUBMIT add pieceId+issueId; REVIEW adds pieceId+issueId+proposalId (from body). `ApprovalCommandHashIntent` has the same operation/selected-target/version binding and exact corresponding parsed body with commandId omitted from payload hashing. Canonical hashing includes all request-selected IDs and expectedVersion plus parsed intent; sort the four change keys in model/size/leatherBase/sole order, preserve omission versus sole=null and normalize optional notes through the shared schema. Never hash generated result issue/proposal IDs. `ApprovalCommandWorkResult` is `{pieceId:string|null,issueId:string|null,proposalId:string|null,decision:ApprovalDecision|null,decisionNotes:string|null,beforeFacts:ApprovalEventFacts,afterFacts:ApprovalEventFacts,outcome:ApprovalCommandOutcome}`. The strict contract owns ApprovalDecision's operation-compatible literals. No credentials/raw request object enter facts/diagnostics.

| Operation                                                         | Current authority for new execution/replayed write                                                                                                                                       |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| APPROVE_INITIAL / RETURN_INITIAL / RESOLVE_ISSUE / REVIEW_CONTACT | `assertBusinessAuthority(actor,Department.APPROVAL)`; ADMIN bypass is already inside that helper                                                                                         |
| REPORT_ISSUE                                                      | `assertBusinessAuthority(actor)` then current CUTTING/PRODUCTION/QUALITY department matched to persisted source stage; ADMIN may report actual source without choosing a fake department |
| SUBMIT_CONTACT                                                    | `assertBusinessAuthority(actor,Department.SALES)` **and actor.id===root.ownerId**; ADMIN has no on-behalf response exemption                                                             |

The metadata-only `observe` read requires current operation-compatible business authority and command.actorId===actor.id. For retained REPORT_ISSUE, require current eligible ADMIN or current employee department equal the immutable issue's retained sourceDepartment; normal movement of the piece is allowed, but later reassignment to another department is not. Other operations require current APPROVAL or SALES/ADMIN authority and their current order/owner relation according to the table. It exposes no order/customer/proposal values and grants no current resource/detail access. Other actors, including another ADMIN, cannot observe the receipt by guessing its ID.

### Ordered transaction algorithm

1. Reuse the existing database client; open ReadCommitted transaction with maxWait 5000ms, timeout 10000ms, local lock_timeout 5000ms. There is no network/file/mail work inside it.
2. `lockAccountRows(tx,[actorId],"read")`, load current identity and enforce the per-operation authority above. Account locks serialize relevant authority changes; retained history is never revalidated against an actor's future department.
3. Acquire transaction advisory lock using the established SHA-256→signed64 pattern over `p04-approval-command:${commandId}`. The namespace/table differs from P02 sales commands deliberately; do not change that accepted protocol.
4. Read ApprovalCommand by commandId. Compare actor/operation/orderId/expectedVersion/payloadHash and request-selected child targets only: pieceId for REPORT; pieceId+issueId for RESOLVE/SUBMIT; pieceId+issueId+proposalId for REVIEW. REPORT has no caller issueId and SUBMIT has no caller proposalId, so never compare a missing input slot against its generated stored result ID; recover that identity from the stored outcome. Enforce current operation-compatible receipt authority, including retained sourceDepartment for report recovery. A binding mismatch is `APPROVAL_COMMAND_CONFLICT`; exact replay returns identical receipt/outcome with replayed=true, no business work/root/history change and no full savedOrder.
5. For a new command, create one server occurredAt. `lockApprovalOrder` locks the submitted `sales_drafts` root FOR UPDATE using an actor-safe scope. Missing/foreign roots are `ORDER_NOT_FOUND`; load current bounded SALES_ORDER_SELECT plus target sidecars inside the same transaction. Require expectedVersion=root.version and root.version<2147483647, otherwise `ORDER_VERSION_CONFLICT`.
6. Execute the operation-specific algorithm below. It changes only its allowed fields and calls the shared `this.advanceApprovalOrderVersion(tx,{orderId,expectedVersion,occurredAt})` exactly once. That helper performs conditional updateMany `{id,status:'SUBMITTED',version:expectedVersion}` → version+1/updatedAt and requires affectedRows=1. No second version clock, separate piece version or double bump is added.
7. Map bounded before/after facts and final outcome against the contract, then INSERT one ApprovalCommand with exact identity/hash/versions/operation/actor/target/decision fields and snapshots. Root/state/issue/proposal/history commit together; deferred graph checks run at commit. A command with rolled-back work leaves no receipt.
8. Parse metadata-only response using `approvalCommandDataSchema` and return HTTP200 after commit. It contains kind/receipt/replayed/outcome only, no money/contact/raw snapshots. Clients separately read current projections; historical receipt afterVersion is a synchronization floor, not a current full-order cache value.

Lock order is actor account rows (ascending helper ordering) → command advisory lock → root row → existing issue/proposal row when required → active catalog SHARE lock only for contact submission. Root serialization also coordinates P03 resubmit/paid operations, whose existing services lock the same root. Never lock/modify another actor account to impersonate contact ownership.

Map recognized lock timeout to `APPROVAL_TRANSACTION_CONFLICT`. Permit at most one complete safe retry for existing recognized P2034 or unique commandId contention, preserving original parsed intent and identity; recheck current authority/root eligibility on retry. Do not retry arbitrary unique/check/FK errors or unknown connectivity/commit errors. Missing response is unknown to the browser; actor-only observe resolves committed result, or exact same intent retry is offered after checking no result. Changed/stale intent requires explicit new review, not automatic mutation replay.

## B01 Initial approval and return

**Requirements**: FR-001–007, SC-001/005. Inputs are strict current order version plus commandId; return adds nonblank reason<=4000 and optional notes<=4000. Initial approval does not accept browser piece lists/actors/target/time.

1. Under shared protocol/root lock, require header AWAITING_APPROVAL, approvedAt null and no retained APPROVE_INITIAL event. Every retained physical piece must be active AWAITING_APPROVAL/INCOMING with no issue/receipt/cancellation. Broken persisted graphs are safe internal defects, not silently omitted pieces.
2. Capture beforeFacts/current counts/money. APPROVE sets header status APPROVED and approvedAt=occurredAt; clears return-proof fields defensively only if already null by pending-state checks. Update all expected piece IDs to CUTTING/INCOMING with count equal active count. Do not create identities/movements claiming receipt/start, skip repair cutting or modify price/customer/number/paper fields.
3. RETURN changes header to RETURNED, sets currentReturnDecisionId=commandId, currentReturnOrderVersion=expectedVersion+1, currentReturnReason=reason and currentReturnedAt=occurredAt. Pieces remain unreleased. Optional notes remain separate in afterFacts.currentReturn; do not concatenate two bounded strings into the header reason.
4. Advance root version once; retain actual decision/history and final facts. New-transition SQL binds the actual return/approval witness. `readCurrentOrderReturnProof` stays unchanged and returns the authoritative current P03 resubmit proof; later P03 resubmit clears it and awaits approval under the same original number/terms.

**Verification**: New `apps/api/src/modules/approval/approval.service.integration.test.ts` exercises all seven order types, actual return→P03 correction/resubmit→approve, optional-note round trip and unchanged price/customer/number. Real independent connections race approve/return from one version; exactly one outcome/event/version/release survives. Inject a controlled database failure after piece update/before event insert and inspect full rollback. Existing P03 resubmission tests remain scoped consumer evidence; actual P04 acceptance uses this service.

## B02 Report manufacturing issue

**Requirements**: FR-008–009, SC-002/005. Input reason nonblank<=4000 and optional notes<=4000; actor/source/time/issue ID are server-owned.

1. Require header APPROVED, selected piece in this root, stage CUTTING/PRODUCTION/QUALITY, workState INCOMING or IN_PROGRESS, receivedAt/cancelledAt/issueId null. Map stage to actual source Department; a non-ADMIN actor must belong to it. Wrong current department is denied; stale/noneligible piece is state conflict. Future P05/P06 callers invoke this same boundary.
2. Read highest retained issue cycle for this piece under the root lock and allocate next positive Int with overflow rejection; create new issue id server-side, APPROVAL_REVIEW state, exact source/reporter/reason/notes/time. A partial unique open-piece index independently prevents duplicate unresolved issues.
3. Set only this physical piece workState BLOCKED and issueId=newIssue.id, preserving its source stage/current work and all other pieces. Do not create order-wide returned status, manufacturing receipt or completion.
4. Advance root, retain REPORT_ISSUE event/facts/outcome, commit. A distinct new legitimate issue after a resolved cycle creates a new retained row rather than overwriting old source data.

**Verification**: Service/HTTP cases for source matches in all three departments, ADMIN actual-source recording, denied sales/foreign department, stale/received/cancelled/missing/foreign piece, duplicate concurrent reports and a subsequent cycle. Verify unaffected companion can still be read as continuing and all financial/private data absent from factory command response. Real state/receipt/event rollback is asserted.

## B03 Resolve issue A/B/C

**Requirements**: FR-010–015, SC-002/004/005. Require current issue APPROVAL_REVIEW, matching piece.currentIssue pointer, source-stage BLOCKED piece, current expected root version and approval/ADMIN. A/B require explicit CUTTING or PRODUCTION target and nonblank decision notes; C requires cancellation confirmation and nonblank reason, forbidding target. Exact branch schema is contract-owned.

1. Load current issue/proposal/source and capture beforeFacts; do not infer a target from source department.
2. A (`RETURN_TO_DEPARTMENT`): set issue RESOLVED with resolutionCommandId/time and retain chosen resumeTarget; clear piece.issueId; set stage to target/workState INCOMING. Work receipt/start/completion remain future department actions. No captured specification changes.
3. B (`SEND_TO_SALES`): set issue SALES_CONTACT and resumeTarget=explicit target; keep source stage/BLOCKED/pointer. Required instructions are retained in the event's decisionNotes. Owner is the stable root.ownerId; no reassignment/platform or fabricated sales action. Initial referral before a submitted proposal does not itself create the pending-reapproval print hold.
4. C (`CANCEL`): call focused `this.cancelIssuePiece(tx,{root,pieceId,issueId,reason,commandId,occurredAt})`. Reject dispatched/delivered order or receipt/nonmanufacturing/ineligible piece. Set selected piece CANCELLED/BLOCKED/cancelledAt/reason, clear current pointer and resolve issue; never removedAt/delete the base piece. Recompute header total from remaining frozen prices with existing exact money helpers. Preserve paid. If no active piece remains set header CANCELLED, otherwise preserve APPROVED. Counts/progress derive existing retained pieces; no refund/receipt/delivery action.
5. Advance root once, record event/facts/outcome. Latest instructions are obtained by one indexed batch join to retained B or review-return events, not a mutable competing instructions store.

**Verification**: Each A/B/C, source/target/required-text/confirmation errors, cross-order issue denial, old issue resolution versus current cycle, one-piece isolation and retry/cancellation once. Exact example total3300/paid2000 → cancel1500 → total1800/paid2000/due0/surplus200. Full cancellation yields zero active/completion0, retained paid/history. Race C with P03 paid update; winner version invalidates loser and a reviewed retry preserves both intended changes without lost paid.

## B04 Submit customer-contact response

**Requirements**: FR-016–019/022, SC-003/005. Only the actual recorded owner with current SALES/ADMIN authority may respond; ADMIN cannot act for another owner. Issue must be SALES_CONTACT with retained target and selected held piece/current pointer. Input is AMEND with nonblank contactNotes and a strict sparse four-key CatalogEntry ID map, or CANCEL_REQUEST with notes and no changes.

1. Capture beforeFacts and load current four approved labels plus existing nullable selection IDs. Preserve required retained nonblank labels even when a prior optional reference is absent. Every nonnull reference must match its exact field/label; a contradictory record is an internal defect, never a first-option/default lookup.
2. AMEND: obtain active catalog SHARE lock only if changed IDs need validation. Omitted keys retain original IDs/labels, including unchanged retained source records. Explicit sole=null clears floor; required model/size/base cannot be null. Supplied new IDs must match their exact field kind/current active source and yield original-language displayValue. Empty changes map is valid notes-only confirmation. Never read quote/rate or change decoration/customer/frozen terms.
3. Insert immutable full resolved proposal before/proposed labels and nullable IDs, owner notes/identity/time, new sequence/id and submitting commandId. CANCEL_REQUEST has no proposed values. Store submitted response, not approved piece data; keep stage/source/BLOCKED/current pointer unchanged.
4. Set issue.latestProposalId and REAPPROVAL; retain target. Advance root once, record command facts/outcome. Any submitted response/request begins whole-order print hold; return to sales later retains that proposal pointer/hold.

**Verification**: Four permitted fields, notes-only, explicit floor clear, required clears/prohibited decoration/middle floor addition/customer/paid/membership rejects, exact source language/kinds, inactive/unknown entry and missing catalog on a changed selection, unchanged retained values without activation. Verify no current capture/price/total/cancellation/resume changes, actual owner enforcement including other-owner ADMIN denial and eligible owner-ADMIN acceptance, stale/duplicate responses and unknown-result observation. SQL rollback after proposal insert leaves no pointer/event/orphan.

## B05 Review customer-contact response

**Requirements**: FR-019–023, SC-003/005/006. Approval/ADMIN only; root expected version, current issue REAPPROVAL and requested proposalId===issue.latestProposalId; same piece/issue/order/source-stage BLOCKED pointer and retained target. Required review notes are nonblank<=4000.

1. Load immutable latest proposal, exact prior/proposed catalog records and current approved four fields. Verify its before values still equal current approved fields; a mismatched saved graph cannot be silently rebased. Capture beforeFacts.
2. ACCEPT is valid only for AMEND. Do not reprice, re-read active catalog or substitute newer options. `this.applyContactProposal(tx,{proposal,occurredAt})` updates exactly the selected base row's model/size/leatherBase/sole and updatedAt using retained proposed labels; update/delete/create only those four selection rows, preserving omitted/null retained references without fabricated IDs. It never calls broad `writeDraftCapture`, changes another row/header or touches decoration/other selection keys. Original source strings remain exact. Resolve issue with command/time, clear pointer and set retained target/INCOMING. Notes-only acceptance still creates the explicit positive release decision.
3. RETURN_TO_SALES keeps stage/BLOCKED/current pointer, target and latestProposalId, changes issue SALES_CONTACT and records required instructions. Prior proposal stays immutable. Owner may submit a fresh proposal/cancellation request; no automatic old-spec restore/resume occurs and print hold persists.
4. CANCEL uses exactly B03's retained cancellation helper. It works for AMEND or CANCEL_REQUEST and never applies unapproved proposed data. CANCEL_REQUEST cannot be accepted to resume; approval must cancel or return it for more contact.
5. Advance root once, retain review event/facts/outcome and commit. Print eligibility is recomputed from all current issues; one resolved review cannot clear another pending/recontact cycle.

**Verification**: Real contact→return→resubmit→accept and contact→cancel cycles, both request kinds, stale proposal ID/root version, wrong owner/department, target preserved, no automatic restore, approved four-field exactness, source activation change between submit/approval without new pricing, cancellation proposal never applied. Controlled failure after capture/selection update rolls back capture/issue/piece/root/event. Companion state/prices remain identical.

## B06 Reads, histories and safe projections

### Read transaction and authority

Use RepeatableRead transactions with the same maxWait/timeout/lock-timeout policy and current account SHARE lock. Bounded row/count reads share one snapshot. Read operations may safely retry once on recognized transaction conflict, never convert errors into empty data. Central `authorizeDepartments` is the route boundary; service checks current authority/resource again. Factory financial/private projection is selected before response, not hidden by JSX/CSS.

`getOrder` requires current approval/ADMIN. `getSalesContactOrder` requires owner SALES or ADMIN broader read; both use the same internally scoped current-order projection helper. orderHistory/event permit approval/ADMIN across submitted orders or actual owner SALES for its own order. Missing/foreign resources are not-found without identity leakage. dashboard/listPending/listIssues/own history require approval/ADMIN. salesContacts retains owner scope for ordinary sales; ADMIN may read broader contact context but cannot submit on behalf. officialPaper permits approval/ADMIN or owner SALES. Factory order read is allowed if at least one current piece stage matches the actor's CUTTING/PRODUCTION/QUALITY department or an unresolved issue retains that sourceDepartment; ADMIN retains broader safe reads. This relation authorizes whole existing factory-safe order/pieces/counts/tracking, not a misleading subset percentage. Mutation still requires the selected current-department piece. Warehouse pages remain P07; no factory finance/private contact access is added.

### Current reads and bounded selection

ApprovalOrderData wraps current SalesOrderDto plus workflow `{initialApproval,currentReturn,allowedActions,printEligibility,issues}`. Reuse current SALES_ORDER_SELECT, add one batch of <=200 open issues with latest immutable proposal and retained before/proposed CatalogEntry records, actual initial approval event and matching current return notes. The original submitted paper is not rewritten merely to display a pending proposal. Current issue instructions derive from the latest B/review-return command with `decisionNotes`, actor/time; batch by issue IDs, no one-query-per-row loop.

ManufacturingIssueSummary and full issue DTO use the same pure action-hint rules `{canResolve,canSubmitContact,canReviewContact}` with current actor, immutable ownerId, current issue state/pointer and latest proposal. Queue selection already includes owning root context; map hints without separate per-row identity/permission requests. Hints cannot grant authority and never enable an ADMIN response for another owner. Initial RETURNED sales detail reads the P04 currentReturn wrapper even when no manufacturing issues exist, so optional review notes remain visible alongside the existing P03 reason/proof.

Pending rows filter submitted roots/header AWAITING_APPROVAL; issue queues can show all unresolved states or the explicitly selected state, while sales contacts show SALES_CONTACT/REAPPROVAL under owner scope. Counts and rows share accepted type/search/state filters. Parse existing page/limit rules (default25/max100); pending orders sort root.updatedAt DESC/id DESC, issue/contact queues sort reportedAt DESC/id DESC, and histories sort occurredAt DESC/commandId DESC. Use existing total/zero/out-of-range pagination helpers. Dashboard is bounded aggregates: approvedToday counts all actual APPROVE_INITIAL events during the configured business-calendar day, while returnedOrders counts distinct current RETURNED roots without a today filter. Own history stays actor-specific. For approvedToday bounds parameterize controlled nowInstant and validated zone: start=`date_trunc('day',nowInstant AT TIME ZONE zone) AT TIME ZONE zone`, end=`(date_trunc('day',nowInstant AT TIME ZONE zone)+interval '1 day') AT TIME ZONE zone`; compare occurredAt>=start AND <end. Reuse existing parseOrderBusinessTimeZone/OrderCalendarUnavailableError; there is no existing day-range helper to invent. Absent/invalid calendar yields `ORDER_CALENDAR_UNAVAILABLE` for dashboard only; commands remain independent. Source query/index ownership is data-model.md and contract filters.

### Histories and event detail

Proposed `apps/api/src/modules/sales-orders/order-activity.queries.ts` exports `findOrderActivity(tx,scope:OrderActivityScope,query,orderId?):Promise<SalesOrderActivityData>`, with trusted scope `{kind:'OWNER',ownerId}` or `{kind:'APPROVAL'}`. Order by occurredAt DESC/eventId DESC/kind ASC, including IDs that collide across the two command namespaces. Retrieve only the bounded page's detailed event projections; do not load unbounded JSON snapshots to page in JavaScript.

Existing `findSalesOrderActivity` remains a wrapper that supplies OWNER for ordinary sales or APPROVAL for ADMIN. Add `kind:'approval'` to SalesActivityItem without changing existing order/draft event or P03 full-revision contracts. Own approval history filters actorId=current actor and operation APPROVE_INITIAL/RETURN_INITIAL/RESOLVE_ISSUE/REVIEW_CONTACT; it excludes factory reports and sales contact submissions from “my decisions.” Authorized order history includes all relevant actual actors. Event detail requires both event.orderId=selected order and authorized current resource scope and projects typed ApprovalEventFacts only; factory callers cannot fetch raw/private event detail. Historical actor snapshots never become current permission.

### Official and factory paper

Official eligibility requires actual retained APPROVE_INITIAL witness matching approvedAt, a permitted postapproval header state and no current pending contact cycle: issue.state SALES_CONTACT or REAPPROVAL **and** latestProposalId nonnull.
