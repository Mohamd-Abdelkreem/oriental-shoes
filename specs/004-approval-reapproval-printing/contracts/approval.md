# P04 HTTP and executable-contract design

This is a proposed interface ledger for [P04](../spec.md), not implemented routes or executed evidence. [Backend design](../backend-design.md) owns algorithms/transactions; [data model](../data-model.md) owns persistence; [frontend design](../frontend-design.md) owns query/form behavior. All URLs below are relative to the existing configured `/api/v1` prefix.

## 1. Existing boundaries and permitted extensions

- Reuse `successEnvelopeSchema`, `paginationMetaSchema`, `paginationQueryFields`, `isSafePaginationWindow`, `nonEmptyBoundedString`, `salesUuidSchema`, `salesVersionSchema`, `salesInstantSchema`, current account enums and existing response/validation/error owners. Installed contracts manifest records Zod `4.4.3`; no dependency change is proposed.
- Preserve `salesOrderSchema`, `salesOrderCommandDataSchema`, `salesCommandReceiptSchema`, `salesCommandActorSchema`, `SalesCommandExecutor` and previously retained P02/P03 command snapshots. They encode sales-only command authority and full historical order projections. P04 must not weaken their actor restrictions or parse approval facts as old order snapshots.
- Create browser-safe `packages/contracts/src/approval/approval-command.schema.ts` for receipt/outcome; `approval-event.schema.ts` for safe event summaries; `approval.schema.ts` for bodies, queries, workflow and paper. Export deliberate public symbols through `packages/contracts/src/index.ts`; API DTO files alias these symbols rather than duplicating schemas.
- The command owner exports `approvalCommandOperationSchema`, `approvalActorSchema`, `approvalIssueStateSchema`, `approvalTargetSchema` plus the named receipt/outcome/data schemas and inferred types. Actor shape is shared safe identity only; operation-specific actor refinement belongs to the receipt and executor. `approval.schema.ts` exports `contactChangesSchema`, the body/query/data schemas, `approvalPieceParamsSchema`, `approvalIssueParamsSchema` and `approvalEventParamsSchema` in the ledgers below.
- Extract current status/stage/work-state/business-number scalar schemas into proposed `packages/contracts/src/sales-orders/sales-order-values.schema.ts`. Export `salesOrderStatusSchema`, `orderPieceStageSchema`, `orderWorkStateSchema`, `salesBusinessNumberSchema`; re-export existing public `salesOrderStatusSchema` from its original schema owner. Change internal uses only; accepted values/regex/bounds stay identical. This makes the additive approval-event activity variant possible without a cycle between the approval wrapper and sales-order activity schemas.
- Extend only `salesActivityItemSchema` with the third outer variant `{kind:'approval',event:approvalActivityEventSchema}`. Existing `kind:'draft'`/`kind:'order'`, P03 `orderActivityEventSchema`, `salesOrderRevisionDataSchema` and sales receipt snapshots remain unchanged. `approval-event.schema.ts` imports scalar/value owners, never the financial wrapper or sales activity union.

## 2. Shared validation and wire conventions

Every object below is strict; unknown keys are errors, including actor/role/time, prices, state/counters and fixed specification fields. IDs are lowercased by `salesUuidSchema`; versions are integers 1 through 2,147,483,647. Instants are offset-aware ISO strings emitted in UTC. Money/counts continue using the existing P03 schemas and exact decimal strings; JSON numbers never carry monetary values.

Required reason/instruction/contact text uses `nonEmptyBoundedString(4000)`: retain entered text, reject whitespace-only, NUL and over-limit input. Optional notes accept omitted/null/blank as null, preserve nonblank text, reject NUL or more than 4000 characters before normalization. No concatenation of optional return notes into the separately bounded reason. All selection display strings remain exact source values, including source whitespace/case.

GET operations accept explicit parameter/query schemas. Empty query is `salesEmptyQuerySchema`; no unchecked query keys. Lists use existing page/limit parsing: default 1/25, maximum limit 100, safe offset validation. `search` is trimmed, maximum 150 characters, no NUL; empty becomes omitted. Type uses `salesOrderTypeSchema`. Sort after filtering by descending event/update instant and UUID as specified below; zero results means zero totalPages, and an out-of-range page returns empty items with correct metadata.

## 3. Command input ledger

Every command has required `{commandId:UUID,expectedVersion:Version}`; every version is the root `sales_drafts.version`, not an issue-local counter. Route IDs bind the target before hashing. Bodies never accept an `orderId`, `pieceId` or `issueId` duplicate that could disagree with the route.

| Exported schema / type                            | Additional exact fields                                             | Meaning and validation                                                                         |
| ------------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `approveInitialBodySchema` / `ApproveInitialBody` | None                                                                | Current pending initial revision only.                                                         |
| `returnInitialBodySchema` / `ReturnInitialBody`   | `reason:RequiredText`, `notes?:OptionalText`                        | Return current initial revision; retain optional notes separately.                             |
| `reportIssueBodySchema` / `ReportIssueBody`       | `reason:RequiredText`, `notes?:OptionalText`                        | Actual source state/department/reporter are server-derived.                                    |
| `resolveIssueBodySchema` / `ResolveIssueBody`     | Discriminated `decision` union below                                | Current `APPROVAL_REVIEW` issue only.                                                          |
| `submitContactBodySchema` / `SubmitContactBody`   | Discriminated `kind` union below                                    | Eligible SALES or ADMIN that itself owns the order, in `SALES_CONTACT`; no on-behalf response. |
| `reviewContactBodySchema` / `ReviewContactBody`   | Required `proposalId:UUID` and discriminated `decision` union below | Bind exact current proposal while issue is `REAPPROVAL`.                                       |

Resolve branches:

- `decision:'RETURN_TO_DEPARTMENT'`, `target:'CUTTING'|'PRODUCTION'`, `notes:RequiredText`.
- `decision:'SEND_TO_SALES'`, `target:'CUTTING'|'PRODUCTION'`, `notes:RequiredText`.
- `decision:'CANCEL'`, `reason:RequiredText`, `confirmed:true`; target/notes are unsupported.

Contact branches:

- `kind:'AMEND'`, `contactNotes:RequiredText`, `changes:ContactChanges`. `ContactChanges` is a strict sparse object with only `model?:UUID`, `size?:UUID`, `leatherBase?:UUID`, `sole?:UUID|null`. An empty changes object is a valid notes-only response. Omission preserves that field. Null/blank is forbidden for model/size/base; explicit null clears optional floor. No strings/labels, decoration, other piece fields, paid, customer or target are accepted.
- `kind:'CANCEL_REQUEST'`, `contactNotes:RequiredText`; `changes` is unsupported, not silently discarded. Confirmation here sends a request and does not cancel a piece.

Changed selection IDs must resolve to the corresponding kind on the active reviewed catalog at submission. Resolve/store exact labels and entry provenance into an immutable full proposal then; do not pick a first entry or change decoration/prices. Unchanged fields retain their prior labels/references, including old source values. Approval accepts that exact retained proposal rather than resolving it under a later active catalog.

Review branches:

- `decision:'ACCEPT'`, `notes:RequiredText`; valid only for the current `AMEND` proposal, including a notes-only response. Use the retained target; no target override.
- `decision:'RETURN_TO_SALES'`, `reason:RequiredText`; preserves the same held issue/target and previous proposal, permits renewed owner contact.
- `decision:'CANCEL'`, `reason:RequiredText`, `confirmed:true`; applies retained cancellation without applying proposed fields. Valid for AMEND or CANCEL_REQUEST. A cancellation request cannot be accepted as an AMEND/resume.

## 4. Receipt and uncertain-result protocol

The proposed immutable P04 command ledger and `ApprovalCommandExecutor` are narrow owners for these six operations: `APPROVE_INITIAL`, `RETURN_INITIAL`, `REPORT_ISSUE`, `RESOLVE_ISSUE`, `SUBMIT_CONTACT`, `REVIEW_CONTACT`. Do not expand the previous sales ledger operation/actor enums.

`approvalCommandReceiptSchema` / `ApprovalCommandReceipt` is strict:

`{commandId,operation,orderId,actor:{id,fullName,role,department},beforeVersion,afterVersion,occurredAt}`.

Both versions are required; `afterVersion = beforeVersion + 1`. Actor is the actual captured safe actor, fullName maximum 150, role/department current existing enums. Employee actor constraints depend on operation: initial/resolve/review requires APPROVAL; report requires CUTTING/PRODUCTION/QUALITY; contact requires SALES. Eligible ADMIN retains cross-department authority, including contact only when it is itself the immutable order owner; it cannot impersonate another owner's contact response. The schema permits ADMIN for SUBMIT_CONTACT while the service enforces ownership. No actor credentials, email or account phone appear.

`approvalCommandOutcomeSchema` / `ApprovalCommandOutcome` is strict:

`{orderId,orderVersion,orderStatus,pieceId:UUID|null,pieceStage:PieceStage|null,pieceWorkState:WorkState|null,issueId:UUID|null,issueState:IssueState|null,proposalId:UUID|null}`.

It describes immutable result facts, not a current order projection. Initial operations have null piece/issue/proposal fields; piece operations have matching target IDs and state. There are no prices, contacts, raw facts, current eligibility or financial snapshots in this output. `orderVersion` equals receipt `afterVersion`, and order identity agrees across receipt/result.

`approvalCommandDataSchema` / `ApprovalCommandData` is `{kind:'approval-command',receipt,replayed:boolean,outcome}`. All P04 commands return HTTP 200 in the existing success envelope through `ResponseHelper.ok`. The executor stores the exact safe outcome; an exact replay returns that outcome with `replayed:true`, not a newly built result under later state. Same command ID with another actor/operation/route/version/payload is a conflict. Current authority and resource relation are rechecked before replay/observation. For REPORT_ISSUE only, the original actor may recover its bounded metadata after the piece moves away if it remains eligible ADMIN or remains in that retained report's actual source department. A department reassignment to another factory department is insufficient. This retained action witness does not authorize current factory detail; suspended/ineligible actors are denied. Other operations retain their normal current order/owner relation.

After a lost response, GET the original command ID. A 404 means no currently observable committed command result; it does not by itself prove a concurrently pending transaction rolled back. An explicit same-ID/same-intent retry may safely deduplicate under the executor lock; never create a different command to guess the outcome. Retain input while unknown. After any confirmed receipt, refetch the current role-authorized root/workflow and affected lists; do not publish old receipt facts as current state or automatically reissue a confirmed command after a refetch failure.

## 5. Read DTOs

The following names are proposed public schema/type pairs. Types use PascalCase corresponding to each camelCase schema.

### Workflow and current issues

- `approvalDecisionStampSchema` / `ApprovalDecisionStamp`: `{decisionId,orderVersion,actor,approvedAt}` from a real `APPROVE_INITIAL` or accepting `REVIEW_CONTACT` record, never an arbitrary last actor or captured signature.
- `contactValuesSchema` / `ContactValues`: `{model:string,size:string,leatherBase:string,sole:string|null,catalogSelections:{model:UUID|null,size:UUID|null,leatherBase:UUID|null,sole:UUID|null}}`. Labels maximum 200; required three labels nonblank. A retained label need not receive an invented entry reference.
- `pieceContactProposalSchema` / `PieceContactProposalDto`: `{id,kind:'AMEND'|'CANCEL_REQUEST',contactNotes,before:ContactValues,proposed:ContactValues|null,submittedBy:Actor,submittedAt}`. AMEND has full resolved proposed values; CANCEL_REQUEST has null proposed values. It is immutable. Review disposition lives in issue/decision history, not a competing mutable proposal truth.
- `approvalInstructionSchema`: `{commandId,actor,occurredAt,text}` from the latest SEND_TO_SALES or RETURN_TO_SALES decision for the current cycle; null before such a decision. It is distinct from original report reason/notes.
- `manufacturingIssueSummarySchema` / `ManufacturingIssueSummary`: `{id,pieceId,state,sourceDepartment,reportedAt,reason,notes,resumeTarget,currentProposalId,instructions,allowedActions:{canResolve,canSubmitContact,canReviewContact}}`. State is `APPROVAL_REVIEW|SALES_CONTACT|REAPPROVAL|RESOLVED`; target is null or CUTTING/PRODUCTION. Lists exclude RESOLVED. Reason/notes are original report input; instructions are separately retained approval guidance. The bounded list mapper computes these three hints using the same current actor/state/immutable-owner rules as the full issue mapper; a list row never borrows unrelated order-level paid/resubmit flags. Hints do not grant write authority.
- `manufacturingIssueSchema` / `ManufacturingIssueDto`: `{id,orderId,pieceId,state,source:{department,stage,workState},reporter,reportedAt,reason,notes,resumeTarget,currentProposal,instructions,allowedActions:{canResolve,canSubmitContact,canReviewContact}}`. Original source workState is INCOMING or IN_PROGRESS and stage/department is CUTTING/PRODUCTION/QUALITY. Hints never grant authority.
- `approvalWorkflowSchema` / `ApprovalWorkflow`: `{initialApproval:ApprovalDecisionStamp|null,currentReturn:null|{decisionId,reason,notes,returnedAt},allowedActions:{canApproveInitial,canReturnInitial},printEligibility:{allowed:boolean,reason:null|'NOT_APPROVED'|'RETURNED'|'PENDING_REAPPROVAL'},issues:ManufacturingIssueDto[]}`. Issues contains current unresolved cycles only, bounded by 200 and unique piece IDs. Initial optional return notes are selected by the current return decision ID, not concatenated or independently fetched per row.
- `approvalOrderDataSchema` / `ApprovalOrderData`: `{order:SalesOrderDto,workflow:ApprovalWorkflow}`. Keep the original `SalesOrderDto` shape. Wrapper root/issue/proposal selections come from one authorized consistent read; a foreign order is not returned with a merely false action hint.

Print eligibility requires a real initial approval record agreeing with the root's accepted state, no current initial return and no submitted pending piece review. Hold while an unresolved SALES_CONTACT/REAPPROVAL issue retains a submitted proposal, including a proposal returned for renewed contact; resolving one of several holds is insufficient. An initial B referral without any submitted proposal does not invent a submitted revision. No previous-version print route is created.

`IssueQueueItem` is `{order:SalesOrderSummary,piece:{id,position,model,size,leatherBase,sole,stage,workState},issue:ManufacturingIssueSummary}`. No full 200-piece order is embedded in every issue row. Counts/page rows share filters and the same authorized read snapshot; no N+1 per-item workflow/proposal requests. `unresolvedIssues = approvalIssues + salesContactPieces + reapprovalPieces`; initialOrders counts distinct roots. `approvedToday` counts all actual APPROVE_INITIAL decisions across eligible approvers in the configured current business day, excluding issue decisions; the existing dashboard card is department-wide. `returnedOrders` counts distinct current RETURNED roots, matching the existing “returned to sales for correction” card, not historical returns today. Own-decision history remains actor-scoped. Reuse `parseOrderBusinessTimeZone` and current `orderConfig.businessTimeZone`; missing/invalid calendar fails the dashboard with ORDER_CALENDAR_UNAVAILABLE. Compute a controlled instant's local-midnight and next-local-midnight UTC bounds using parameterized database timezone conversion, then compare occurredAt in `[start,end)`; do not use browser/host day or fixed 24-hour arithmetic across daylight-saving transitions. No new calendar requirement is added to commands.

### Retained event detail

`approvalActivityEventSchema` / `ApprovalActivityEvent` is a safe summary `{id,orderId,orderVersion,businessNumber,operation,actor,occurredAt,pieceId:UUID|null,issueId:UUID|null,proposalId:UUID|null,decision:Decision|null,notes:string|null,changedFields:ApprovalChangedField[]}`. Operation is the six-operation enum; decision is null or its applicable resolve/review literal. ChangedField is the bounded unique subset of `approval,status,pieceState,issue,proposal,model,size,leatherBase,sole,cancellation,total`; no raw order, contact or monetary snapshots in a page summary. The metadata-only receipt is not used as a substitute for this authorized business-history projection.

`approvalEventFactsSchema` / `ApprovalEventFacts` describes retained internal facts returned only to eligible approval/ADMIN or actual owner sales:

`{orderStatus,approvedAt,currentReturn:null|{decisionId,reason,notes,returnedAt},money:SalesOrderDto['money'],counts:SalesOrderDto['counts'],pieces:ApprovalPieceFact[],issue:null|{id,state,sourceDepartment,sourceStage,sourceWorkState,resumeTarget,currentProposalId},proposal:PieceContactProposalDto|null}`.

`ApprovalPieceFact` is `{id,stage,workState,issueId,receivedAt,cancelledAt,cancellationReason}`. Pieces contains exactly the affected subset, at most 200, no duplicates: all initially released pieces or the singleton issue piece. This retains cancellation before/after financial evidence without storing a second full order/contact/price snapshot. On creation before issue/proposal is null; after facts retain the changed cycle/proposal even when a resolved current-piece pointer clears. All object fields use the named existing scalar/value schemas and strict nullable shapes; date serialization is deliberate.

`approvalEventDataSchema` / `ApprovalEventData` is `{event:ApprovalActivityEvent,before:ApprovalEventFacts,after:ApprovalEventFacts}`. Event ID/order/version agree with command target/after-version. This P04 detail is never parsed as `SalesOrderRevisionData`; P03 full snapshot drilldown continues its original endpoint/protocol. Factory cannot read these facts/contact notes or raw P03 history.

### Official and factory paper

- `officialOrderPaperDataSchema` / `OfficialOrderPaperData`: `{order:SalesOrderDto,approval:{initial:ApprovalDecisionStamp,pieces:PieceApprovalStamp[]},printVersion:Version}`. `printVersion = order.version`. Each PieceApprovalStamp is `{pieceId,proposalId,decisionId,orderVersion,actor,approvedAt}` for the last accepted AMEND authorizing that active piece's current values; unique piece IDs, maximum 200. Initial stamp comes from APPROVE_INITIAL. A later paid/report/cancel actor cannot become the approval signer. Keep user-entered `responsibleSignature` distinct from these factual annotations.
- `factoryOrderPaperDataSchema` / `FactoryOrderPaperData`: `{order:FactoryOrderProjection,issues:FactoryIssueInstruction[]}`. Reuse the existing strict nonfinancial `factoryOrderSchema` and whole-order piece/tracking/count meaning. A nonadmin reader needs at least one piece currently in its department or held under an unresolved issue originally reported from that department; otherwise the order is not visible. Once that order relation is established, return its whole safe manufacturing context rather than redefining completion against a department-only subset. Actions still validate the exact current department/selected piece. ADMIN may read the complete safe projection. FactoryIssueInstruction is `{pieceId,issueId,state,reason,reportNotes,approvedInstructions:null|string,target:null|'CUTTING'|'PRODUCTION'}`. The array has at most 200 unique piece IDs: select its current open cycle if any, otherwise its most recent resolved cycle ordered by cycle DESC/id DESC. This is current/latest work context, not an unbounded history response. For that selected cycle, approvedInstructions is only the last positive RESOLVE_ISSUE/RETURN_TO_DEPARTMENT or REVIEW_CONTACT/ACCEPT decision's retained notes; if none, it is null. SEND_TO_SALES/RETURN_TO_SALES correspondence, contact notes/proposed fields, money/prices/provenance/private contacts and raw facts are excluded. Existing nonfinancial cancellation reason remains on the factory piece projection. Do not construct a financial DTO then hide/delete keys. Test multiple historical cycles, a newer open cycle without positive guidance and simultaneous current pieces: one selected context per piece, no prior-cycle or contact guidance substituted, no more than 200 rows and no forbidden nested field.

## 6. HTTP routes and authority

All routes are proposed. Express composition remains in `apps/api/src/router.ts`; create `ApprovalService`/`ApprovalController`, `approval.routes.ts`, `approval.queries.ts`, `approval.mapper.ts`, `approval-command-executor.ts`, `approval.errors.ts`, `approval.types.ts` and DTO aliases in the owning `apps/api/src/modules/approval/` module. No second auth/client/response protocol is introduced.

Middleware order is current business authentication → department gate → CSRF for unsafe methods → shared params/query/body validation → controller. Services repeat current authority/target checks under the transaction lock. `authorizeDepartments` exempts ADMIN generally; SUBMIT_CONTACT additionally requires actual immutable owner identity for SALES and ADMIN alike, so that exemption cannot create on-behalf sales authority.

## 7. Stable failures

Keep current authentication, `ACCOUNT_RESTRICTED`, `DEPARTMENT_ACCESS_DENIED`, CSRF, rate-limit and safe internal failures. Request schema/selection membership errors are HTTP 400 `VALIDATION_ERROR`, with body/params/query-prefixed known field paths. Missing/foreign resource existence is not distinguished for an actor lacking a permitted relation.

| HTTP / code                          | Scope and observable meaning                                                                                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 404 `ORDER_NOT_FOUND`                | Missing or inaccessible order/piece parent; no private data.                                                                                                                                            |
| 404 `APPROVAL_ISSUE_NOT_FOUND`       | Issue absent or not the route's authorized order/piece.                                                                                                                                                 |
| 404 `APPROVAL_EVENT_NOT_FOUND`       | P04 event absent/foreign or a P03 event passed to P04 facts endpoint.                                                                                                                                   |
| 404 `APPROVAL_COMMAND_NOT_FOUND`     | No currently observable original-actor result.                                                                                                                                                          |
| 409 `ORDER_VERSION_CONFLICT`         | Expected root version stale; retain form and explicitly review fresh state.                                                                                                                             |
| 409 `ORDER_STATE_CONFLICT`           | Order no longer eligible for initial decision/report/cancellation.                                                                                                                                      |
| 409 `APPROVAL_ISSUE_CONFLICT`        | Duplicate unresolved issue, wrong current issue state or resolved cycle.                                                                                                                                |
| 409 `APPROVAL_PROPOSAL_CONFLICT`     | Proposal ID is not current or chosen review decision cannot apply to its kind.                                                                                                                          |
| 409 `APPROVAL_COMMAND_CONFLICT`      | Same command ID bound to different actor/operation/target/version/intent.                                                                                                                               |
| 409 `APPROVAL_TRANSACTION_CONFLICT`  | Bounded retry/lock-timeout exhausted; observe original result before explicit retry.                                                                                                                    |
| 409 `ORDER_PRINT_NOT_APPROVED`       | No qualifying actual initial approval stamp or initially unapproved revision.                                                                                                                           |
| 409 `ORDER_PRINT_RETURNED`           | Current initial revision returned.                                                                                                                                                                      |
| 409 `ORDER_PRINT_REAPPROVAL_PENDING` | Whole-order print temporarily blocked by pending submitted piece review.                                                                                                                                |
| 503 `ORDER_CATALOG_UNAVAILABLE`      | A newly changed selection cannot use a currently available reviewed catalog; unchanged retained values are still readable.                                                                              |
| 503 `ORDER_CALENDAR_UNAVAILABLE`     | Dashboard today's counts cannot be defined because the existing configured business timezone is missing/invalid; no browser/host fallback. Commands are unaffected by this dashboard-only prerequisite. |

No error may expose SQL/Prisma/provider payloads, credential fields or raw stored snapshots. Command/transaction error types live in `approval.errors.ts`; reuse existing named order/current-account errors where their semantics match. Root/issue/proposal/version validation precedes protected writes and losing outcomes leave state/history/money unchanged.
