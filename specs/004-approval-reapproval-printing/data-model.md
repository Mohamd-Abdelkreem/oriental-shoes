# P04 Data Design

This is proposed implementation design for [the P04 specification](spec.md), not a migration or executed persistence claim. All existing nine migrations and their SQL/checksums remain unchanged. [Backend blueprints](backend-design.md) own transaction order and interfaces; [contracts](contracts/approval.md) own wire fields.

## Existing owners and immutable boundaries

Reuse `packages/database/prisma/schema.prisma`: `SalesDraft` is the aggregate root and `version` remains the sole order concurrency clock. Its `id` equals `SalesOrder.id`; base `SalesDraftPiece.id` equals physical `SalesOrderPiece.id`. Order membership, position, quantity one, owner/type/customer, submitted contact/number/decoration/price/source provenance remain unchanged by P04.

Current source already provides `SalesOrder.status`, `approvedAt`, `currentReturnDecisionId`, `currentReturnOrderVersion`, `currentReturnReason`, `currentReturnedAt`; `SalesOrderPiece.stage`, `workState`, `issueId`, `receivedAt`, `cancelledAt`, `cancellationReason`; and exact monetary fields. Add no competing quantity, balance, paid or lifecycle store.

Existing PostgreSQL owners in migration `20261106000200_p03_catalogs_submitted_orders` remain active: `enforce_sales_order_terms`, `enforce_submitted_root_terms`, `enforce_sales_order_piece_terms`, `prevent_submitted_piece_structure`, `prevent_submitted_decoration_change`, `prevent_submitted_piece_addition`, `check_sales_order_graph` and all their triggers. Preserve the later forward repair `20261106000300_p03_preserve_frozen_decoration_selection`. **No existing function or trigger replacement is planned.** Captured model/size/base/floor changes and state/total changes fit those existing allowed fields.

`SalesCommand`, its immutable rows, enum, `ck_sales_commands_binding`, strict sales-only receipts, executor and observation protocol remain P02/P03 owners. They cannot represent approval/factory actors without broadening accepted contracts. Add one narrow P04 receipt/history table rather than a generic command framework or migration of prior commands.

## New enums and models

All names below are proposed Prisma names; mapped table/column names use snake case.

### Enums

| -------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `ApprovalCommandOperation` | `APPROVE_INITIAL`, `RETURN_INITIAL`, `REPORT_ISSUE`, `RESOLVE_ISSUE`, `SUBMIT_CONTACT`, `REVIEW_CONTACT` | Exactly the six P04 commands                                       |
| `ManufacturingIssueState`  | `APPROVAL_REVIEW`, `SALES_CONTACT`, `REAPPROVAL`, `RESOLVED`                                             | Workflow of one issue cycle, distinct from normal department stage |

Do not add new departments, order types, order statuses or piece stages. Existing `Department`, `SalesOrderStatus`, `SalesPieceStage`, `SalesPieceWorkState` remain canonical.

### ApprovalCommand / approval_commands

One immutable business event is also the durable command receipt; its `commandId` is the decision ID for initial returns/approval and later dispositions.

| Field                                              | Type / nullability                          | Invariant                                                                                                                                                                                  |
| -------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `commandId`                                        | UUID PK `approval_commands_pkey`            | Caller command identity, globally unique inside this protocol                                                                                                                              |
| `operation`                                        | `ApprovalCommandOperation`                  | Fixed operation binding                                                                                                                                                                    |
| `actorId`                                          | UUID, nonnull, User FK RESTRICT             | Actual authenticated actor                                                                                                                                                                 |
| `actorFullName`, `actorRole`, `actorDepartment`    | VarChar(150), UserRole, nullable Department | Retained actual action-time identity; no email/token/password                                                                                                                              |
| `orderId`                                          | UUID, SalesOrder FK RESTRICT                | Every P04 command targets one submitted aggregate                                                                                                                                          |
| `pieceId`                                          | Nullable UUID                               | Null only for initial approve/return; other commands name one physical piece                                                                                                               |
| `issueId`, `proposalId`                            | Nullable UUID                               | Typed semantic binding described below; never arbitrary detached IDs                                                                                                                       |
| `expectedVersion`, `beforeVersion`, `afterVersion` | Nonnull Int                                 | expected=before, before in 1..2147483646, after=before+1                                                                                                                                   |
| `payloadHash`                                      | Char(64)                                    | Lowercase SHA-256 canonical intent                                                                                                                                                         |
| `decision`, `decisionNotes`                        | Nullable VarChar(32) / VarChar(4000)        | RESOLVE uses RETURN_TO_DEPARTMENT/SEND_TO_SALES/CANCEL; REVIEW uses ACCEPT/RETURN_TO_SALES/CANCEL; these operations require nonblank decision notes; both fields null for other operations |
| `beforeFacts`, `afterFacts`                        | Nonnull JsonB                               | Bounded internal P04 fact records, not full SalesOrder DTOs or opaque caller JSON                                                                                                          |
| `outcome`                                          | Nonnull JsonB                               | Exactly the strict metadata-only `ApprovalCommandOutcome` contract                                                                                                                         |
| `occurredAt`                                       | Timestamptz(6), nonnull                     | One server instant for command/state/history                                                                                                                                               |

Internal `ApprovalEventFacts` has exactly `{orderStatus,approvedAt,currentReturn,money,counts,pieces,issue,proposal}` as defined in the contract. `currentReturn` is null or `{decisionId,reason,notes,returnedAt}`. `money`/`counts` reuse existing exact SalesOrder DTO meanings; `pieces` contains affected physical metadata (all pieces for initial decisions, singleton for issue commands), bounded by 200. Each piece fact is `{id,stage,workState,issueId,receivedAt,cancelledAt,cancellationReason}`. `issue` is null or `{id,state,sourceDepartment,sourceStage,sourceWorkState,resumeTarget,currentProposalId}`. `proposal` is null or bounded `PieceContactProposalDto` carrying four-field old/proposed values/contact notes. Before first creation the corresponding issue/proposal is null; renewed contact retains the previous current proposal in beforeFacts and the new one in afterFacts. After resolution relevant facts remain even though the physical current pointer clears. Summary retains disposition/decision notes. These private facts are not a full SalesOrder snapshot/caller JSON; factory endpoints never return them. Cancellation money proves unchanged paid without a financial receipt projection.

Command shape checks: initial operations have null piece/issue/proposal; REPORT has piece+new issue and null proposal; RESOLVE has piece+issue and null proposal; SUBMIT has piece+issue+new proposal; REVIEW has piece+issue+reviewed proposal. The corresponding operation-specific fact parser must reject incompatible fields. Database `ck_approval_commands_binding`, `ck_approval_commands_versions`, `ck_approval_commands_hash` and a deferred graph check enforce those bindings and outcome identity/version. `approval_command_immutable` BEFORE UPDATE/DELETE rejects all changes (`ck_approval_command_immutable`).

Indexes: unique `(order_id, after_version)` named `approval_commands_order_version_key`; partial unique `(order_id)` for operation APPROVE_INITIAL named `approval_commands_initial_approval_key`; `(actor_id, occurred_at DESC, command_id DESC)` for own history; `(order_id, occurred_at DESC, command_id DESC)` for activity; `(operation,occurred_at DESC,command_id DESC)` named `approval_commands_operation_occurred_idx` for role-wide business-day counts; `(issue_id, after_version DESC)` for current instructions and issue history. No cross-table rewrite of the sales ledger is introduced. Root row serialization makes P03 and P04 version increments mutually exclusive.

### ManufacturingIssue / manufacturing_issues

| Field                                                                  | Type / nullability                              | Invariant                                                                            |
| ---------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------ |
| `id`                                                                   | UUID PK                                         | Server-created stable issue identity                                                 |
| `orderId`, `pieceId`                                                   | UUID, nonnull                                   | Composite FK `(piece_id,order_id)` → SalesOrderPiece `(id,order_id)`, RESTRICT       |
| `cycle`                                                                | Int, nonnull                                    | Positive, per-piece increasing; computed while root locked                           |
| `state`                                                                | ManufacturingIssueState                         | One current workflow state                                                           |
| `sourceDepartment`                                                     | Department                                      | CUTTING/PRODUCTION/QUALITY only                                                      |
| `sourceStage`                                                          | SalesPieceStage                                 | Exact matching CUTTING/PRODUCTION/QUALITY stage at report                            |
| `sourceWorkState`                                                      | SalesPieceWorkState                             | INCOMING or IN_PROGRESS at report                                                    |
| `reporterId`, `reporterFullName`, `reporterRole`, `reporterDepartment` | User UUID FK RESTRICT, retained identity fields | Actual reporter; admin allowed, employee department equals source                    |
| `reason`, `notes`                                                      | VarChar(4000), nonnull reason / nullable notes  | Required nonblank reason; optional absence is null                                   |
| `reportedAt`, `updatedAt`                                              | Timestamptz(6), nonnull                         | Real report/workflow instants                                                        |
| `reportedCommandId`                                                    | UUID, nonnull, unique command FK RESTRICT       | Its immutable REPORT_ISSUE witness; deferred because command inserts after issue     |
| `resumeTarget`                                                         | Nullable SalesPieceStage                        | Only CUTTING/PRODUCTION; required after first sales referral and retained thereafter |
| `latestProposalId`                                                     | Nullable UUID                                   | Composite FK with issue ID; points to this issue's latest immutable proposal         |
| `resolvedAt`, `resolutionCommandId`                                    | Nullable instant / UUID command FK RESTRICT     | Both nonnull iff state RESOLVED                                                      |

Unique `(piece_id,cycle)` named `manufacturing_issues_piece_cycle_key`; partial unique `(piece_id) WHERE state <> 'RESOLVED'` named `manufacturing_issues_one_open_piece_key`; unique `(id,order_id,piece_id)` for child bindings. Index `(state, reported_at DESC, id DESC)` for queues; `(order_id,piece_id,cycle)` for bounded order context. Identity/source/reporter/reason/report-time are immutable after insertion; only workflow state/target/latestProposal/resolution/updatedAt may change. Deletion is forbidden by `manufacturing_issue_retained` and source changes by `ck_manufacturing_issue_source_immutable`.

Do not add an independent issue version. The root order version protects every piece decision, proposal and issue update. A change to a companion or paid amount can make a dialog stale; that intentionally yields review/retry instead of silent overwriting.

### PieceContactProposal / piece_contact_proposals

Immutable submitted contact intent, not editable approved piece state.

| Field                                                                          | Type / nullability                               | Invariant                                                                                                                         |
| ------------------------------------------------------------------------------ | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                                                           | UUID PK                                          | Server-created proposal identity                                                                                                  |
| `orderId`, `pieceId`, `issueId`                                                | UUID, nonnull                                    | Composite FK `(issue_id,order_id,piece_id)` → issue; RESTRICT                                                                     |
| `sequence`                                                                     | Positive Int                                     | Per-issue increasing under root lock; unique `(issue_id,sequence)`                                                                |
| `kind`                                                                         | PieceContactKind                                 | AMEND or CANCEL_REQUEST                                                                                                           |
| `submittedCommandId`                                                           | UUID, nonnull                                    | Unique FK to its SUBMIT_CONTACT command, RESTRICT                                                                                 |
| `submittedById`, `submittedByFullName`                                         | User UUID FK RESTRICT, VarChar(150)              | Actual owner with current SALES/ADMIN authority; no on-behalf exemption; actor/time also in command                               |
| `contactNotes`                                                                 | VarChar(4000), nonnull                           | Nonblank recorded communication, never proof of external delivery                                                                 |
| `beforeModel`, `beforeSize`, `beforeLeatherBase`, `beforeSole`                 | VarChar(200); first three nonnull, sole nullable | Exact retained approved labels from base capture, never caller-authored snapshot values                                           |
| `beforeModelId`, `beforeSizeId`, `beforeLeatherBaseId`, `beforeSoleId`         | Nullable CatalogEntry UUID FKs                   | Existing retained bindings when present; missing prior optional references are not fabricated                                     |
| `proposedModel`, `proposedSize`, `proposedLeatherBase`, `proposedSole`         | Nullable VarChar(200) columns                    | AMEND requires first three labels; sole nullable; CANCEL_REQUEST has all null                                                     |
| `proposedModelId`, `proposedSizeId`, `proposedLeatherBaseId`, `proposedSoleId` | Nullable CatalogEntry UUID FKs                   | Supplied changed selections resolve real IDs; omitted retained selections may retain null references; CANCEL_REQUEST has all null |
| `submittedAt`                                                                  | Timestamptz(6), nonnull                          | Actual submission instant                                                                                                         |

CatalogEntry is already immutable and preserves source IDs/exact display values. For every nonnull binding, field kind and exact label must agree with that record. Existing P03 response/persistence permits retained captured values without a catalogSelections entry, so preserve their exact label and null reference rather than inventing a lookup/default. The proposal therefore retains typed four-field labels as well as nullable source bindings, all derived by the server from current capture or validated source IDs. AMEND is complete after resolving the sparse command: omitted keys reuse prior labels/IDs, explicit sole=null clears label/reference, and required keys cannot clear. A notes-only map retains identical before/proposed values, including null references. CANCEL_REQUEST has no proposed fields and cannot apply any correction.

`ck_piece_contact_proposals_values` validates positive sequence, required nonblank prior labels, kind-specific proposed labels/nullable references and nonblank contact notes. Deferred `ck_piece_contact_proposal_bindings` validates every nonnull catalog field kind/exact label, issue membership and SUBMIT_CONTACT witness. Proposed IDs may belong to a later reviewed source than frozen decoration without changing original price provenance. Changed IDs must come from the active source at submit; approval uses the retained proposal without re-resolving under newer catalog. Index `(issue_id, sequence DESC)`; unique `(id,issue_id)` supports latestProposal binding. `piece_contact_proposal_immutable` rejects UPDATE/DELETE (`ck_piece_contact_proposal_immutable`). Review outcome is in immutable REVIEW_CONTACT events/current issue, not a mutable copy of submitted content.

## Existing-model additions and final graph checks

Add Prisma relations from User/SalesOrder/SalesOrderPiece to these models and inverse self-owned relations for command/issue/proposal references. Add unique `(id,order_id)` on SalesOrderPiece for the composite issue membership FK. Attach the existing `SalesOrderPiece.issueId` to the issue `(id,orderId,pieceId)` binding with a deferred FK plus graph check; nullable means no current open issue. Preserve every existing frozen term/structure constraint.

The authored forward SQL, not Prisma's relation syntax, owns circular deferral. The following named FKs are **DEFERRABLE INITIALLY DEFERRED**, all ON DELETE RESTRICT: `manufacturing_issues_reported_command_fkey` (`reported_command_id` → commandId), `manufacturing_issues_resolution_command_fkey` (`resolution_command_id` → commandId), `piece_contact_proposals_submitted_command_fkey` (`submitted_command_id` → commandId), `manufacturing_issues_latest_proposal_fkey` (`latest_proposal_id,id` → proposal `(id,issue_id)`), `sales_order_pieces_current_issue_fkey` (current issue/order/piece binding), `approval_commands_issue_fkey` (issue/order/piece binding), `approval_commands_proposal_fkey` (proposal/issue binding). Parent order/actor/catalog FKs without a cycle may remain immediate RESTRICT. This permits work to insert an issue/proposal or mark resolution before inserting the one immutable command while still rejecting a missing witness at commit.

Named checks `ck_manufacturing_issues_source` and `ck_manufacturing_issues_state` enforce the source-stage/department/work-state mapping, retained reporter role/department compatibility, nonblank bounded reason and terminal/nonterminal target/proposal/resolution shape described above. `ck_approval_commands_actor` checks retained operation actor snapshots (APPROVAL or ADMIN for decisions; matching source employee or ADMIN report; SALES/ADMIN plus actual owner at submit). `ck_approval_commands_decision` checks operation-specific decision/notes presence. Contextual cross-row owner/source checks belong in `check_approval_order_graph`, under root serialization, not a fake CHECK that queries other tables.

`enforce_manufacturing_issue_transition` BEFORE INSERT/UPDATE enforces initial APPROVAL_REVIEW and only APPROVAL_REVIEW→SALES_CONTACT/RESOLVED, SALES_CONTACT→REAPPROVAL, REAPPROVAL→SALES_CONTACT/RESOLVED. A resolved row cannot change/reopen. Once resumeTarget is nonnull it cannot change. RETURN_TO_SALES preserves latestProposalId; SALES_CONTACT→REAPPROVAL must attach a newly submitted higher-sequence proposal. The graph's current-command witness validates which permitted operation caused the transition. Illegal transitions use `ck_manufacturing_issue_transition`; they are not permitted merely because final nonnull fields look plausible.

New `check_approval_order_graph(orderId)` runs as DEFERRABLE INITIALLY DEFERRED constraint triggers on the new three tables and updates to SalesOrder/SalesOrderPiece/SalesDraft. It verifies final transaction state:

1. Every open issue points to a noncancelled piece in the same order, source stage and BLOCKED work state; that piece's `issueId` equals this issue. Every nonnull current pointer points back to exactly one nonresolved issue. A resolved issue is no longer that piece's current pointer.
2. Source department matches source stage, the **retained action-time** reporter/actor snapshot is compatible with its recorded operation, state/target/proposal/resolution combinations satisfy table rules, and proposal IDs reference the same issue/piece/order. Never require a historical actor's current role/department/status to equal its old snapshot; later reassignment/suspension preserves history. Live authority is checked at each new read/write, not used to invalidate retained facts.
3. If a current return proof names an actual P04 command, it must identify RETURN_INITIAL for that order and its `currentReturnOrderVersion` equals root.version and the decision's afterVersion; reason/time match the event. Existing P03 controlled proof rows without a P04 witness are preserved as upstream boundary fixtures, not fabricated approval history. A separate deferred transition trigger `p04_return_decision_binding` on a newly changed return proof requires the matching new RETURN_INITIAL witness; it does not reject untouched pre-migration proof rows. Optional notes remain separate from the bounded reason. Do not add a mandatory FK from the historical `currentReturnDecisionId` field to the new table.
4. P04 initial approval exists at most once and binds its command instant to approvedAt. A deferred `p04_initial_approval_binding` on a newly approved transition requires the real APPROVE_INITIAL witness. Existing approvedAt/status rows remain preserved without invented identity and are not sufficient for official-paper eligibility. For a command inserted by the current transaction, require afterVersion=root.version and its affected afterFacts/outcome agree with final state. For older immutable events only structural/history bindings remain enforced: never require an old piece/issue/proposal snapshot to equal later current state. Existing source terms remain protected by unchanged P03 checks.
5. Every newly inserted command's retained actor/operation/target, before/afterVersion, outcome and associated issue/proposal rows are compatible. An AMEND acceptance applies only the four stored selection IDs/labels and no unapproved data; cancellation cannot apply proposed fields. Head-state checks run for the inserted aggregate-head event; later root updates do not reapply old command outcomes. Open issue/current-pointer checks always cover the current graph.

Do not replace P03's `check_sales_order_graph`: it continues to require header.totalAmount equal sum of noncancelled frozen prices, full stable piece membership and a current return version. P04 cancellation updates piece and total in the same transaction; fully cancelled total zero is allowed while required membership remains 1..200 retained pieces. Counts/money are derived through existing `deriveOrderCounts`/`calculateOrderMoney`; no stored percentage or refund record is added.

## Transition table

| Command                        | Required starting state                                                                                        | Persistent result                                                                                  |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| APPROVE_INITIAL                | Header AWAITING_APPROVAL; no initial approval; every active piece AWAITING_APPROVAL/INCOMING, no issue         | Header APPROVED/approvedAt; all active pieces CUTTING/INCOMING; one event/root version increment   |
| RETURN_INITIAL                 | Same eligible pending revision                                                                                 | Header RETURNED + current proof; pieces unreleased; one event/root increment                       |
| REPORT_ISSUE                   | Header APPROVED; current piece CUTTING/PRODUCTION/QUALITY, INCOMING/IN_PROGRESS, no issue/receipt/cancellation | Preserve source stage; workState BLOCKED; pointer to new APPROVAL_REVIEW issue; one root increment |
| RESOLVE_ISSUE A                | Current issue APPROVAL_REVIEW                                                                                  | Resolve issue; clear pointer; selected CUTTING/PRODUCTION + INCOMING                               |
| RESOLVE_ISSUE B                | Current issue APPROVAL_REVIEW                                                                                  | SALES_CONTACT; retained explicit target; source stage/BLOCKED unchanged                            |
| RESOLVE_ISSUE C                | Current issue APPROVAL_REVIEW                                                                                  | Resolve/cancel retained piece; CANCELLED/BLOCKED; clear pointer; exact total recalculated          |
| SUBMIT_CONTACT                 | Issue SALES_CONTACT; actual owner sales                                                                        | Insert immutable proposal; latestProposal pointer; REAPPROVAL; held piece unchanged                |
| REVIEW_CONTACT ACCEPT          | REAPPROVAL + latest AMEND                                                                                      | Apply only stored four selections/captures; resolve; clear pointer; retained target/INCOMING       |
| REVIEW_CONTACT RETURN_TO_SALES | REAPPROVAL + latest proposal                                                                                   | SALES_CONTACT; preserve target/latest proposal; held piece unchanged; reason retained in event     |
| REVIEW_CONTACT CANCEL          | REAPPROVAL + latest proposal                                                                                   | Same retained cancellation logic; never apply unapproved proposal                                  |

Every row also produces one ApprovalCommand and root version+1. If cancellation removes the final active piece set header status CANCELLED; otherwise retain APPROVED. Paid remains unchanged. Initial return and piece return are separate operations: piece workflows never set whole-order RETURNED or alter P03's resubmission proof.

## Forward migration and existing-data strategy

Proposed migration: `packages/database/prisma/migrations/20261106000400_p04_approval_piece_issues/migration.sql`. Its implementation must confirm that this next name remains unused; create a later forward migration if another accepted migration has since claimed it. This plan creates no SQL file and executes no migration.

Use one additive migration: create new enum types/tables/indexes/functions; add relations/FKs/graph triggers; leave nine existing SQL files byte-identical. New enum values are not added to pre-existing enum types, so no split enum-use migration is needed. All application tables keep existing data unchanged.

Before adding issue bindings, inspect the target in a separately authorized read-only migration preflight for pre-existing nonnull issue pointers. P03 has no persisted issue producer; any such value has no accepted issue/source/report history to infer. Do not fabricate records, null pointers, reset states or import local MVP fixtures. Orphan/noncanonical issue pointers are a deployment reconciliation gate: report nonsecret counts and stop that binding migration until a reviewed forward treatment is authorized. Existing valid P03 approved/returned graphs, including controlled consumer fixtures without real P04 witnesses, remain byte-identical; do not retroactively invent approvers or receipts and do not close official-print acceptance from approvedAt alone. New-transition triggers apply to future transitions rather than validating nonexistent prior history. Normal populated P03 upgrade requires no data rewrite/backfill. Preserve all account/customer/catalog/submission/sequence/price/contact records.

Migration verification must include fresh deployment, populated P03 upgrade containing drafts and awaiting/approved/returned controlled graphs, all prior checksums/rows unchanged, repeated deploy, sidecar constraints, immutable records and orphan-issue legacy data failing atomically without mutation. Current fixture helpers that perform a new approval/return transition after this migration must use real P04 service decisions where claiming live acceptance, or insert a complete explicitly controlled witness graph for a P03 consumer-only boundary case. Historical fixture meaning remains labelled; synthetic witness data never certifies real P04 execution or official-print authority.

Rollback is forward recovery or restoring an approved backup before incompatible writes; no down migration deleting retained decision history. Do not remove tables after business decisions exist. Production execution/backup/restore remain separately authorized release work.
