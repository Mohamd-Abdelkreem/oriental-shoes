## 1. Verified foundations and compatibility

Current owners inspected: `packages/contracts/src/{auth,account,http}/*.schema.ts`, `apps/api/src/modules/{auth,users}/`, `apps/api/src/middlewares/{auth,authorization,csrf,validation}.middleware.ts`, `apps/api/src/core/{errors,pagination,responses}/`, `apps/api/src/router.ts`, `apps/api/src/infrastructure/security/jwt.service.ts`, `apps/web/src/services/api/api-client.ts`, and existing auth/users adapters and tests.

Existing `authUserDataSchema`, `authSessionDataSchema`, `safeUserSchema`, `userRoleSchema`, request schemas, `successEnvelopeSchema`, `errorEnvelopeSchema` and `paginationMetaSchema` are reused. No second envelope, transport, auth context or token protocol is introduced. The installed contracts package uses Zod 4.4.3; use its already-established `z.uuid`, `z.iso.datetime`, strict objects and inferred input/output types. Existing API responses are built through `ResponseHelper.ok(response,data,message,path,requestId)` or `.created` for registration.

Changing SafeUser adds required nullable fields and new status values: producer, mapper, OpenAPI, browser parsers, fixtures and consumers must change together. This is a coordinated P01 deployment; do not run the new frontend against an old API/schema, or old business services against the new authority schema. Migration/rollback order belongs to data design. Unknown/missing fields cannot be filled with a default department, approval or demo identity to bridge versions. The current root roadmap remains unchanged.

All route paths below are relative to the configured API prefix (`appConfig.apiPrefix`, default `/api/v1`). JSON success/error content types and existing request-ID/timestamp/path fields remain unchanged. Public message strings remain safe English API messages; the existing Arabic UI maps known codes/field failures. No credential is added to ordinary URLs or response fields. Purpose-bound verification/reset query credentials retain their existing dedicated flow and redaction controls.

## 3. Identity sessions, authority and middleware

### 3.1 One existing session protocol

Credential-valid login for any extant account may create an identity session, including unverified, pending, rejected and suspended states. It returns the current expanded SafeUser and the same access token/refresh cookie/CSRF cookie protocol. This implements private own-status access; it never represents business eligibility. Wrong password and nonexistent email both remain `401 UNAUTHORIZED` with the same safe invalid-credentials response, and return no account object/cookies.

Refresh uses the current token-family absolute expiry, stored hash/id/user binding, one-time consumption and replacement record. It can rotate into a restricted identity session while returning the account's actual current state. It cannot reactivate, approve or preserve an old department. Token role/email claims remain protocol-compatible but current database role/state/department determine authority. No new access-token revocation store or persisted browser credential is introduced.

Keep access token in module memory, refresh token HttpOnly cookie and CSRF token readable cookie; preserve cookie attributes/paths/expiry and remember-me family durations. Public verification/reset purpose credentials stay in their existing dedicated query flow only. No return-location field is added to login HTTP input; the frontend validates its requested route against current identity authority.

Row/count reads share one repeatable snapshot or the equivalent data-design read transaction and current ADMIN authority lock. `pagination.total` counts exactly the current scope+search (or selected target history), while `pendingCount` independently counts all verified pending USERs, regardless current scope/search. No frontend page-local search or fixture fallback.

The search is literal substring matching, preserving the existing screen's meaning. Proposed `escapeStaffSearch(search:string):string` in `staff.queries.ts` prefixes each backslash, percent and underscore with a backslash before passing it to Prisma `contains` filters with `mode:'insensitive'`. Proposed `buildStaffWhere(query:StaffListQuery):Prisma.UserWhereInput` combines the selected scope and the three-field OR using that escaped value; rows/count use the same result. Do not accept caller regex/wildcard operators. PostgreSQL pattern escaping is documented in [PostgreSQL 18 LIKE](https://www.postgresql.org/docs/18/functions-matching.html#FUNCTIONS-LIKE), and the supported Prisma case-insensitive filter is documented in the [Prisma v7 client reference](https://www.prisma.io/docs/orm/v7/reference/prisma-client-reference#mode). These are query mechanics, not a new full-text/search product.

Use current pagination metadata `{page,limit,total,totalPages,hasNextPage,hasPreviousPage}` both in domain `data.pagination` and the existing derived envelope `paginationMeta`; values must agree. Zero total means zero pages. An out-of-range positive page returns empty items with truthful total/pages/flags, never another employee's page; frontend offers/clamps to an available page after refetch. Pagination is stable ordering of a changing set, not a frozen multi-request snapshot.

## 5. Decision identity, replay and safe reconciliation

The UI allocates a lowercase UUID commandId for a confirmed intent and keeps it with the original expectedAccessVersion/department while awaiting its outcome. It is not a secret and must not be generated from array length/email. A different intent or freshly reviewed target version gets a new UUID. Global effective-command identity is enforced by `StaffDecision.commandId`, not an in-memory cache.

Ordered command behavior, using the data design's account locks and one transaction:

1. Normalize/deduplicate/sort actor and target UUIDs, then acquire `write` account locks for both in that order. Reload and recheck the acting account under the transaction; require current verified ACTIVE ADMIN before exposing or changing the target. The actor cannot be the target because ADMIN targets are forbidden. The single lock mode deliberately serializes an administrator's concurrent staff writes and avoids a mixed-mode helper.
2. Load target and deny missing target404 or ADMIN target403. Read any existing effective command receipt with the global commandId.
3. For an existing receipt, compare actor ID, target ID, requested endpoint operation and normalized original payload, including original expectedAccessVersion and department. Any mismatch →409 STAFF_COMMAND_CONFLICT. Semantic event actions such as RECONSIDER do not replace endpoint operation binding.
4. Exact receipt replay succeeds only if target current accessVersion and current authority fields equal the receipt's committed after-version/snapshot. Otherwise →409 STAFF_ACCESS_CONFLICT. Return current safe target plus original decision and `replayed:true`; append nothing and do not touch timestamps/version.
5. With no receipt, expectedAccessVersion must equal the target's current accessVersion; otherwise →409 STAFF_ACCESS_CONFLICT before any no-op/transition handling. This prevents a stale request from being disguised as an unchanged action.
6. A supported same-intent current-result no-op returns `{staff:current,decision:null,replayed:false}` without a version, timestamp or successful-decision change. Its commandId is deliberately **not reserved**: no effect means no StaffDecision receipt. Retrying it remains safe through expectedAccessVersion; changed intent must receive a new client UUID. No generic no-op receipt subsystem is introduced.
7. Validate the named transition. Invalid current state →409 STAFF_TRANSITION_CONFLICT. Apply the one allowed change, increment accessVersion once and store the actual decision snapshots/actor/time together. Commit must return `{staff:result,decision:event,replayed:false}`; no decision may report success after rollback.
8. A globally conflicting commandId or transaction conflict is reconciled by the same full operation with the same normalized input under the bounded retry policy in data design. Never blindly retry an arbitrary connection/unknown-commit failure. Any observed later change remains conflict.

Response schema relationships: `replayed:true` requires a non-null decision; a null decision is the unchanged outcome only; a non-null applied decision has the returned target's after accessVersion/authority snapshot. No error carries a raw database account, partial success or an added error `data` object. The client uses the existing detail/history reads to reconcile uncertainty and displays failure/conflict honestly. Unknown transport outcome cannot create a new command intent automatically.

## 6. Safe errors and response parsing

### 6.1 Stable error owner and code table

Keep the existing error envelope and current safe handlers. New feature error classes extend existing `AppError`; they do not change `ForbiddenException`/`ConflictException` globally. Proposed `apps/api/src/modules/auth/auth.errors.ts` owns `AccountRestrictedError` and `DepartmentAccessDeniedError`; proposed `modules/staff/staff.errors.ts` owns `StaffAdminTargetForbiddenError`, `StaffNotFoundError`, `StaffAccessConflictError`, `StaffCommandConflictError` and `StaffTransitionConflictError`, respectively matching the named staff codes below. Each new error has a no-argument constructor with a fixed safe message/status/code and no raw cause/payload retained. Existing anonymous classification remains exactly 400 BAD_REQUEST or 401 UNAUTHORIZED where currently expected.

| HTTP / code                                  | Meaning and protected state                                                                                                                                                                               |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400 VALIDATION_ERROR                         | Existing shared parsing failure, unsupported/invalid fields; no write.                                                                                                                                    |
| 400 BAD_REQUEST                              | Existing pagination numeric/default/range error, missing refresh credential, invalid verification credential, incorrect current password or reused new password as specified above; no authority granted. |
| 401 UNAUTHORIZED                             | Missing/invalid/expired identity credential, nonexistent identity, bad login/reset credential or used refresh; no private account/state disclosure.                                                       |
| 403 ACCOUNT_RESTRICTED                       | Valid identity lacks current business eligibility; keep identity session, load own current status, never treat as anonymous success.                                                                      |
| 403 DEPARTMENT_ACCESS_DENIED                 | Business-eligible employee requests a different department; ADMIN exemption remains explicit.                                                                                                             |
| 403 FORBIDDEN                                | Existing role denial, CSRF failure or CORS denial; preserve the same shared code and safe contextual message.                                                                                             |
| 403 STAFF_ADMIN_TARGET_FORBIDDEN             | Authorized staff caller selected ADMIN for a write; no account/history change.                                                                                                                            |
| 404 STAFF_NOT_FOUND                          | Authorized ADMIN selected an absent staff identity; no fallback target or history change.                                                                                                                 |
| 409 STAFF_ACCESS_CONFLICT                    | Expected version stale, exact replay after a later authority change, or replay snapshot mismatch; preserve winning state and refresh/review.                                                              |

| 429 RATE_LIMIT_EXCEEDED                      | Existing TooManyRequestsException code, envelope and limiter headers; no automatic mutation retry.                                                                                                        |
| 500 INTERNAL_ERROR / 503 SERVICE_UNAVAILABLE | Existing safe unexpected/infrastructure failure; never fake empty staff or completed decision. A lost response may leave outcome unknown, requiring observation.                                          |

Do not attach account restrictions to public credential failures. Restricted-session errors are private only after identity validation. Non-admin staff callers fail before a target lookup and receive no existence information. Password-current mismatch and reset/verification failures preserve their existing safe error distinctions; do not replace all auth errors with a new staff code.

### 6.2 Runtime response validation and central transport

Auth/users/staff adapters and the central refresh interceptor receive unknown response data, parse existing successEnvelopeSchema, parse the operation's data schema, and only then install credentials or update server state. Invalid envelope/data must not install a token, return null, synthesize staff, or claim success. Root frontend design owns exact API/hooks symbols and epoch protection, referencing this wire ledger.

Add proposed exported `parseApiResponse<T>(raw:unknown,dataSchema:ZodType<T>):ApiResponse<T>` and `ApiContractError` in `apps/web/src/services/api/api-client.ts`. The error has `constructor(requestId:string='')`, a fixed safe message and readonly sanitized requestId, without retaining raw issues/payloads. Extend existing `getApiError` to return `code:'CONTRACT_ERROR'`, `statusCode:502`, no fieldErrors and that requestId for this class. The 502 value is a local safe classification, not a claim that the server returned HTTP 502. This is distinct from existing network/HTTP classification and is not automatically retried. Central refresh parsing must use full AuthSessionData, not its current static tokens-only generic.

Preserve single-flight refresh and at-most-one protected-401 replay. A business 403 does not initiate refresh; the UI reloads own current-user state before safe navigation. Keep exact anonymous refresh recognition; network/403/429/500/503/malformed-response failures remain visible errors and never become anonymous success. Existing refresh-failure token-clearing policy remains, with errors propagated; no additional redirect for these non-anonymous failures. Token-bearing query keys and old-account late-result installation are resolved by the frontend design, without a parallel session owner.

The frontend transport owns the exact reasoned epoch/restore-policy/subject algorithms in frontend §§2.1/3. A new document permits initial parsed restoration; a bound epoch accepts only its expected subject. Passive mismatch raises `AuthIdentityChangedError`, clears unusable token, retains expected subject and closes restoration. An explicit login attempt creates a credential-required epoch; failed/malformed/unknown credential outcomes leave that gate closed. Only `acceptCredentialLogin` after fully parsed successful credentials for that current required epoch binds the subject/token and reopens restore. Passive `setAccessToken` cannot do so. Confirmed current-originating-scope session endings create signed-out; same-document loadSession returns known null without passive refresh. Navigation/retry/token clearing alone never reopens a closed policy.

Both client errors have no-argument safe constructors: `AuthIdentityChangedError` maps to local `AUTH_IDENTITY_CHANGED`/409; proposed `AuthReauthenticationRequiredError` maps to local `AUTH_REAUTHENTICATION_REQUIRED`/409 with fixed "Sign in again to continue." message, empty request ID/field errors and no subject/credential disclosure. These are not server HTTP replies, staff conflicts or automatically retryable transport failures. Public login/purpose forms remain available; protected/status work stays blocked. Frontend F-ID/F-ROUTE fixes guest-before-pending resolution, exact getter/acceptance signatures and the sole GuestOnlyRoute navigation effect. That effect uses current canonical session/Query/epoch/URL checks and the shared full-user safe target resolver; LoginForm performs no success navigation. Restricted account-switch reachability remains a local path-entry presentation decision, never an authority grant.

This credential lifecycle is bounded to one live document. A full reload starts ordinary cookie restoration; no persistent quarantine is introduced. Same-tab raw-adapter serialization orders known cookie-mutating settlements only, with release before response interception. It promises neither rollback of unknown Set-Cookie outcomes nor cross-tab serialization. Existing server routes/envelopes/credentials and one QueryClient account owner remain unchanged.

## 8. Required contract evidence

Implementation must extend actual discovered contracts/auth/API/web tests, not create ceremonial unrun examples. The feature plan selects commands/test paths and infrastructure. Required cases include:

- Existing auth input bounds/normalization/remember-me, no requested department or privileged field acceptance; new strict SafeUser shape and state/assignment refinements; every response excludes credentials and approver internals.
- Auth real HTTP registration/verification now pending, credential-valid private restricted session, correct/wrong department and ADMIN exemption, current-user/refresh in restricted states, CSRF and token replay, active-only recovery/reset, and failed account/session operations.
- Staff auth/role/target denials, each named transition, legacy preparatory approval without reactivation, same-intent no-op, stored receipt replay, global command binding mismatch, stale-after-later-change conflict and atomic rollback/concurrent actor-target changes.

- Runtime malformed account/staff/history/envelope parsing including central refresh; distinguish CONTRACT_ERROR from offline/anonymous state, no credential installed from malformed data, and no 403 refresh loop.

Reading existing source or this contract establishes design only. It does not establish implementation, backend acceptance, browser acceptance, production configuration or successful runtime tests.
