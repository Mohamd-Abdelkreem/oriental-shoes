## Summary

Extend the existing identity foundation rather than replace it. Correct credentials establish one identity session, including a restricted account's private status. A separate current-record business guard requires verified ACTIVE status and, for an employee, explicit approval and one department; verified active ADMIN is exempt from employee assignment. Existing JWT, refresh rotation, cookies, CSRF, transport and QueryClient remain the protocol owners.

Ordinary staff changes use named commands, an observed access revision, a client-generated command UUID, deterministic user-row locks and a retained decision committed with the state change. The current result can be safely observed/replayed; stale intent never overwrites a later decision. Existing verified USERs become unassigned pending-review accounts; suspensions remain. ADMIN provisioning is a separately restricted, audited initial procedure, not another staff endpoint.

Complete the required backend group and its real database/HTTP acceptance before connecting the existing staff/status/account screens. Preserve the current Arabic/RTL/Cairo presentation and reached operational UI. P02–P08 domain data, print widening and production release are excluded.

This feature plan is separate from protected root `plan.md`. Root-roadmap owner review and OPS-01 release inputs remain open under their existing scope; this PLAN request does not approve execution.

## Contracts, Authority and Failure Design

The complete schema, HTTP/middleware and error ledger is [contract §§2–7](contracts/identity-access.md#2-contract-symbol-ledger). Its semantics are mandatory for all operations below. Missing/invalid identity is distinct from a valid restricted account, wrong department, validation, absent target, stale state and infrastructure failure. Malformed successful responses are local `ApiContractError`/`CONTRACT_ERROR`, not offline/empty/anonymous success. Producer and consumer change together; old binaries cannot remain writers against the new account constraints.

The common protected read/write, replay and migration algorithms are [data §§4–8](data-model.md#4-effective-employee-transitions). A route's early middleware snapshot is not the write-time authorization check. Restriction changes lock the same user rows that P01 writes/read transactions check. Later domain services must consume that authority seam; no dummy operational endpoints are added to pretend those phases exist.

The complete frontend policy is [frontend §§2–7](frontend-design.md#2-interface-and-file-action-ledger). One account/session query remains; the transport's monotonic epoch guards obsolete work without storing a second account. Restricted identity sessions can use private status/current-user and exit; profile/password/staff business operations remain denied. Success is published only after authoritative confirmation and only in the originating identity scope.

## Operation Blueprints

### OP-01 — Registration and verification resend

**Requirements**: FR-001, FR-002, FR-015, FR-016, FR-021, FR-025; Story 1 and the registration/boundary examples.

**Interfaces/owners**: REUSE `AuthService.register(data:RegisterBodyDto):Promise<AuthResponseWithoutTokens>` and `resendVerification(data:EmailRequestBodyDto)` in current auth.service; current AuthController/route limiter/DTO/EmailService owners. Exact HTTP and response schemas: contract §4.1. Existing registration returns created account only after awaited verification delivery; resend returns its neutral result. Input has no department/authority fields.

**Read context / current gap**: AuthService register/resend, `auth.rate-limiters.ts`, EmailService/EmailDelivery, registration form/hooks and auth service/controller/integration tests. Current registration compensation is useful; fixtures/requested departments and new notification channels are not requirements.

**Algorithm**:

1. Parse/normalize through existing shared schemas and retain current source/account rate limits. Reject unsupported privileged fields and duplicate normalized email under the existing conflict policy; do not disclose review state in that conflict.
2. Hash password outside a database transaction. Create USER/PENDING_VERIFICATION with no employee fields and version 0, retaining one-time verification hash/expiry. Uniqueness is enforced by the database, not only a precheck.
3. Deliver verification through existing EmailService outside the transaction. Preserve awaited registration delivery and conditional cleanup keyed to this still-unverified account/token on delivery failure; do not delete a later verified/changed account. Cascade cleanup of this failed new identity's refresh records follows the existing relationship. Return safe data only; delivery failure is existing safe service-unavailable feedback, not successful registration.
4. Resend selects only eligible pending-verification identity, respects current cooldown, conditionally replaces the matching old hash/expiry once and sends outside transaction. The public result stays neutral for missing/ineligible/cooldown and delivery outcomes. Existing detached resend mail is not a durable delivery guarantee. Retrying registration cannot create a second normalized email identity.

**Frontend**: Existing register/resend hooks/forms and F-LINK; preserve error draft/pending states, exact password significance and optional phone. No required requested department is added.

**Concrete checks**: Existing `auth.schema.test.ts`, auth service unit and real auth/app integration: name/email/phone/password bounds; duplicate email; rejected privileged fields; verified-versus-unverified compensation race; provider failure; neutral resend/cooldown; no credentials in returned account/logs. New mail doubles remain outside the database claim. Browser case C1 below proves actual verification-link use.

### OP-02 — Redeem email verification

**Requirements**: FR-002, FR-006, FR-011, FR-022; Story 1.

**Interfaces/owners**: MODIFY existing `AuthService.verifyEmail(token:string):Promise<AuthResponseWithoutTokens>` and existing verification presentation; no new endpoint/token type. Contract §4.1, data §6 and F-LINK own response, transaction and visible state.

**Algorithm**:

1. Verify the existing purpose-bound signature/claims and normalize its email; find a candidate matching token hash/expiry. Never treat email or a valid-looking token string as authority by itself.
2. In one transaction acquire the candidate user write lock, reload, and require pending verification, no verification timestamp, matching hash and unexpired token. Invalid/consumed/changed predicates return existing safe failure without state/event changes.
3. Consume token hash/expiry and set one server verified time. USER becomes PENDING_APPROVAL with all employee fields absent; increment accessVersion. An existing ADMIN pending verification may become verified ACTIVE with no employee fields; this never promotes a USER. Suspended/review/rejected states cannot be activated by this operation.
4. Require one affected row, map expanded SafeUser and commit. No staff decision is fabricated because no administrator approval occurred. Second redemption fails rather than granting/repeating approval.

**Frontend/checks**: F-LINK changes activation wording to verified/awaiting review, guards token replacement/late completion and keeps tokens out of query keys. Existing auth service/integration tests plus proposed verify-email-panel test and real browser C1 verify pending state, no department and denied business access. An expired/replayed link leaves account/approval unchanged.

### OP-03 — Identity login, current-user, refresh and business authorization

**Requirements**: FR-003, FR-011, FR-012, FR-015, FR-016, FR-020, FR-021; Story 3 and current-session examples.

**Interfaces/owners**: Current AuthService login/refresh signatures and UsersService.getCurrentUser remain; contract §3 fixes `createIdentityAuthenticationMiddleware`, existing business middleware, `authorizeDepartments` and revised route-factory signatures. Data §6 fixes `AUTHORITY_ACCOUNT_SELECT`, `AuthorityAccount`, `lockAccountRows`, `loadIdentityAccount`, `assertBusinessAuthority`. Frontend F-ID/F-ROUTE fixes loadSession, token acceptance, epoch and navigation signatures.

**Algorithm**:

1. Login normalizes existing input, loads the credential record and compares password outside a short transaction. Missing/wrong credentials share current 401 feedback and no returned account/session. Inside the transaction lock the user for read, reload the private credential separately from the public authority selection and require the hash just compared still to match; a raced password change returns unauthorized.
2. Create the existing JWT/refresh record from current identity/role/email and remember-me duration. Correct credentials may establish identity for any extant state. Restricted status is truthful account data, not business authorization. No second token protocol or browser storage is introduced.
3. Refresh verifies existing cookie/CSRF/family binding, locks the user before token record work, consumes the stored original refresh once and creates its replacement within the same transaction. Retain original absolute family expiry and remember-me policy; return current SafeUser even if restricted. Invalid/missing/used token preserves existing error classes. A rotated restricted session still cannot work.
4. Identity middleware verifies bearer and loads a current extant selected account, sets private no-store and `request.user`; current-user returns that own account only. Business middleware uses the same current resolution then current verified ACTIVE checks, employee approval/department or ADMIN exemption. Optional department guard checks requested scope. New business 403 never triggers a refresh/replay loop.
5. Protected service reads acquire current actor read lock and run scoped queries in their transaction; writes use write locks and recheck authority. A saved suspension/reassignment therefore governs subsequent operations despite old JWT claims. An already-running operation can linearize before the change; no claim of erasing already-viewed content or live push is made.
6. Browser F-ID validates response before token/cache publication, preserves exact expected-anonymous pairs, and uses the epoch plus its bound subject ID for login/refresh/request replay/manual cache writes. Same-tab cookie-mutating auth requests are serialized; their dispatch rechecks epoch. A refresh returning another subject raises local AUTH_IDENTITY_CHANGED and blocks token installation/request replay. A credential attempt moves to a closed credential-required policy; failure cannot reopen passive restoration. Only a fully parsed successful login for that attempt binds its subject and reopens restore. F-ID fixes the reasoned epoch/acceptCredentialLogin/getAuthSessionRestorePolicy interfaces, local AUTH_REAUTHENTICATION_REQUIRED outcome, canonical login publication, sole GuestOnlyRoute navigation and signed-out handling. Known response settlement ordering is not a rollback guarantee for unknown or cross-tab cookie effects. F-ROUTE fresh-reads current identity on pathname entry before mounting protected content, and re-resolves business/department denial without loops/flashes. Full signatures/error/reauthentication behavior are owned once in frontend F-ID/F-ROUTE. I2 makes GuestOnlyRoute the sole post-login navigator using the current-user safe return target. Its same-file Suspense body reads the URL, preserves restricted account-switch access through a path-entry epoch and rechecks live URL/current Query/canonical identity/epoch immediately before replacement; LoginForm only submits credentials and handles errors.

**Cases**: All six employee departments, ADMIN exemption, every restricted state, missing/wrong credentials, malformed auth/refresh data, CSRF, two simultaneous refreshes and token replay; compare-hash race; two already-open sessions suspended/reassigned; old response/finally cannot replace new identity. Owners: existing auth service/app integration, auth hooks/transport/routes/safe-return tests, proposed account-access/status guard tests, browser C1–C3. No later-domain persistence is claimed by calling an unbuilt endpoint.

### OP-04 — Staff directory, detail and retained decision reads

**Requirements**: FR-004, FR-005, FR-014, FR-016, FR-024; Story 2.

**Interfaces**: Proposed StaffService `listStaff`, `getStaff`, `listStaffDecisions` and controller handlers in contract §7; exact GET paths/schemas/pagination in §4.2; query/mapper signatures above. Data §6 supplies current ADMIN lock. Frontend F-STAFF-READ owns actor-scoped keys, eligibility, query signals, search, controlled pagination and dialog history.

**Algorithm**:

1. Run business guard, ADMIN role and strict params/query validation before target lookup; non-admin callers receive no directory/count/existence information.
2. Open a short RepeatableRead transaction, read-lock current actor and recheck verified active ADMIN. Execute row/count/pending-count queries on that same transaction for one consistent read. A recognized P2034 abort may retry the full read once with current checks; other failures stay visible.
3. Apply the exact scope/search and ordering in contract §4.2. The all-staff directory can read ADMIN rows but displays no staff mutation controls for them. Pending count is global verified-pending USER count, independent of the current search. Never fetch all rows for browser filtering.
4. For detail/history resolve the selected stable user ID, return missing-target404 without fallback. Use safe account/decision projection; history order is actual decision time with ID tie-break. Match domain/envelope pagination including zero/out-of-range pages. Commit/read completion releases the actor lock before network work.

**Checks**: Proposed staff service unit/integration and contracts tests plus app HTTP: case-insensitive name/email/phone substring across pages, null phone, search bounds, pending count, consistent metadata, no-match versus failed read, read-only ADMIN, absent target, historical names retained. ### OP-05 — Named staff changes and safe reconciliation

**Requirements**: FR-005–FR-016, FR-022, FR-024; Story 2, concurrency and unchanged-state examples.

**Interfaces**: Five named StaffService commands (approve, reject, changeDepartment, suspend, reactivate), typed body/response and handlers are fixed in contract §§2,4.3,5,7. Approve covers pending approval, rejected reconsideration and suspended legacy preparation. Wire operation and semantic audit action remain distinct. Full canonical transaction is data §§4–5; do not duplicate a second transition implementation per endpoint.

**Ordered implementation**:

1. Apply business/ADMIN/CSRF/strict validation, derive actor, then enter the common short transaction. Normalize/deduplicate/sort actor and target UUIDs and lock both for write; current actor must still be verified active ADMIN. Missing target404 and ADMIN target403 are checked before target transition/replay can disclose a result.
2. Classify recorded command identity, exact payload/base-version binding and current-result replay; otherwise require expected current version, then eligible no-op or the exact data §4 transition. No-op returns no decision and does not reserve its UUID. A stored key with altered binding or a stale-after-later-change replay is a conflict, never silent success.
3. Perform the conditional allowed-field write, increment revision once and insert immutable actual-actor/time/before/after decision in the same transaction. Decision-insert failure rolls back account/revision. Recognize only the named global command uniqueness race and bounded transaction abort retry described in data §5; no generic retries of unknown outcomes.
4. Return explicit safe staff/current decision/replayed result. No notification delivery occurs. Record no successful decision for denied, cancelled, invalid, stale or rolled-back intent.
5. F-STAFF-READ applies the same-target accessVersion merge at Query.setData through structuralSharing and at mutation publication through a functional updater; actor/epoch fencing is also required. Original command receipts remain unchanged when a newer cached target wins. F-STAFF-WRITE retains original UUID/version/payload for uncertain outcomes, reloads the same target/history through that guarded detail path and reconciles from committed cache. A changed intent gets a new UUID after review. Pending/dismissal/conflict/draft/focus and affected cache invalidations are fixed in frontend §§5–7; no optimistic authority or local MVP patch is used.

**Cases**: Each exact state-table row plus no-op, wrong actor/ADMIN target, invalid/null/multiple department, wrong source, stale version, key mismatch, exact retry, later-version retry, same key across targets, actor suspension ordering and forced dependent insert rollback. Tests: proposed `staff.service.test.ts`, `staff.service.integration.test.ts`, `staff.schema.test.ts`; real HTTP in app integration and the frontend owners listed in §8 of frontend design. ### OP-07 — Password recovery and purpose-link validation/reset

**Requirements**: FR-016, FR-018, FR-021, FR-024; Story 4.

**Interfaces**: Retain existing forgotPassword/resetPassword/validateResetToken signatures, routes/limiters and EmailService. Contract §4.1 fixes exact safe outcomes; data §6 fixes locked credential checks; frontend F-LINK owns token-safe validation lifecycle and transient versus invalid feedback.

**Algorithm**:

1. Forgot-password returns the current neutral public result for nonexistent or currently ineligible identity. Only verified ACTIVE accounts with required business eligibility can receive usable recovery. Acquire user write lock before replacing the recovery hash/expiry; if eligibility changed, leave credentials unchanged and return neutral. Generate/hash token without external network work in the transaction.
2. Send the current reset email outside the transaction. Preserve neutral acknowledgment and safe classified logging for detached failure; this is not durable/guaranteed delivery or an approval message. A newer recovery request replaces the earlier token; only the currently stored hash is usable.
