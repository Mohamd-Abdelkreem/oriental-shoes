## 3. Single-session lifecycle and late-response algorithm

### F-ID — Login, restoration, refresh and account changes

1. `sessionQueryOptions(queryClient)` is the single options/query-function owner for `AUTH_SESSION_QUERY_KEY`, built with installed `queryOptions` and containing 60-second stale time, five-minute collection, `retry:false` and the epoch/subject/version-safe query function described below. `useSession(options?)` calls `useQuery` with this object and `enabled:options?.enabled ?? true`. Normal existing observers retain mount/focus/reconnect behavior; route-entry guards observe with `useSession({enabled:false})` and start the explicit entry read in F-ROUTE. Both observe the same cache/key, never a second account store. Do not introduce polling or push.
2. Before token or HTTP work, `loadSession` captures epoch/signal and reads `getAuthSessionRestorePolicy()`: signed-out returns known local `null` with the normal epoch/signal settlement checks; credential-required throws `AuthReauthenticationRequiredError`; identity-changed throws `AuthIdentityChangedError`; only restore follows the existing refresh/current-user sequence. If the memory token is absent, await the epoch-owned shared refresh and recheck epoch/signal before `usersApi.getMe(signal)`. A refresh waiter never forwards its AbortSignal to the shared raw cookie attempt; check it before joining and after awaiting. Cancelling one waiter does not cancel another observer's rotation. Restricted accounts remain valid `AuthUserData`. Obsolete work becomes cancellation without publication or a new-account error.
3. Apply the credential lifecycle table below. A new document starts in restore mode with no subject. A parsed passive credential may establish the first subject there; an existing bound subject must match every later passive result. Mismatch clears the unusable token, retains expected subject and selects identity-changed. An explicit credential attempt creates a new credential-required epoch; failure leaves it required. Only fully parsed current-epoch credential-login success may bind the attempted identity and reopen restore. Confirmed session endings select signed-out. Navigation, focus/reconnect, read retry, ordinary token clearing and failed commands never reopen a closed gate. Exact server anonymous pairs remain 400/BAD_REQUEST and 401/UNAUTHORIZED from restore/current-user; other errors retain their real classification.
4. Serialize each raw adapter attempt for login, refresh, logout/all, change-password and reset-password through the existing cookie tail. Resolve/store the raw `AxiosAdapter` via installed `axios.getAdapter` and `_templateRawAdapter`; retries reuse it rather than wrapping a wrapper. The queue releases on raw fulfillment/rejection BEFORE response interception, so a protected401 can enqueue refresh and one retry without deadlock. Recheck captured epoch and restore policy at raw dispatch; obsolete epochs cancel. Credential-required/identity-changed/signed-out block passive refresh and ordinary protected dispatch. Explicit login and the existing public registration/verification/resend/recovery/reset flows retain their dedicated permissions; public password recovery is not business authorization. Refresh bearer/CSRF headers at actual dispatch, removing old headers first. Never discard the old raw-cookie tail on an epoch change. Known same-tab Set-Cookie settlement ordering does not prove rollback of unknown outcomes or cross-tab ordering.
5. Each useLogin mutation function begins beginAuthSessionEpoch("credential-login") as its first synchronous operation and keeps that epoch locally. Await old private-read cancellation, recheck epoch, run the observer-preserving private-query clearing sequence below, recheck and call authApi.login(body,epoch). Do not share an onMutate epoch ref with mutationFn; the installed context does not carry that result. The API parses full credentials and calls acceptCredentialLogin; pre-acceptance failures leave the gate closed without cleanup reopening it. After acceptance, recheck epoch and read current identity. A failed getMe leaves the accepted subject bound and surfaces the actual error. Perform the epoch/policy/subject/version-safe session write within this mutation and return setQueryData’s actual canonical AuthUserData object; remove the unqualified onSuccess setter. The public LoginBody→AuthUserData shape stays unchanged. LoginForm only awaits this hook, preserves RHF/pending/errors and suppresses obsolete/cancelled errors by mounted/submission generation. It performs no success router replacement, returnTo resolution, token/cache write or epoch transition. GuestOnlyRoute observes canonical publication and owns all post-login navigation, including restricted credential completion, under F-ROUTE. Thus no form continuation can compete with a guest redirect.
6. Make the existing request interceptor synchronous with the installed Axios `{synchronous:true}` interceptor option. Every Axios request, including public auth calls, receives private `_templateAuthEpoch` at API invocation; initialize it from current transport epoch only when the caller supplied none, and never overwrite it during retry. `authApi.login`/`refresh` explicitly supply their captured epoch, so an old queued public auth request cannot adopt the newer epoch before dispatch. Before 401 refresh/replay and before publishing a successful auth result, require the captured epoch still to match; an old request must never replay using the new account's token. Keep `_templateRetried` one-shot behavior and the existing public-auth path exclusions.
7. `refreshAuthSession(expectedEpoch)` remains the one refresh POST/full-response-parse/passive-token-publication owner for restoration and protected401 interception. Check epoch/policy before initiating or joining; closed policies never POST. Reuse only the same epoch's `{epoch,promise}`; no waiter AbortSignal reaches the HTTP request. Parse complete envelope/AuthSessionData then call passive `setAccessToken` once. False cancels obsolete work; mismatch quarantines before replay/publication. The interceptor awaits this same full promise and checks original epoch/signal before its existing one replay. Finally clears the slot only if promise and epoch still match. A stale settlement cannot reopen a gate, erase a newer slot or cancel another waiter.
8. For logout/logout-all/change-password/reset, capture originating epoch and current actor when applicable before dispatch. Only their confirmed success for that still-current epoch/actor may cancel old private reads, recheck after awaiting cancellation, call `beginAuthSessionEpoch("confirmed-ending")`, run that same observer-preserving private-query clearing sequence and navigate to login. No await may separate a final scope check from the synchronous epoch transition. A superseded successful ending must not clear a newer session or navigate its view. Failure preserves current state/error and never claims revocation. Signed-out loadSession returns known null without cookie restoration until an explicit new login. Refresh failure may clear an unusable memory token without changing restore policy or asserting logout.
9. Manual cache writes and visible completion callbacks from profile/staff/identity operations capture originating epoch/actor. They may publish or announce only in that current scope. Late old-account results cannot repopulate a cleared cache, close another dialog or show success there. Staff keys remain actor-scoped. Same-target staff publication also applies the independent accessVersion commit rule in F-STAFF-READ; actor/epoch agreement alone does not order that employee's versions.
10. Only accepted credential-login success in its required epoch adopts a different subject in this document. Normal initial restore is separate. Same-subject accessVersion changes re-evaluate guards and invalidate private staff reads. After loadSession and epoch checks, the session query returns an already-cached same-subject account when its accessVersion is greater than the delayed response. Profile/login manual setters use the same version comparison. Login returns the canonical published object without creating a component navigation owner; GuestOnlyRoute checks that exact current session object, successful Query state, current epoch/policy and live URL before redirecting. Cross-subject versions never authorize adoption. Query remains the account owner; transport keeps only credential-lifecycle metadata.

#### Observer-preserving identity cache clearing

The existing session observer must remain attached to the same Query across credential submission and canonical publication. In auth.hooks.ts, use one private `clearPrivateQueries(queryClient: QueryClient): void` helper: synchronously set `AUTH_SESSION_QUERY_KEY` to `null` with `setQueryData<AuthUserData | null>`; capture its exact Query using `getQueryCache().find({queryKey: AUTH_SESSION_QUERY_KEY, exact: true})`; remove every other Query with `removeQueries({predicate: query => query !== sessionQuery})`. The null write creates the session Query if absent and preserves its object if observed; it also removes old identity/error data. Do not use QueryClient.clear, remove the session Query, reset it into an automatic fetch, or clear the running mutation cache. The calling F-ID5/F-ID8 sequences own cancellation and epoch/actor checks; no await separates their final scope check from this synchronous helper. Old private query data is removed, while the observed session Query remains to notify GuestOnlyRoute when current identity is later published. QueryClient.clear/removeQueries destroys removed Queries; a subsequent setQueryData can create a new Query that an existing observer has not joined. Do not rely on LoginForm's local mutation renders, incidental parent renders or background fetches to repair that subscription.

#### Credential lifecycle and dispatch decisions

| Event / current boundary                                             | Resulting policy and subject                               | Passive behavior                                                                         |
| -------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| New browser-document module                                          | restore; no subject                                        | Ordinary initial cookie restoration may bind its first parsed identity.                  |
| Bound normal session                                                 | restore; expected subject retained                         | Same subject only.                                                                       |
| Explicit credential login begins                                     | credential-required; new epoch, token/subject cleared      | No focus/reconnect/route/interceptor refresh or ordinary protected dispatch.             |
| Login rejects, is malformed or has unknown outcome before acceptance | credential-required remains                                | Keep actual login error and form; never fall back to an unbound cookie identity.         |
| Parsed credential login succeeds for current required epoch          | restore; parsed subject/token bound atomically             | Same-subject restoration may proceed.                                                    |
| Passive result has another subject                                   | identity-changed; expected subject retained, token cleared | Reject publication/replay; expose explicit login.                                        |
| Confirmed current-scope session ending                               | signed-out; new epoch, token/subject cleared               | loadSession returns known null; ordinary protected work/passive refresh remains blocked. |

`acceptCredentialLogin` returns false without state changes unless epoch is current and policy is credential-required. Ordinary `setAccessToken` cannot open that gate. `clearAccessToken` clears only memory token, not policy/expected subject. The signed-out and credential-required policies expose no user data; pending/error form state remains owned by the mutation/RHF. This protection lasts for one live document. Full reload starts ordinary initial cookie restoration; no persisted quarantine, cross-tab lock or rollback guarantee is introduced.

A current backend denial is decisive even while a session snapshot is fresh. `ACCOUNT_RESTRICTED` and `DEPARTMENT_ACCESS_DENIED` trigger an awaited session refetch and route re-evaluation, not a write retry. If that refetch fails, show its error and keep protected work blocked. Other authorization denials remain visible and are not universally converted to logout. The local `AUTH_IDENTITY_CHANGED` and `AUTH_REAUTHENTICATION_REQUIRED` outcomes block protected work and offer explicit login without passive refetch; neither is grouped with server 409 staff conflicts. Existing access-token lifetime limits remain as documented; no client code claims universal instantaneous token revocation.
